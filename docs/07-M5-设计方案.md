# M5 设计方案 —— 撤销 / 重做

> 里程碑：M5（在 M4「笔 / 橡皮 / 压感」之后）
> 目标机：希沃一体机（Windows 10/11 x64）
> 状态：**已实施并通过验收**（生产工程与 harness 均 0 warning / 0 error）

---

## 1. 目标与非目标

### 目标
| # | 能力 | 说明 |
|---|---|---|
| 1 | 撤销 | 写一笔、擦一次、清一次空，各可撤销一步 |
| 2 | 重做 | 撤销之后可以再还原回去 |
| 3 | 按钮 + 快捷键 | 工具栏「撤销 / 重做」，`Ctrl+Z` / `Ctrl+Y`；栈空时按钮置灰 |
| 4 | 清除笔迹可撤销 | 因此去掉了原来的确认对话框 |

### 非目标（明确不做）
- **不做笔迹持久化** —— M6。关窗口仍然全丢。
- **不做"撤销工具切换 / 墨色切换"** —— 那些是视图状态，不是纸上的内容。
- **不做撤销栈的落盘** —— M6 一并考虑。
- **不自己实现擦除** —— 沿用 M4 的原生方案，理由见 §2.1。

## 2. 关键技术决策

### 2.1 真相来源：`StrokeCollection.StrokesChanged`

M5 比预想简单得多，原因是一条 WPF 的公开契约：

> `StrokeCollection.StrokesChanged` 事件把**任何**笔迹变化都描述成"移除了哪些、加入了哪些"。

写字、橡皮擦除、清空，无一例外 —— 擦除在 `InkCanvas` 内部就是
**"移除原笔画 + 加入被切分后的碎笔画"**。于是：

**撤销 = 反做（移除 Added、加回 Removed）；重做 = 正做。**

**这一行几何代码都不用写。** M4 选「擦除交给原生机制」在这里第二次收到红利：
因为不自己拆分笔画，也就完全不需要自己实现"把碎笔画拼回原样"。

**更强的一点：本设计不依赖擦除的实现形态。** 不管内部产生的是一次 remove + N 次 add，
还是单个事件里原地替换，只要变更经由这个事件通知就成立 ——
而"回调里带着完整的 `Added` / `Removed`"是公开契约，不是实现细节。

**为什么存对象引用而不是坐标**：被移除的 `Stroke` 仍被撤销栈握着、不会被回收，
加回去就是**原来那一个对象**（harness 用 `ReferenceEquals` 钉死了这条），
几何、颜色、压力样式全部原样 ⇒ 不存在"重建导致失真"的风险。

### 2.2 事务合并：一次落笔 / 一次擦除 = 一步

**问题**：一次拖动擦除会**连续产生多次** `StrokesChanged`（每擦掉一段就改一次集合）。
若逐次入栈，用户按一下 `Ctrl+Z` 只撤销了一小段 —— 完全没法用。

**对策**：以「按下 → 抬起」为界合并。
`PreviewStylusDown` 开事务（仅当输入不被抑制），`PreviewStylusUp` 提交事务：

- 事务内的所有变更**累积成一个撤销单元**，末尾统一入栈；
- **空事务直接丢弃**（点一下没画不占步数）；
- 抬笔时**无条件提交**：Down 被抑制时提交是空操作，但若漏掉这一步，
  事务会一直悬着把**下一次**操作并进同一单元 —— 表现为"按一下撤销掉两笔"，极难定位；
- `BeginTransaction` 时若发现上一次事务没收尾（例如笔在屏幕外抬起、配对不上 Up），
  **先把它提交掉**，避免两步并成一步且无从察觉。

### 2.3 应用历史期间必须屏蔽记录

**这是全 M5 最隐蔽的坑。** `Undo()` / `Redo()` 自己也是通过 `Add` / `Remove` 改集合，
于是同样会触发 `StrokesChanged`。若不屏蔽，撤销动作会被**当成新操作压栈**：

- 撤销栈越撤越长，`Ctrl+Z` 后栈里还留着东西；
- 重做栈被"新操作"清空 ⇒ **撤销一次之后就再也重做不回来**。

对策：`_applying` 标志位，`Apply()` 期间事件处理器直接返回。
harness 第 5 条专测这条：**反复撤销/重做 10 轮，栈深必须始终回到原值**。

### 2.4 换文档必须清空历史（且顺序不能反）

换文档会清空笔迹。此刻若留着旧历史，一次 `Ctrl+Z` 就会把
**上一份试卷的批注"复活"到新试卷上** —— 现象像"撤销出了鬼影"，很难联想到根因。

顺序要求：**先清笔迹，再 `Reset()`**。
因为清空本身也会入栈一条记录；若先 `Reset` 再 `Clear`，那条记录会留下来，问题照旧。

### 2.5 撤销栈必须设上限

擦除会把一条笔画拆成若干碎笔画，这些对象被撤销栈引用着**无法回收**，
反复擦改时内存会持续增长。定 **100 步**：远超一节讲评课的批改量，同时给出回收点
（超限时丢弃最早的记录，那一刻它引用的笔画才可能被 GC）。

### 2.6 「清除笔迹」去掉确认对话框

有了撤销，一个能一键还原的操作每次都拦一道只会拖慢讲评节奏。
「清除笔迹」本身就是**一个可撤销单元**（事务外发生的变更自成一步 ——
这条兜底不能省，否则这类"非输入产生"的变化会被静默丢掉，根本撤销不了）。

## 4. 验收：harness 断言与实测数据

`dotnet build` 生产工程与 harness 均 **0 warning / 0 error**；
harness **全部检查通过**（退出码 0，`===== 全部检查通过 =====`）。

| # | 断言 | 实测结果 |
|---|---|---|
| 1 | 单笔往返 + 同一对象引用 | 1 → 0 → 1，`ReferenceEquals` 成立 |
| 2 | **一次擦除合并为一步** | **4 次集合变更（移除 1 + 加入 3）→ 撤销栈只增 1 步** |
| 3 | 撤销一次完整复原原始笔画 | 3 条碎笔画 → 撤销 → 1 条且是原对象 |
| 4 | 重做一次完整回到擦除后 | 1 → 3 |
| 5 | 两次独立落笔 = 两步 | 栈深 2 |
| 6 | 空事务不留记录 | 补一个空事务后栈深仍为 2 |
| 7 | 新操作清空重做栈 | 撤销后 `CanRedo=True` → 写新笔画后 `False` |
| 8 | **反复撤销/重做 10 轮栈深不变** | 初始 3 → 10 轮后仍 3，笔画数仍 3 |
| 9 | 容量上限 | 压入 120 步 → 栈深 100（上限 100） |
| 10 | 清除笔迹可撤销 | 3 条 → 清除 0 条 → 撤销后 3 条 |
| 11 | 换文档清历史 | 前 `CanUndo=True` → 后 `False`、笔画数 0 |
| 12 | `HistoryChanged` 接线 | 新操作 + 撤销 + 重做 → 3 次通知 |
| 13 | **端到端光栅** | 蓝线像素 **4905 → 撤销后 0 → 重做后 4905** |

第 13 条是最强的证据：**"撤销后一个蓝色像素都不剩"** 证明撤销真的作用在渲染输出上，
而不只是集合里的一个计数。

证据图：`artifacts/m5-smoke/m5-undo-1-before.png`、`-2-after-undo.png`、`-3-after-redo.png`；
完整输出 `artifacts/m5-smoke/verify-m5.txt`。

### 诚实说明：擦除的端到端仍要靠一体机

本机没有笔、没有触摸屏，**真实的橡皮擦除输入造不出来**（`StylusEventArgs` 无法构造）。
harness 第 2 条断言的是**模拟的擦除变更序列**（移除 1 条 + 加入 3 段），
验证的是真正有风险的两件事：**多次变更能否合并成一步、反转后能否精确复原**。

至于"真实 `EraseByPoint` 产生的变更序列长什么样" —— 见 §2.1：
我们的机制只依赖事件契约，不依赖序列形态，所以这一点不构成风险。
但**"擦一下之后按 Ctrl+Z 能否恢复"这件事的最终确认仍在一体机上**（见 §5）。

## 5. 一体机实测补充清单（M4 清单之外的 M5 部分）

M4 的 9 条清单（`docs/05` §5）继续有效。M5 另加 4 条：

| # | 操作 | 期望结果 | 失败时的说明 |
|---|---|---|---|
| 10 | 写三笔，按 `Ctrl+Z` 三次 | 一笔一笔依次消失；按钮置灰 | 若一次消失三笔 → 事务没开合，检查 `PreviewStylusDown/Up` |
| 11 | 擦掉一段字迹，按一次 `Ctrl+Z` | **被擦的整段一次性回来** | 若只回来一小截 → 事务合并失效（本机已断言，出现即说明一体机有额外输入路径） |
| 12 | 撤销后按 `Ctrl+Y` | 重做回来；若中间又写了新笔画，则重做按钮变灰 | — |
| 13 | 写几笔 → 换一份 PDF（`Ctrl+O`）→ 按 `Ctrl+Z` | **没有任何反应**（按钮应为置灰） | 若复活出上一份试卷的批注 → 换文档清历史的顺序错了 |

第 11 条是 M5 在一体机上最值得看的一条。
