# 21. M16 —— 浮动工具栏：方形重排 + 渲染变换拖动

日期：2026-09-24（M15 交付当天真机反馈驱动）

## 1. 缘起与需求

真机反馈两条：**① 浮动工具栏拖动很卡；② 长方形外观遮挡明显，整理成正方形。**

M13 把工具栏浮动化时（TopChrome 迁入 CanvasOverlayGrid + FloatingDrag 把手拖动），
拖动机制是"每次 TouchMove 改 `TopChrome.Margin`"——真机 213Hz 触摸率下，
每帧都触发 CanvasOverlayGrid 全量 Measure/Arrange（工具栏里 40 来个按钮全部重测），
这就是卡的根因。

## 2. 拖动改渲染变换（S1）

`FloatingDrag` 重写为：

- **拖动中只改 `TranslateTransform`**（RenderTransform，纯渲染队列，零布局）：
  `_translate.X = current.X - startMargin.X`；
- **松手才落 Margin**（位置的唯一事实：持久化、窗口缩放重摆都读 Margin），
  变换清零 —— 两者在松手那一刻对齐，画面不跳；
- 捕获被打断（LostMouseCapture / LostTouchCapture）→ `Abort()`：变换清零、不提交，
  视觉退回 Margin 位置。注意 OnRelease 里**先提交再 ReleaseCapture**，
  随后的 Lost* 事件走 Abort 是无害 no-op（变换已零、_dragging 已假）；
- 签名收敛：去掉 `onMoved`（拖动中不再需要外部回调），只留 `onCommitted`。
  两处调用点（MainWindow 工具栏、CanvasViewportHost 计算器）同步更新，
  计算器面板顺带受益（共享同一助手）。

Margin 仍是唯一事实、变换只是临时视觉偏移 —— 这个分工让
M13 的全部下游（toolbar_x/y 持久化、SizeChanged 重摆、显隐护栏）**一行不用改**。

## 3. 方形重排（S2~S4）

原结构：竖排 StackPanel 内两条超长 WrapPanel（1280 宽下几乎横贯全屏）。

新结构（`MainWindow.xaml` TopChrome 重写）：

- `MaxWidth="500"` 限宽，单个 `WrapPanel` 承载全部按钮自然换行 → 约 370×480 方阵；
- 新样式 `Style.ToolbarTileButton`（76 宽 × MinHeight 44 —— **触控下限 40 不许破**，
  docs/15 §8.2）+ `Style.TileText`（13 号居中省略文字行）：
  图标上、文字下的小方格；
- 新间距 `Gap.Tile = 0,0,6,6`（换行流需要右+下边距，行距才均匀）；
- `ToolButtons`（注册表生成的 14 个工具按钮）内部面板
  StackPanel → **WrapPanel**：否则 14 个按钮永远一行，撑破方阵；
- 原"第一行 / 第二行"的工程标识、文档信息、ZoomText、QuestionIndexText
  都是"看的信息"不是按钮 → 抽出来放方阵上方的**状态行**；
- 竖直分隔线全部去掉：换行流里分隔线落点不可控，分组靠间距与排列顺序；
- **所有按钮的 x:Name / Click / 命令 / ToolTip 原样保留**（42 个命名元素
  拼接后逐一核对）—— 纯排版层改动，code-behind 零改动。

备选方案（UniformGrid 六列九宫格启动器）被否：色块 / 笔宽 / 缩放文本等
异类控件要逐个特殊处理，改动大风险高。

## 4. 踩坑

### 4.1 源级断言的块尾锚点不能是注释（M13/M14 教训的变体）

RunM16Checks 用 `"M12 S2：悬浮球"` 作 TopChrome 块尾锚点，
但先 `StripComments(xaml)` 再找 —— **锚点本身在注释里，被剥掉了**，
`IndexOf` 返回 -1，切片越界崩。修法：这一条读原文（不去注释）。
教训升级：**锚点要么在代码/属性里，要么干脆不去注释**。

### 4.2 注入测试的 DPI 坐标错位（测试假象，不是应用 bug）

pywinauto/UIA 拿到的坐标与 `SetCursorPos` 的物理像素坐标系不一致
（高 DPI 缩放屏），工具栏在**默认左上角**时误差小、注入测试全绿；
一旦按 toolbar_x/y 比例摆到屏幕中部，注入点击**全部落偏**——
连普通按钮（计算器）都"点不到"，一度误判为拖动回归。
判别方法：拿一个**位置无关的普通按钮**做对照，它也到不了 ⇒ 注入链路问题。
修法是给注入进程 `SetProcessDpiAwareness(2)`；
后续又因桌面转非交互（锁屏）中断 —— 真机拖动手感留给用户上机验证，
机制面由 harness 源级护栏 + 松手提交链路与 M13 同源兜底。

### 4.3 换行流里别用竖直分隔线

原设计靠 Divider 分组；限宽换行后分隔线落在行中还是行首不可控，
视觉上"断行断得莫名其妙"。分组改靠间距（Gap.Tile）与排列顺序，
可预期性反而更好。

## 5. 断言（RunM16Checks，5 条源级）

1. FloatingDrag：TranslateTransform 驱动、松手落 Margin、无 onMoved；
2. 两处 Attach 调用点切新签名；
3. TopChrome 限宽 500 + 瓦片按钮 ≥10 + TileText；
4. ToolButtons 内部面板为 WrapPanel；
5. 设计令牌（ToolbarTileButton / TileText / Gap.Tile）齐备。

M13 的护栏（显隐方法体零缩放调用 / 浮动化结构）继续有效、复跑通过。
