## 3. ★ 优先级列表的工程校正（请重点看这一节）

你的 6 项按直觉排序非常合理，但**基于上面的代码事实和微软官方文档，有 3 项需要改写、1 项建议否决**。这不是挑刺 —— 其中一项如果不改，做完第 1 项再做第 2 项会**把第 1 项的收益原样抹掉**。

### 3.1 第 2 项（Pointer 消息）建议**否决**

微软官方文档 *Mitigation: Pointer-based Touch and Stylus Support* 原文：

> **No support for real-time inking.** While inking and stylus plugins still work, **they are processed on the UI thread**, which can lead to poor performance.

翻译过来就是：

- 开启 `Switch.System.Windows.Input.Stylus.EnablePointerSupport` 后，**WPF 取消实时墨迹支持**；
- `StylusPlugIn` **还是能用**，但**从笔线程退回 UI 线程处理** —— 恰好把第 1 项的收益整个抵消。

（该开关在 .NET Core / .NET 5+ 上**存在且可用**，但必须用 `AppContext.SetSwitch(...)` 在第一个窗口显示前调用，因为 .NET Core 不读 App.config。所以"开不了"不是理由，**"开了有害"才是**。）

另外三条一体机专属风险，都指向同一个结论：

| 风险 | 后果 |
|---|---|
| 「希沃笔尾橡皮」靠 WISP 的 `EditingModeInverted` + 反转标志 | 换到 Pointer 栈后反转识别可能失效 —— 一行代码都不用写就白拿的橡皮没了 |
| Pointer 栈用**屏幕绝对坐标**而非窗口坐标（[dotnet/wpf#3360](https://github.com/dotnet/wpf/issues/3360)），per-monitor DPI 下曾有点位偏移 bug | 我们的画布本来就靠 `MatrixTransform` 做缩放，再叠一层坐标口径差异 = 缩放后落墨偏移，且**只在特定 DPI 下出现** |
| 开启后 `Stylus.IsPressAndHoldEnabled="False"` 失效（无法通过该属性隐藏触摸反馈圈） | 一体机上会长按出圈 |
| 拖放（Drag/Drop）不能再由触摸/笔发起 | 我们暂时没有，但 M12+ 若做"拖 `.twb` 进窗口"会撞上 |

**⇒ 建议走 WISP + StylusPlugIn 路线，Pointer 开关保持关闭。** 收益（触摸 60fps）只对手指有效；而本项目的核心场景是**笔**，笔在 WISP 下本来就是高频上行的（30fps 那个数字说的是**触摸**的 promotion 频率）。

> 诚实补充：这条结论**需要一台真机数据来盖章**。§5.6 的测量会同时给出「笔的实际上行采样率」——如果测出来真的是 30Hz 上限，我会回来重新评估。

### 3.2 第 3 项（笔迹渲染放到独立 UI 线程）**WPF 已经做了**

`InkCanvas` 内部的 `DynamicRenderer` 就是**在笔线程上渲染实时墨**的（见 §2.1 链路图）。这正是一体机上"墨跟着笔尖流动"的实现。

所以第 3 项真正该做的是**反过来的那件事**：**别让 UI 线程卡住**。因为即使墨在笔线程上流得很顺，UI 线程一卡，抬笔后的静态渲染、状态栏刷新、工具切换就会顿。

UI 线程的嫌疑排队（S3 逐条验）：

| 序 | 嫌疑 | 依据 | 初判代价 |
|---|---|---|---|
| 1 | `InkLayer` 尺寸 = 整个排版范围，而 `Scale` 最大 16 ⇒ 视觉尺寸可达数万 DIP；`IsHitTestVisible=true` 时每次笔输入都要在这一层做精确命中测试 | `CanvasViewportHost.xaml.cs:1343-1366/842` | 待测 |
| 2 | `FitToCurve=true`：抬笔时折线 → 贝塞尔的拟合是 UI 线程 CPU 活，点数越多越贵 | `PenProfile.cs:36` | 待测 |
| 3 | `StrokesChanged` 的三个同步订阅者（`InkHistory`/`BoardQuery`/`AutoSaveScheduler`） | 见 §2.1 | 小 |
| 4 | PDF 页渲染回推（`Dispatcher.BeginInvoke`）与笔输入抢 UI 线程 | `PageRenderScheduler.cs:218` | 待测 |
| 5 | 每笔 `OnStrokeCollected` 里的 `Clone()` | `CanvasViewportHost.xaml.cs:1477` | 极小 |

### 3.3 第 6 项（降采样 / 简化笔刷）**与第 2 部分（笔锋）直接冲突，排到最后**

笔锋的本质是**逐点变宽度**，需要**更密的点**才能算出平滑的宽度渐变；降采样会把笔锋磨成台阶。

**⇒ 只在「测量证明点数确实过多且是卡顿主因」时才做**，否则不动。放在 S5，且默认结论是"不做"。

### 3.4 第 1 项（StylusPlugIn）**做，但收益要重新定义**

这是本轮的重点，必须把话说清楚，免得做完你觉得"怎么没变快"：

**`InkCanvas` 自带的 `DynamicRenderer` 已经在笔线程上渲染实时墨了。** 所以再挂一个自定义 `StylusPlugIn`，**不会让墨流得更快** —— 它和 `DynamicRenderer` 是并列关系，不是替代关系。

它的真实价值是这三条：

1. ★ **只有它能在笔线程上拿到每一点的原始数据 + 时间戳**（`RawStylusInput.Timestamp`）。而 `StylusPoint` **不含时间戳** —— 也就是说「速度」这个量**在抬笔后无法从点集反推**，只能在采集时算。这是笔锋的地基，没有替代方案。
2. **只有它能在 `DynamicRenderer` 之前改写点**（`RawStylusInput.SetStylusPoints`）—— 包括改写 `PressureFactor`。这是 §6.2 笔锋正解的关键。
3. 能在笔线程上做坐标换算、去抖、重采样，不占 UI 线程。

**⇒ S1 的定位：地基 + 第一次真机测量。它本身的性能收益接近 0，但 S2（笔锋）离开它就做不成。**

## 5. S1 详细设计 —— StylusPlugIn 地基

### 5.1 三个必须绕开的硬约束（先看这个，否则实现方式会选错）

**约束 A — `UIElement.StylusPlugIns` 是 `protected`，从外部加不进去。**

```csharp
protected StylusPlugInCollection StylusPlugIns { get; }   // UIElement
```

⇒ **必须派生 `InkCanvas` 子类**，在子类构造函数里挂插件。反射拿这个属性太脆，不做。

> 已核实：harness **没有任何** `typeof(InkCanvas)` / 类型相等的断言，全部经 `host.InkSurface` 属性访问（`tools/PdfSmokeTest/Program.cs` 20 余处）。所以把 XAML 里的 `<InkCanvas>` 换成派生类是**安全的**。

**约束 B — 想做"实时笔锋"，插件必须排在 `DynamicRenderer` 之前。**

`StylusPlugIns` 是按顺序执行的（官方《墨水线程模型》）：排在 `DynamicRenderer` 前面的插件改过的点，**会实时显示**；排在后面的，改的点要等抬笔才生效（表现为"墨迹跳动"）。

⇒ 子类构造函数里用 **`StylusPlugIns.Insert(0, plugin)`** 抢占队首。

> ⚠️ **待验证点 #1**：`InkCanvas` 内部的 `DynamicRenderer` 是在**构造函数**里加的还是 `OnApplyTemplate` 里加的？
> 若是构造函数 ⇒ 我们 `Insert(0, …)` 稳稳排在它前面。
> 若是 `OnApplyTemplate` ⇒ 它在 `InitializeComponent` 之后才加进来（会排在我们后面），需要在 `Loaded` 里再 `Insert(0, …)` 一次。
> **S1 第一件事就是把这个用日志打出来验证**（`StylusPlugIns.Count` + 每项类型 + 顺序）。

**约束 C — RTI 回调跑在笔线程上，项目里那些状态全部无锁、线程不安全。**

`OnStylusDown/Move/Up` 的执行线程是 `PenThreadWorker`，**不是 UI 线程**。而项目里：

- `_pen` / `_tools` / `_viewport` / `_diag` 都是 UI 线程对象；
- `InkHistory`、`BoardQuery`、`AutoSaveScheduler` 订阅 `StrokesChanged` 且**无任何锁**（`AutoSaveScheduler.cs:16` 自己都写明了"读 `StrokeCollection` 不是线程安全的"）。

⇒ **插件内绝对禁止**：读 `_pen`、读 `_tools`、改 `DefaultDrawingAttributes`、碰 `Strokes`、动撤销栈。

⇒ **并且禁止 `Dispatcher.Invoke`（同步）** —— 笔线程等 UI 线程、UI 线程正在等笔线程的事务 ⇒ **RTI 经典死锁**。要回 UI 线程只能用 `BeginInvoke`（异步）。

⇒ 允许：往**插件私有缓冲**写点、算数、置 `volatile` 标志。落墨/改属性一律回 UI 线程。

> 参考模板：项目里唯一那条后台线程就是这么写的 —— 独立线程采集 + `Dispatcher.BeginInvoke` 回推（`Pdf/PageRenderScheduler.cs:70/218`）。

### 5.2 设计

三个类，职责单一：

```
InkSurfaceCanvas : InkCanvas          （Views/Controls/）
    └─ 唯一职责：构造时把 InkSamplerPlugIn 插到队首；暴露 Enabled 开关
         ↑ XAML 里 <InkCanvas x:Name="InkLayer"> 换成本类型，其余不变

InkSamplerPlugIn : StylusPlugIn       （Input/）
    ├─ OnStylusDown/Move/Up：笔线程
    │     ① rawStylusInput.GetStylusPoints(Element) → 世界坐标点集
    │     ② 记 Timestamp → 算相邻点间隔
    │     ③ 写入私有 InkSampleBuffer（无锁环形缓冲 / 单次笔画缓冲）
    │     ④ S1 阶段：**不改点**（只采集）。S2 才在这里 SetStylusPoints 伪造压力
    └─ OnStylusUpProcessed：回 UI 线程，把这一笔的统计交给 InputDiagnostics

InkSampleBuffer                        （Input/）
    └─ 纯数据结构 + 纯函数：装点、算时长/间隔/点数
       ★ 刻意不依赖 RTI —— 好让 harness 直接喂合成点做断言
```

**关键可测性设计**：`InkSamplerPlugIn` 把逻辑收敛到一个不碰 RTI 的入口，例如

```csharp
// harness 可直接调用：绕过 RTI，喂合成点
internal void AcceptRawSample(in RawSample sample)
```

因为本机**没有笔、没有触摸屏**，`RawStylusInput` 在 harness 里**不可能被伪造**。所以凡是能被断言的逻辑（坐标口径、时间间隔、统计口径）都必须落在 `InkSampleBuffer` / `AcceptRawSample` 这一层，RTI 回调只留"取点 + 转交"两行。

### 5.3 复用现有测量设施，不另造一套

`Infrastructure/InputDiagnostics.cs` 已经是"笔/触摸现场记录仪"（计数 + 汇总 + down/up 配对校验），设计意图完全对口。**扩展它，不新建并行系统**：

新增

```csharp
/// <summary>记录一笔采样：点数 + 时长（毫秒）。用于算真机采样率。</summary>
public void NoteSampledStroke(int pointCount, int durationMs)
```

`FlushSummary()` 里追加一段：

```
===== M11 笔采样 =====
  笔画数 = 12
  平均点数 = 47.3   平均时长 = 312 ms   推算采样率 ≈ 152 Hz
  最快一笔 = 96 点 / 405 ms（237 Hz）   最慢一笔 = 8 点 / 210 ms（38 Hz）
```

★ **这一行 `推算采样率 ≈ XXX Hz` 就是 S1 最值钱的产出** —— 它回答了一个我们现在只能猜的问题：**这台一体机把笔报成了什么、多快**。有了它，§3.1 的"否决 Pointer"结论才能盖章，§3.3 的"要不要降采样"也才有依据。

### 5.4 坐标换算：直接吃 §2.1 那个红利

因为 `InkLayer.Left/Top = 0` 且祖先只有 `WorldHost` 一个矩阵，**`InkLayer` 的本地坐标 ≡ 世界坐标**。

而 `RawStylusInput.GetStylusPoints(IInputElement relativeTo)` 会**替我们应用 `relativeTo` 的变换**。所以：

```csharp
// 插件关联到 InkLayer（Add 时 WPF 自动设 Element）
rawStylusInput.GetStylusPoints(Element)   // ⇒ 已经是世界坐标
```

**不需要手写矩阵换算**，也就不会出现"缩放后笔迹漂移、100% 时看不出来"这种最难查的 bug。

**双保险（必做）**：同时用 `Element.TransformToAncestor(root)` 独立算一遍，两条路的结果**对账**，差值 > 0.5 world 单位就写 WARN 日志并带上当时的 `Scale` / `Offset`。

> ⚠️ **待验证点 #2**：RTI 的变换表在 `Scale` 变化后是否实时更新。若滞后一帧，表现为"刚缩放完落的第一笔偏一点"。上述对账就是为了抓它 —— 在 harness 里用 `Scale=4` + 平移后喂合成点，能直接验出来。

## 6. S2~S5 概要（本轮不实现，先给方向，等 S1 验收后再展开）

### 6.1 你要的"进阶：骨架点 → 不对称椭圆 → 轮廓填充"，我建议**先不做**

理由（这是本项目最硬的一条铁律）：

- 轮廓填充的结果**不是 `System.Windows.Ink.Stroke`** ⇒ 就不能用 `StrokeCollection.Save`（ISF）序列化 ⇒ 直接撞碎 `.tbink` / `annotation.tbink` 的整条持久化链；
- `EraseByPoint`（点擦）的命中测试依赖 `Stroke` 几何 ⇒ 擦除要重写；
- 导出走 `PageRasterizer` 光栅化 `WorldHost`，自定义 `DrawingVisual` 能出图，但"按产物规范回读"那套验收要重做；
- 一句话：**它会把 M1~M10 至少 4 个不变量连根拔起。**

### 6.2 ★ 笔锋正解：速度 → 伪造 `PressureFactor` → 白嫖 WPF 原生压感管线

`Ink/PressurePolicy.cs` 里 M3 时就写下过一条限制：

> WPF 在 `IgnorePressure = false` 时按压力因子线性缩放笔宽，这套映射是**内建的、不可自定义曲线**（要自定义就得在笔画落下后重建几何，那正是"墨迹几何永不重算"要避免的事）。

**破解它的钥匙：不要在"曲线"那一端想办法，在"数据源"那一端想办法。**

既然 `PressureFactor` 是我们能改的输入，那就**在插件里把「速度」映射成 `PressureFactor` 写回去**：

```csharp
// 笔线程，StylusPlugIn.OnStylusMove
var points = rawStylusInput.GetStylusPoints(Element);
foreach (var p in points)
{
    float w = SpeedPressureMap.Width01(dtMs, distance);   // 越快越细 → 0..1
    p.PressureFactor = 0.35f + 0.65f * w;                  // 映射到可用区间
}
rawStylusInput.SetStylusPoints(points);                    // ★ 写回
```

于是白得三件事：

| 得到 | 为什么 |
|---|---|
| **实时可见的笔锋** | `DynamicRenderer` 按 `PressureFactor` 渲染（前提：插件要排在它前面，见约束 B） |
| **抬笔后与实时一致** | `IgnorePressure=false` 时 WPF 用同一套压力因子生成最终 `Stroke` |
| **零改动持久化** | `PressureFactor` 是 `StylusPoint` 的**标准属性**，ISF 原生保存 ⇒ `.tbink`/`.tbw` 一行不用改 |

**它满足全部不变量**：点仍是世界坐标、几何仍不重算、擦除不用改、导出不用改。

**已知代价与对策**

| 代价 | 对策 |
|---|---|
| 无压感设备（红外框 + 被动笔，压力恒 0.5） | 我们伪造的值**覆盖**掉原始值 ⇒ 反而变成优势：这类设备也照样有笔锋。`PressurePolicy.IsPressureConstant` 的兜底逻辑要相应调整为"看我们伪造的这一笔" |
| WPF 压感映射下限是 `Width * 0.5` 左右（不是 0） | 起笔/收笔的"尖"做不到 0 宽。想要更尖只能上轮廓填充（§6.1，暂不做） |
| 速度抖动 ⇒ 宽度抖动 | `SpeedPressureMap` 里做低通（相邻点加权）；纯函数，harness 可直接喂序列断言单调性与值域 |
| 触摸面积的取用 | `TouchDevice` 才报 `Size`（`InputDiagnostics.NoteTouch` 已记录"驱动不报尺寸"的情形）⇒ 面积只作为**可选增益项**，拿不到就纯速度 |

**速度笔锋 vs 压感笔锋的取舍**：一体机上压感未必存在（见 §6.2 表格第二行），而速度**永远算得出来**。所以主算法用速度，压感若可用则按 `max(速度, 压感)` 之类合成 —— 具体合成律在 S2 展开时给。

→ **S2 = `Input/SpeedPressureMap.cs`（纯函数）+ 插件里那 6 行写回 + 压感复选框旁加「笔锋」开关。**
