# M7 设计方案 —— 工具系统与插件宿主

> 状态：**M7.1 已实施并验证通过**（2026-09-21）→ 实施记录见 §9；M7.2 / M7.3 待做。
> 用户已拍板：①按 M7.1 → M7.2 → M7.3 三步走；②插件走「外部 DLL + 程序目录下 `plugins\`」；
> ③第一个示范学科工具 = **直尺**。
> 前置：M0~M6 全部完成；M4.2 的一体机输入修复已生效。

---

## 1. 目标

M4 的 `BoardTool` 三态是**临时占位**（枚举 + 宿主里一串 `switch`）。
它的根本限制不是"少几个工具"，而是：**每加一个工具都要改宿主**。
到了学科工具阶段（直尺、量角器、坐标系、电路符号…），这个代价不可接受。

M7 要达到的效果：

1. **加工具不改宿主** —— 工具从"枚举分支"变成"实现接口的对象"，宿主只认接口。
2. **工具可以独立成 DLL** —— 放进程序目录下的 `plugins\` 即被识别，主程序编译期不认识它。
3. **迁移零行为变更** —— 笔 / 橡皮 / 手迁移到新系统后，行为与 M6 逐条一致（harness 断言）。
4. **工具能画东西，且免费继承已有能力** —— 产物落进墨迹层，于是自动获得
   随缩放平移、撤销/重做、橡皮擦除、`.tbink` 持久化。

## 3. 核心设计决策

### D-M7-1：三层分离（契约 / 宿主 / 插件）

```
MathPhys.Ink.Plugin.Abstractions   ← 独立类库，只有接口与值类型
        ↑                    ↑
   MathPhys.Ink      MathPhys.Ink.Plugin.Ruler（示例插件）
   （宿主 + 内置工具）        （只引用 Abstractions）
```

**主程序与所有插件都必须引用同一份 Abstractions**。这不是风格问题：
插件用 `AssemblyLoadContext` 单独加载，若它自带一份 Abstractions 副本，运行时就会出现
两个同名不同身份的类型 —— `as IWhiteBoardPlugin` 会静默返回 `null`，
表现为"插件目录里明明有 dll，却一个工具都没注册"，且不报任何错。
所以加载器里**Abstractions 强制走默认上下文共享**（见 D-M7-4）。

### D-M7-2：工具的输出契约 —— **落墨型优先**

工具画出来的东西，首选表达成 `Stroke` 交给宿主：

- 一笔直尺线 = 一条两点 `Stroke`；
- 曲线 = 采样若干点的 `Stroke`。

这么做**一行持久化代码都不用写**，却立刻拥有：
世界坐标（随缩放平移不漂移）、撤销/重做（`InkHistory`）、橡皮可擦、`.tbink` 可存可读。

拖动过程中的"橡皮筋"预览走宿主的 **`AddPreview`**：临时图元、抬笔即清、
**不进墨迹层、不进撤销栈**。

> **显式取舍**：M7 **不做**「图元型」工具（可选中、可拖动、可改参数的可编辑图形，如
> 带刻度的量角器实体）。那需要一套自己的选择/移动/删除/持久化机制，是独立里程碑。
> 一期只做"落墨型"，把契约先定死，后续要加图元型时是在同一套接口上扩展，不推翻。

### D-M7-3：输入分发 —— 工具占"书写赛道"，宿主独占"视口赛道"

选中工具后，宿主按工具声明调整墨迹层：

```
CapturesCanvasInput == true  →  InkLayer.IsHitTestVisible = false   // 输入交给工具
IsManipulationEnabled        = !CapturesCanvasInput                 // 手=开
```

要点（全是 M4.2 换来的教训）：

- **"不落墨"一律用 `IsHitTestVisible=false`，绝不用 `e.Handled`**。后者挡不住笔输入线程上的
  `DynamicRenderer`（⇒ 抬笔字消失），还会泄漏输入捕获（⇒ 一切触摸失灵）。
- 指针转发是**观察 + 转发**，不设 `Handled`。
- **视口操作（中键平移、滚轮缩放、Manipulation、Ctrl+组合键）永远归宿主**，`IToolContext`
  根本不暴露改视口的 API ⇒ 插件再怎么写也弄不坏平移缩放。
- 一期只转发**隧道 Stylus 链**（`OnPreviewStylus*`）。这一条链在 M4.2 的实测里
  鼠标 / 笔 / 被提升的触摸都会经过。若某台机器只产生 Touch 事件，再补 `OnPreviewTouch*`
  喂同一份 `ToolPointer`，工具侧无感（**待一体机实测**）。

### D-M7-4：插件加载 —— 目录约定 + 可卸载上下文 + 失败隔离

- 目录：**程序目录下的 `plugins\`**（不是 `%LOCALAPPDATA%`）。
  理由与侧车文件一致：老师拷 U 盘把整个文件夹拷走，插件跟着走。
  布局：`plugins\<插件名>\<插件名>.dll`（每个插件一个子目录，各自带依赖，互不干扰）。
- 每个插件一个 `AssemblyLoadContext`（`isCollectible: true`），
  依赖从**自己所在的子目录**解析；**Abstractions 强制共享**（D-M7-1）。
- **失败隔离**：某个插件加载/注册时抛异常 ⇒ 只记日志 + 状态栏一行提示 + 跳过它。
  绝不影响启动，也不影响其他插件。
- 契约版本：`PluginApi.Version`（int）。不匹配 ⇒ 拒绝加载并给出可读原因（"插件太新/太旧"）。
- **诚实说明（不吹）**：.NET 里没有可靠的进程内插件沙箱，
  插件就是本进程里的普通代码，**只装自己信任的**。这句话会写进 `plugins\说明.txt`。

### D-M7-5：内置工具与外部插件走同一套接口

笔 / 橡皮 / 手改写成 `PenTool` / `EraserTool` / `HandTool`，**通过同一套 `IWhiteBoardPlugin`
注册**。好处是把迁移风险一次性暴露在 M7.1（可断言"零行为变更"），
而不是留到 M7.3 才第一次发现接口设计错了。

## 4. 接口草图

```csharp
// ---- Abstractions ----
public enum ToolInputKind { None, Ink, Erase }        // 替代 BoardTool（策略输入）
public enum ToolPointerPhase { Down, Move, Up }

/// 一次指针事件。世界坐标由宿主换算好，工具不做任何坐标运算。
public sealed record ToolPointer(
    ToolPointerPhase Phase, Point World, Point Viewport,
    int DeviceId, bool Inverted, int ClickCount);

public interface ITool
{
    string Id { get; }                    // 稳定标识：pen / eraser / hand / ruler
    string DisplayName { get; }           // 按钮文字
    string ToolTip { get; }
    Key? Shortcut { get; }                // 单键快捷键（1/2/3…），null = 无
    bool CapturesCanvasInput { get; }     // 是否需要指针输入
    ToolInputKind InputKind { get; }      // 笔输入分类的真相源
    Cursor Cursor { get; }
    InkCanvasEditingMode EditingMode { get; }

    void Activate(IToolContext context);
    void Deactivate();                    // 拖动中被切走也要被调用（否则预览残留）
    void OnPointer(ToolPointer pointer);  // 仅在 CapturesCanvasInput 时收到
}

/// 插件能用的宿主能力 —— 是<b>受控子集</b>，刻意没有"改视口/开关文档/清空历史"。
public interface IToolContext
{
    Size ViewportSize { get; }
    double Scale { get; }
    IReadOnlyList<Rect> PageRects { get; }
    Point ToWorld(Point viewportPoint);
    Point ToViewport(Point worldPoint);
    Color PenColor { get; }
    double PenWorldWidth { get; }
    void CommitStrokes(StrokeCollection strokes);  // 事务包裹：一次提交 = 一个撤销单元
    void AddPreview(UIElement visual);             // 世界坐标层的临时视觉
    void ClearPreview();
    void SetStatus(string text);
}

public interface IToolRegistry { void Add(ITool tool); IReadOnlyList<ITool> Tools { get; } }

public interface IWhiteBoardPlugin { string Name { get; } void Register(IToolRegistry registry); }

public static class PluginApi { public const int Version = 1; }
```

内置工具的形状（迁移后宿主里的 `switch` 全部消失）：

| 工具 | CapturesCanvasInput | InputKind | EditingMode | Cursor | 快捷键 |
| --- | --- | --- | --- | --- | --- |
| 笔 Pen | false | `Ink`（反转时 `Erase`） | `Ink` | `Pen` | 1 |
| 橡皮 Eraser | false | `Erase` | `EraseByPoint` | `Cross` | 2 |
| 手 Hand | true | `None` | `None` | `Hand` | 3 |
| 直尺 Ruler（示例插件） | true | `None` | `None` | `Cross` | 4 |

## 6. 风险与预判的坑

1. **ALC 类型身份分裂**（最经典）⇒ Abstractions 强制共享，加载器里显式判断
   "程序集名 == Abstractions" 时走默认上下文。
2. **插件里的 XAML/BAML**：pack URI 必须写全名（`pack://application:,,,/插件名;component/...`），
   否则资源加载不到。示例插件一期**用纯代码画预览**，不引 XAML，绕开这条。
3. **插件往 `Application.Current.Resources` 塞词典是全局副作用** ⇒ 一期不支持主题/皮肤扩展点。
4. **拖动中切工具**：必须先 `Deactivate` 清预览、复位指针状态；否则预览图元残留、
   下一次拖动起点是上一次的（与 M4.2"捕获悬空"同类问题）。
5. **提交要合并成一个撤销单元**：一次直尺操作必须按一次 Ctrl+Z 整体消失
   （正是 M5 擦除事务的同款需求）。
6. **本机无触摸屏** ⇒ 指针转发只能断言"喂进去的 `ToolPointer` 世界坐标正确"，
   真实触摸链路仍靠一体机清单。
7. **热插拔不做**：一期只在启动时扫一次目录（运行时卸载再加载涉及 UI 重建，收益低、坑多）。

- harness（`tools/PdfSmokeTest`）新增：

### 9.2 与方案的三处偏差（都是实现时发现契约可以更清楚）

1. **`CapturesCanvasInput` 拆成两个布尔**：`UsesInkLayer`（墨迹层是否接输入）+ `NeedsPointer`（是否需要指针转发）。
   一个布尔表达不了"手"与"直尺"的区别 —— 两者都不落墨，但手要 Manipulation、直尺要指针。
   现在的规则是两行，四个组合正好覆盖笔 / 橡皮 / 手 / 插件工具。
2. **契约里不放 `InkCanvasEditingMode`**，改自定义 `ToolInkMode { None, Ink, EraseByPoint }`：
   一旦契约绑死 WPF 的采集模式，M4.1 预留的 `WM_POINTER` 路线（`docs/05` §2.6）就得改所有插件。
   翻译责任留在宿主（`MapInkMode`），且擦除分支取 `EraserProfile.Mode`，保持"擦除方式"真相源唯一。
3. **指针转发补了鼠标链路**：方案只写"一期只转发隧道 Stylus 链"。
   实现时两条都接了（Stylus + Mouse），用 `_toolPointerActive` 闸门去重 ——
   因为鼠标会被 WPF 提升成 Stylus，而这条提升链在不同驱动/系统版本上未必一致；
   多接一条的成本是一段代码，收益是本机（无触摸屏）现在就能用鼠标验证直尺。

### 9.4 验证结果

- 生产工程与 harness：**0 warning / 0 error**。

  注册表（3 工具 + 默认激活笔）、快捷键（含小键盘、未声明键返回 null）、Id 去重、
  工具声明 → 墨迹层四属性映射（含 `NeedsPointer` 的假工具）、激活/停用计数、

### 10.2 实现时定下的三件事（方案里没写死）

1. **版本判定不看 `PluginApi.Version`，看"插件对契约 dll 的引用版本"。**
   `PluginApi.Version` 是 `const`，编译时被**内联**进插件自己的 IL 里，运行时反射读不到
   "这个插件编译时用的是哪一版契约"。引用版本写在元数据里，可靠。
   而且契约 dll **没有强名称**，.NET 按**简单名**绑定 ⇒ "插件引用 v2、宿主只有 v1"这件事
   **不会**导致加载失败，而是静默把 v1 交给插件。所以必须由我们自己拒绝，并把原因说成人话
   （实测输出：`插件针对契约 v2，本程序是 v1`）。
2. **依赖解析 = resolver + "插件目录下同名 dll" 回落，且契约与宿主在最前面被排除。**
   resolver 要读同名的 `.deps.json`，而类库项目默认不生成它 —— 所以补一条目录回落，
   让"插件把自己的依赖和 dll 放一起拷过来"这种最常见分发方式能工作。
   `PluginContract.IsSharedWithHost` 的判断放在 `Load` 的**最前面**：
   哪怕插件目录里放了一份契约副本，也不采用。resolver 构造失败不算错误，降级到目录回落即可。
3. **一个插件类注册失败不拖垮同 dll 里的另一个插件类**（按类型逐个 try/catch）。
   且"注册了 0 个工具"记 `Failed` 而不是 `Loaded` ——
   报告写着成功、用户却找不到按钮，是最招人烦的那种假成功。

## 11. M7.3 设计方案：正式直尺插件（待确认）

### 11.1 要解决的真实问题

### 11.3 三个关键设计决定

**1. 落墨仍是"一条 Stroke"，刻度与文字只活在预览里**

拖动中在预览层放三样东西（预览层在 `WorldHost` 内 ⇒ 本地坐标 ≡ 世界坐标，直接按世界坐标摆）：

```
<Line>        线段本体（颜色 = 当前墨色，粗细 = 当前笔宽）
<Line> ×2     两端短横（刻度感，长度 ≈ 8 world）
<TextBlock>   中点上方「4.2 cm　30°」
```

抬笔时**只把那条线段**交给 `CommitStrokes`（一次事务 = 一步撤销），预览随即被宿主清掉。

> **为什么刻度/文字不烙进卷面**：文字进不了 `Stroke`（`Stroke` 只能表达几何路径），
> 要让文字留在卷面上就得有"图元 / 文字批注"机制 —— 那是另一个里程碑（M8）。
> 硬凑的办法（拿线段拼数字）会让卷面变脏、缩放后糊成一团，**不做**。
> 换个角度想：老师要的是"辅助线"和"这条多长"这个信息；信息给到（拖动中 + 状态栏），
> 线留在卷面上就够用了。

**2. 文字用反向缩放保持屏幕字号恒定**

预览层是世界坐标层，直接放 `TextBlock` 会**随缩放变大变小** —— 缩小到 50% 时长度数字就看不见了。
做法：给 `TextBlock` 挂 `LayoutTransform = ScaleTransform(1/Scale)`，于是它在屏幕上永远是 14 px，
而**位置**仍然跟世界坐标走（贴着线段中点）。`Scale` 由 `IToolContext.Scale` 给出。

**3. 吸附只改终点，绝不动起点；力竭的情况一律不落墨**

- 吸附：粒度 **15°**，只有"离最近的 15° 倍数 ≤ 8°"才吸（否则任意角都被扭走）。
  跨 0° 环绕（353° → 0°）要专门处理 —— 这是这类计算最经典的错点（写成两行就是 bug）。
- **起点永不被吸附挪动**：起点是老师按下的那一点，动它会让人"笔还没抬，线已经跳了"。
- 手写笔在触摸屏上没有压力/反转信号（M4.2 结论），所以**不做"按住某键关吸附"** ——
  一体机上没键盘可按。留的后路是：真需要自由角，**同一插件再注册一个"自由角直尺"实例即可
  （同一个类 + 一个开关，成本是一行注册）** —— 先看实测需不需要，不预先加按钮。
- 误触：`Down → Up` 距离 < 2 world（≈0.07 cm）⇒ **不提交任何笔画**、清预览。
  否则老师每次想切工具时在卷面上点一下，就留下一个小点，越积越多。
- `Deactivate`：清内部拖动状态（宿主已负责清预览，但工具自己也要复位 ——
  否则下次拖动的起点还是上一次的）。

### 11.4 长度与单位

世界坐标 = PDF point = 1/72 inch ⇒ **长度(cm) = world × 2.54 / 72**。
A4 宽 595 pt = 21.0 cm，量出来正好，说明这把尺子是真的。
角度 = `atan2(dy, dx)`，显示取 `[0°, 180°)`（直线没有方向，只报倾角）。

### 12.2 与方案的四处偏差（都是动手时才暴露的）

**① 吸附容差 8° → 5°（方案里的算术笔误，必须记下来）**

半步宽只有 **7.5°**。容差一旦 ≥ 7.5°，**任意角度**都落在某个 15° 倍数的容差内 ——
那就不是"吸附"而是"强制量化到 15°"，老师连一条任意方向的辅助线都画不出来。
而且方案自己给的两条例子互相矛盾：

- `37° → 37°`（离 30° 有 7°）要求容差 **< 7°**
- `353° → 0°`（离 180° 有 7°）要求容差 **≥ 7°**

两者在同一个均匀度量下不可能同时成立。取 **5°**：满足"只管手抖、管不到'我就想画 37°'"
的原始意图，也与 `37°→37°` 这条例子一致。**跨 0° 环绕改用 `178° → 0°` 验证**
（同为环绕边界、且在 5° 容差内），断言覆盖等价，不再自相矛盾。

> harness 里专门加了一条不等式断言：`容差 × 2 < 粒度`。
> 这个设计意图从此**不是文档里的一句话，而是一条会红的回归** —— 谁把容差调大立刻被发现。

**② 预览图元 3 个 → 4 个**

方案 §11.5 的表里写 `PreviewCount == 3`，但 §11.3 列出的图元是
「尺身 + 两端短横 ×2 + 长度文字」= 4 个。以清单为准，断言取 4。

**③ 吸附必须"保留长度、只转角度"，并且要显式消掉方向歧义**

轴角是**直线**的角度，`178°` 与 `0°` 是同一条轴。若直接把 178° 按 0° 重建，
往**左**拖出来的线会翻到**右边**（终点跑到手指的另一侧）—— 肉眼一看就是"尺子疯了"。
做法：重建后用点积判号，取与原始向量同向的那个解。
harness 用 `(100,100) → (-400,100.5)` 断言"约束后终点仍在起点左侧"。

**④ 长度文字用 `LayoutTransform` 反向缩放**

预览层在 `WorldHost` 内部 ⇒ 它就是世界坐标层，直接放 `TextBlock` 会随缩放一起变小，
缩到 50% 时长度数字就糊成一团。给容器挂 `ScaleTransform(1/Scale)` 抵消：
**位置**仍贴世界坐标走（贴着线段中点），**字号**在屏幕上恒定 14 px。

### 12.3 落墨与预览的分工（与方案一致）

抬笔时**只把一条两点 `Stroke`** 交给 `CommitStrokes`（一次事务 = 一步撤销），
刻度与长度文字只活在预览层、抬笔即清。于是撤销 / 橡皮 / `.tbink` 持久化 / 随缩放平移不漂移
**一行都不用写**。

长度：世界坐标 = PDF point = 1/72 inch ⇒ **cm = world × 2.54 / 72**。
A4 宽 595 world 量出 **20.99 cm**（harness 断言），说明这把尺子是真的。
