# M10 设计系统与界面美化 —— 设计与实施方案（**S0~S6 已全部实施**，2026-09-23）

> 目标：把散落在 XAML 与 C# 里的**颜色、字号、间距**收敛成一套语义化**设计令牌**，
> 并给控件套上统一模板 —— 让界面从"能用的 Windows 默认样式"变成
> **大屏可读、低干扰、可一键换深浅**的一体机界面。
>
> ★ 本里程碑**只建系统，不做像素级美化**。像素级打磨留到功能稳定后统一进行。
> ★ 本里程碑**不改任何功能行为**：笔迹、图形、导出、工程存读全不动，7 个插件完全冻结。

## 0. 范围与边界

### 0.1 做什么

1. 建立 `Design/` 下的资源字典：**Colors**（语义化颜色，深浅两套）、**Typography**（字体与字号层级）、**Spacing**（间距与圆角）
2. 统一 **6~8 种实际用到的**控件模板（工具栏按钮、图标按钮、切换按钮、勾选框、提示气泡、面板底板、弹窗）
3. 评估 HandyControl，并给出**是否引入**的结论与判据
4. 建立一套图标规范（统一风格与光学尺寸）

### 0.2 不做什么

- **不做像素级美化**：不调"某个按钮差 2px"、不做动效、不做阴影层次
- **不动插件 UI**：`FunctionInputWindow` / `VirtualKeyboard` 属插件自有界面，M10 不接管（理由见 §9.4）
- **不改任何交互行为与快捷键**：M10 是"换表现层"，不是"改功能"
- **不做真正的主题切换 UI 入口**（放到 S6；S0 只保证"色板可换"这件事在结构上成立）
- **不做用户自定义配色**
- **不引入嵌入式字体**（字体族只指定系统已有字体，理由见 §6.2）

### 0.3 与既有里程碑的关系

M0~M9 的功能全部冻结。M10 只覆盖"表现层"，且每一步都以"**行为与像素可回归**"为验收前提。

## 1. 现状勘察（为什么值得做）

| 事实（已实测） | 影响 |
|---|---|
| `App.xaml` 的 `<Application.Resources>` **是空的** | 全工程零资源字典，没有任何设计系统 |
| 宿主界面共 **11 个去重色值**，出现在 **41 处**裸写 | 改一个颜色要在十几处找（仅 `#55554E` 一个值就出现 **15 次**） |
| `GfxParameterPanelView.cs` 用 **C# 构造**又定义了 **5 处 ARGB 半透明色**（4 个新色值） | 颜色分散在**两种定义方式**里，XAML 换肤管不到代码建的面板 |
| **0 个 `ControlTemplate` / `Style`** | 所有按钮都是 Windows 默认样式；当前"看着像白板软件"纯靠手工设 `Padding` / `Background` |
| **0 个图标**（XAML 里 `Path` / `Image` / `Geometry` 均为 0） | 全靠文字按钮，窄窗口下工具栏只能靠 `WrapPanel` 换行 |
| 尺寸**四套并存**：主工具栏 ≈30 / 停靠条 44 / 演示窗 48 / 参数面板 40 | 同一个"按钮"在同一屏上有 4 种高度 |
| 字号**八档并存**：11 / 12 / 13 / 14 / 15 / 16 / 17 / 18，且**没有任何一处指定字体族** | 层级无规范；字体靠系统默认 + 中文回退，跨机器可能不一致 |
| ★ **墨色定义在两处**：`InkPalette.cs` 定义 5 色（含中文名），`MainWindow.xaml` 把**同样 5 色 + 名字再手抄一遍** | 工具按钮 M7.1 已改成"按注册表生成"，**墨色按钮漏掉了** —— 改 `InkPalette` 后色块不会跟着变 |
| ★ **撞色**：墨橙 `#E86A0B` 同时是"未保存"状态色 | 两套语义共用一个值，改任一方都会误伤另一方 |
| ★ **半透明色只在深色下成立**：参数面板描边 `#60FFFFFF`、输入框底 `#40000000` | 换成浅色界面后 `#60FFFFFF` 会**完全看不见**（白描边画在浅底上） |

> 结论：现状不是"不好看"，而是**没有系统** —— 颜色、尺寸、字号各自为政，
> 且已存在两处**真实的重复与冲突**（墨色重复、橙色撞色）。M10 首先修的是这个。

## 2. 设计原则

| # | 原则 | 可检验的含义 |
|---|---|---|
| 1 | **大屏优先** | 可点目标最小 **40×40 DIP**；正文字号 **≥15**；比普通桌面软件大一档 |
| 2 | **低干扰** | 界面用中性色；**主色只用于"当前状态"**（选中/激活），不用来装饰 |
| 3 | **语义化，不写死** | 任何颜色/字号/间距都通过令牌引用；**全仓库零裸色值**（可断言） |
| 4 | **换色板即可换深浅** | 深浅两套只替换**值**，结构、布局、代码零改动 |
| 5 | **两套色板分开管** | 墨迹色与界面色**互不影响**：红笔永远是红笔，界面换浅色它不变 |
| 6 | **图标风格统一** | 同一套图标源、同一网格（24）、同一视觉重量；不用两个来源混搭 |

## 3. 三套色板的划分（★ 核心架构决定）

### 3.1 判据：它会不会被导出到 PNG / PDF？

M9 的导出链路只包含 **页面 + 笔迹 + 图形对象**，**不含任何界面元素**。
这条现成的事实给了一个非常干净的、**可检验的**划分判据：

> **会进导出产物的 → 墨迹板 / 画布板；不会进的 → 界面板。**

### 3.2 三套板（而不是两套）

| 板 | 前缀 | 内容 | 会进导出？ | 随界面换深浅？ |
|---|---|---|---|---|
| **界面板** | `Ui.*` | 窗口底、工具栏、状态栏、分隔线、文字、按钮、状态色、面板底板 | ❌ | ✅ **整体翻转** |
| **墨迹板** | `Ink.*` | 5 个笔色（红/黑/蓝/绿/橙）+ 默认色 | ✅ | ❌ **永不翻转** |
| **画布板** | `Canvas.*` | "纸"白底、图形默认色、选中高亮、手柄填充 | ✅ | ❌ **永不翻转** |

**为什么一定要第三套**：选中高亮与手柄是**画在纸上的**（它们会被导出，老师能在导出的图上看到自己选中的对象框）—— 它们必须与"纸"的明度关系**恒定**，而不是与界面主题同步。
如果把它们塞进界面板，换到浅色界面时，"白纸上的白色手柄"就会消失。

### 3.3 每套板唯一的数据来源（防止再出现"两处定义"）

| 板 | 唯一来源 | 备注 |
|---|---|---|
| 界面板 | `Design/Palette.Dark.xaml` / `Palette.Light.xaml` | M10 新建 |
| 墨迹板 | **`Ink/InkPalette.cs`（已存在）** | ★ 已有，且 harness 已断言"默认笔 == 标着默认的那一档"。M10 **不再新建一份**，而是**让界面色块按钮从它生成** |
| 画布板 | `Design/Palette.Canvas.xaml` | M10 新建（值取现状，仅换写法） |

## 4. 目录与加载结构

### 4.1 为什么必须有 C# 侧的令牌访问器

`GfxParameterPanelView.cs`(15.8KB)、`GfxSelectionTool.cs`、`CanvasViewportHost.xaml.cs`(82KB) 都是**纯代码构建 UI**，取不到 XAML 的 `StaticResource`；`MainWindow.xaml.cs` 里另有 5 个 `static readonly Brush`。

所以令牌必须具备 **C# 访问面**。但**绝不能**因此就"XAML 一份、C# 再一份" —— 那正是 §1 里"墨色重复"那个坑的翻版。

**设计**：单一来源 = XAML 资源字典；C# 侧通过 `Design/Tokens.cs` 统一取值（内部走 `Application.Current.TryFindResource`），**不另存一份色值**。

### 4.2 文件布局

```
src/MathPhys.Ink/Design/
├─ Palette.Dark.xaml      ← 界面板·深色（仅 Color / Brush 值）
├─ Palette.Light.xaml     ← 界面板·浅色（与深色同名的键，只有值不同）
├─ Palette.Canvas.xaml    ← 画布板（不随主题变）
├─ Tokens.cs              ← C# 侧取值 helper（Brush(键名) / Double(键名)）
├─ Typography.xaml        ← S1
├─ Spacing.xaml           ← S2
├─ Controls/Buttons.xaml  ← S3
├─ Controls/Inputs.xaml   ← S3
├─ Controls/Panels.xaml   ← S4
└─ Icons.xaml             ← S4（Fluent Geometry 资源）
```

### 4.3 加载顺序

`App.xaml` 合并 `Palette.Canvas` → `Palette.Dark` → `Typography` → `Spacing` → `Controls/*`。
**顺序 = 优先级**（后加载的覆盖先加载的）。换肤时**只替换界面板那一本**，其余不动。

### 4.4 ★ 铁律：会随换肤变的，必须 `DynamicResource`

| 写法 | 换肤时 | 用在哪 |
|---|---|---|
| `{StaticResource Ui.Xxx}` | ❌ **不刷新**，界面留一半旧色 | 只在"确定不随主题变"的键上用（如 `Canvas.*`） |
| `{DynamicResource Ui.Xxx}` | ✅ 立即刷新 | **所有界面板引用** |

★ 最典型的翻车：最外层 `<Window Background="…">` 若写成静态引用，切浅色时会**只换内层、留一圈黑底**，看起来像"漏了一块"。

### 5.3 浅色色板的色温选择

现有深色家族是**暖灰**（R ≥ G ≥ B）：`#33332F`(51,51,47) / `#55554E`(85,85,78) / `#B4B2A9`(180,178,169) / `#F1EFE8`(241,239,232)。

提案浅色**沿用同族**（暖白），而不是纯中性灰 `#F5F5F5`。理由：
1. 延续现有已经在用的护眼调子；
2. 与"纸"白共存时，暖白比冷白更不像"屏幕"；
3. 教室投影下暖白不刺眼。

★ 风险提示：暖白在偏色投影仪上会略显黄。届时**只换值不动结构**（同一套键改一遍即可），这正是设计系统的意义。

### 5.4 S0 的验收判据

1. **视觉零差异**：S0 只换写法不换颜色 ⇒ 改动前后截图**逐像素一致**（可自动比对）
2. **全仓库零裸色值**：扫 `src/**`，除 `Design/Palette*.xaml` 与 `InkPalette.cs` 外，`#RRGGBB` / `Color.FromRgb(` / `Color.FromArgb(` 必须为 0
3. **键存在性**：每个被引用的令牌键都能在资源字典里解析到（★ 拼错键名 WPF **不报错、静默用默认值**，只有肉眼能发现）
4. **令牌冻结**：所有令牌 Brush 均为冻结实例（防止代码改色污染全局）
5. **墨色去重生效**：断言"色块按钮底色 == `InkPalette.Colors[i].Color`"
6. **741 条回归不变**；Debug / Release 均 0 警告 0 错误

## 6. Typography（S1）

### 6.1 层级表（8 档 → 6 档）

| 令牌 | 字号 | 字重 | 用途 | 现状 |
|---|---|---|---|---|
| `Text.Caption` | 13 | Normal | 状态栏右侧提示 | 12 |
| `Text.Label` | 15 | Normal | 分组标签（墨色/笔宽）、次级说明 | 12 |
| `Text.Body` | 15 | Normal | 常规文字、次级信息 | 13 / 14 |
| `Text.BodyStrong` | 16 | SemiBold | 文件名 / 缩放百分比 / 状态 | 14 |
| `Text.Button` | 15 | Normal | 按钮文字 | 系统默认（≈12） |
| `Text.ButtonLarge` | 17 | SemiBold | 停靠条 / 演示窗的大按钮 | 16 |
| `Text.Title` | 18 | SemiBold | 面板 / 窗口标题 | 15 / 17 |

（11 与 12 合并到 `Caption`；18 归 `Title`。）

★ **S1 会有一次"看起来变挤"的阶段**：按钮与标签的字号从 12 提到 15，工具栏会变宽、`WrapPanel` 更早换行。这是**预期的中间态**，空间回收靠 S4 的"图标化 + 分组压缩"。验收按"逐屏比对 + 无溢出无遮挡"。

### 6.2 字体族

现状：**宿主 XAML 里 0 处 `FontFamily`** ⇒ 走 WPF 默认 `Segoe UI`，中文靠系统回退（实际落到微软雅黑）。

提案：显式指定回退链 `Microsoft YaHei UI, Microsoft YaHei, Segoe UI`。理由：
1. 跨机器结果一致（一体机机型不一）；
2. 中英混排（"导出 PNG"）时中英文高度更协调；
3. 与你其他工具的字体习惯一致。

★ **不引入嵌入式字体**：免安装交付要连字体文件一起打包并做授权审查，收益不抵成本。
★ 字体族**只设一次**（`Window` / `Application` 级），不要在 20 个按钮上重复设。

| 令牌 | 值 | 用途 |
|---|---|---|

| `Space.S` | 8 | 组内间隙、控件之间 |
| `Space.M` | 12 | 分组之间 |
| `Space.L` | 16 | 区块之间 |

### 8.3 弹窗策略（★ 需定夺）

现状：
- `MessageBox.Show` **6 处**（打开失败、保存警告、导出结果、覆盖确认…）
- 系统文件对话框 **3 类**（`OpenFileDialog` / `SaveFileDialog` / 文件夹选择）
- ★ **`MessageBox` 与系统文件对话框都是操作系统原生窗口，WPF 无法换皮** —— 它们在 Win10/11 上是系统观感，与我们的深色/浅色界面都不一致。

三个选项：

| 选项 | 做法 | 代价 |
|---|---|---|
| A 保持原生 | 什么都不做 | 观感不统一（深色界面里弹出浅色系统框） |
| **B 自建 `TDialog`（推荐）** | 替换 **6 处 `MessageBox`**；文件对话框保持原生 | 工作量小（形态固定：标题 + 正文 + 1~2 按钮）；可控、可断言 |
| C 引入控件库的弹窗 | 见 §10 | 为一个弹窗引入整套依赖 |

推荐 **B**：6 处 `MessageBox` 的形态高度一致（以 `OK` + Warning 为主），做成一个服务后就永久统一；而**文件对话框自建成本高且无必要**（老师对系统文件选择器最熟）。

★ 另一条候选（不在本里程碑）：**导出结果不用模态弹窗，改成状态栏 + 轻提示** —— 模态弹窗会打断讲课动作。这属于交互改进，建议单独立项。

## 9. 图标方案

### 9.1 候选对比

| 方案 | 授权 | 集成方式 | 体积 | 关键适配点 |
|---|---|---|---|---|
| `Segoe MDL2 Assets`（系统字体） | 随 Windows | 直接用字体 | 0 | Win10/11 均在；但字形粗细不可调、只有单色，缩放清晰度依赖系统 |
| `Segoe Fluent Icons`（系统字体） | 随 Windows | 同上 | 0 | ★ **仅 Win11 提供** → Win10 一体机上会变"豆腐块" ⇒ **排除** |
| **Fluent UI System Icons**（微软，MIT） | MIT | 取 Path Data 内联为 `Geometry` 资源 | 几十 KB | 风格统一、可跟 `DynamicResource` 换色、**无字体依赖** |
| `Lucide`（ISC） | ISC | 同上 | 同上 | 线条更细（1.5~2px stroke），在 40px 触摸按钮里视觉偏轻 |

### 9.2 推荐：Fluent UI System Icons（24×24 Regular，取 Path Data）

理由：
1. **MIT**，可离线拷贝，契合免安装交付；
2. **不引入字体文件** —— 省掉"打包字体 + 授权审查"两件事；
3. 只内联**用到的几十个**，体积可忽略；
4. **可以跟随主题换色**（同一份 `Geometry`，描边色走 `DynamicResource`）；
5. 与本项目"资源进 `Assets/`、随 publish 走"的既有做法一致。

落地规范：
- 统一 **24×24 网格**，`Path` 用 `Stretch="Uniform"` + 固定 `Width` / `Height`
- 主工具栏图标 **24**；停靠条 / 演示窗大按钮 **28~32**
- **统一光学边距**：图标在按钮内居中，四周留 8 —— 不要有的贴边有的居中（这是"看着不整齐"的头号原因）
- **不混用两个图标源** —— 混搭是"不统一"最直接的来源

### 9.3 插件 UI 暂不接管（有意的）

`FunctionPlot` 的输入窗与虚拟键盘是**插件自有界面**（跨程序集）。若要接入宿主设计系统，需为"插件如何取宿主资源"单独定协议；而这两个界面属低频使用，M10 不为它扩大范围。
**这是有意的取舍，不是遗漏** —— 副作用是这两处会在一段时间内与宿主观感不一致。

## 10. HandyControl 评估

### 10.1 事实（2026-09 核实）

- **MIT 授权**；GitHub `HandyOrg/HandyControl` 约 **7.1k★**，最近提交 **2026-07**（活跃维护）
- 多目标框架，**含 `net8.0-windows`**；NuGet 包名 `HandyControl`（3.x 系列）
- 提供 80+ 控件、**全量重写原生控件样式**、自带 Default / Dark / Violet 皮肤；中文文档完善；有 `hc:MessageBox`、`Dialog`、`Growl`、`hc:IconElement.Geometry` 等能力
- 社区选型共识（多篇 2026 选型文）：偏**工业风、信息密度高**，**适合上位机 / 管理端**；默认观感"偏重"
- ★ 被反复点名的头号坑：**"全量覆盖"式样式替换 = 样式污染**（它在 App 级资源里替换**所有**原生控件的默认 Style）

### 10.2 本项目视角的得失

**得**：① 六七种控件的模板不用自己写；② 皮肤机制让深浅切换接近免费；③ 弹窗 / 通知有现成解；④ 图标附加属性更省事；⑤ 中文生态成熟。

**失**：

1. **样式污染直击本项目最敏感的地方**。`CanvasViewportHost` 里 `InkCanvas` 与多个 `Canvas` 的输入归属是靠 `IsHitTestVisible` / `IsManipulationEnabled` **精确控制**的（M7.3 的教训：输入归属一旦被抢，就会出现"笔尖在纸上却写不出字"）。全局替换模板必须**逐条回归**这些输入不变量。
2. **我们的尺寸本来就是"非标准"的**（40×40、字号 +1）。HandyControl 默认是普通桌面尺寸（按钮约 30~32 高）⇒ **仍然要覆盖一遍**，省下的工作量打对折。
3. **不可断言**。本项目核心纪律是"关键行为要能在 harness 里断言"。第三方模板的内部结构我们**断言不了**；而自建模板可以断言"按钮最小边长 ≥ 40""色块底色 == 笔色"这类规范，**规范本身就成了回归项**。
4. **实际用量极小**。我们真正需要的控件只有 `Button` / `ToggleButton` / `CheckBox` / `TextBlock` / `Border` / `ToolTip`（+ 可能的 `ScrollBar`）。没有 `DataGrid`、`TreeView`、`ComboBox`、`TabControl`、`Ribbon`、`PropertyGrid` —— 也就是它 80+ 控件里 **九成用不上**。
5. 多一个约 3~5 MB 的依赖（对包体积无实质影响），但本项目在依赖上一贯克制（连 WinForms 都刻意禁用）。

### 10.3 结论

**M10 不引入 HandyControl，先自建精简设计系统。**

主要理由：真正要自建的模板只有 **6 种左右**（§8.1），而**样式污染面**与**不可断言性**却要**全额承担**；这也与你"低干扰、可控、大屏优先"的方向更一致。

**但保留"可换底"结构**：所有控件一律通过 `Style` / `ControlTemplate` 键引用，**不在 XAML 里内联样式值** —— 将来若要整体替换成任何控件库，业务代码零改动。

**回头重新评估的触发判据**（任一成立就重开这个议题）：

1. 需要 `DataGrid` / `TreeView` / `PropertyGrid`（例如"批量改多题参数""学生名单"）
2. 需要 `ColorPicker` / 取色器
3. 需要多标签页 / 导航框架（例如"M11 做多份试卷并排"）
4. 自建模板的维护成本超过引入成本（用**实际改动量**判断，不靠感觉）

> 若仍倾向现在引入：建议改成**一次限时对比试验** —— 单开分支只做 S3 的三种控件（Button / ToggleButton / ToolTip），量三个数：① 覆盖成 40×40 需要多少条 override；② §12.1 的输入不变量回归是否全绿；③ 包体积增量。**拿数据再拍板，不赌。**

### 12.1 不受影响（已实测确认）

### 12.3 新增的可断言性（M10 的额外收获）

设计系统一旦是"数据"，就能被断言 —— 建议进 harness：

1. **零裸色值**：扫 `src/**`，除 `Design/Palette*.xaml` 与 `InkPalette.cs` 外不得出现裸色值

4. **墨色一致**：色块按钮底色 == `InkPalette.Colors[i].Color`
5. **尺寸规范**：模板层按钮最小边长 ≥ 40

### 19.2 ★★ 必须先知道的事实：纸色只在「页外」可见

页视觉是「纸面矩形（`_paperBrush` 填充）在下 + PDF 位图在上」，而渲染出来的 PDF 位图是**不透明白底**。

harness 那条米黄像素断言之所以能验到纸色，是因为它用的是**没打开文档**的空宿主

所以本次特意把"页外可见"写进操作卡与文档，免得老师以为没生效。

### 19.5 端到端光栅断言为何要显式设笔宽

那条断言验的是"墨水层变换链 == 视口换算"，判据里有一条前置：`stats.InkPixels > 20`
（确认笔画真进了光栅）。默认笔宽从 1.5 降到 0.8 后，100% 缩放下 0.8 world 就是 0.8 px，
抗锯齿后只剩 **4 个墨点** ⇒ 前置不成立、断言 FAIL（而它的偏差其实是 `0.00`，说明**坐标链是对的**）。

修法是给这一段**显式**设一档「中」(1.5)：`host.SetPenWidth(InkPalette.Widths[1].WorldWidth);`
—— 理由是"验坐标就别让笔宽这个无关变量漂"，免得以后每调一次默认笔宽都要重新校准这条坐标断言。
