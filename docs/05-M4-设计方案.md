# M4 设计方案 —— 笔 / 橡皮 / 压感

> 里程碑：M4（在 M3「笔迹层接入」之后）
> 交付批次：**M4a**（工具三态 + 橡皮 + 墨色笔宽）→ **M4b**（压感开关 + 无感设备回退）
> 目标机：希沃一体机（Windows 10/11 x64）

---

## 1. 目标与非目标

### 目标
把白板从"能写字"推进到"能批改"：

| # | 能力 | 说明 |
|---|---|---|
| 1 | 三态工具 | 笔 / 橡皮 / 手。M3 只有笔与手两态 |
| 2 | 笔尾反转擦除 | 笔尾（橡皮头）按到纸上直接擦，不必先去点工具按钮 |
| 3 | 橡皮工具 | 点擦，半径 10 world（≈3.5 mm） |
| 4 | 墨色 | 红（默认）/ 黑 / 蓝 / 绿 / 橙 |
| 5 | 笔宽 | 细 0.8 / 中 1.5 / 粗 2.5 / 特粗 4.0（world 单位） |
| 6 | 压感 | 可开关；设备不报压力时自动回退到恒定笔宽 |

### 非目标（明确不做）
- **不做撤销/重做** —— M5 的正题。
- **不做笔迹持久化** —— M6。所以「清除笔迹」仍是不可逆操作。
- **不做自定义压力曲线** —— 见 §2.4 的理由。
- **不做擦除的替代实现** —— 坚持用 WPF 原生机制，理由见 §2.1。

---

## 2. 关键技术决策

### 2.1 擦除交给 InkCanvas 原生机制，不自己写

WPF 的 `InkCanvas` 自带两条擦除通道：

- `EditingModeInverted`（默认 `EraseByPoint`）—— 笔尾反转时自动启用
- `EditingMode = EraseByPoint` —— 正笔尖也擦

我们的责任因此缩小到两件事：**把 `EraserShape` 设对**、**把反转输入放行**（M3 是 `Handled = true` 直接掐掉）。

**为什么不自己实现**：`StrokeCollection` 没有公开的擦除 API。要实现"点擦"必须自己拆分笔画几何
（按命中点切分 `StylusPointCollection` 并重建 `Stroke`），那正是在推翻 M3 立下的核心命题
——「笔迹几何永不重算」。整笔擦虽然只要 `Strokes.Remove`，但只有一档能力，不够用。

**代价（必须承认）**：擦除动作本身无法被 harness 自动断言 —— `StylusEventArgs` 在测试里构造不出来，
本机也没有笔。所以 harness 只断言"配置与策略正确"，擦除的端到端表现交给 §5 的一体机清单。

### 2.2 输入分工：3 工具 × 2 设备 × 2 反转 = 12 组合

`InkInputPolicy.Decide` 是纯函数（只收 `BoardTool` + `TabletDeviceType` + `bool inverted`），
于是 12 种组合可以被 harness 逐条钉死：

| 工具 | 设备 | 反转 | 动作 | 说明 |
|---|---|---|---|---|
| 笔 | Stylus | 否 | Draw | 笔尖；**鼠标也被 WPF 报成 Stylus**，故鼠标在此落墨 |
| 笔 | Stylus | **是** | **Erase** | ← **M4 唯一的行为变更**（M3 是 Suppress） |
| 笔 | Touch | 否/是 | Suppress | 手指、手掌 |
| 橡皮 | Stylus | 否/是 | Erase | 笔尖与笔尾都擦 |
| 橡皮 | Touch | 否/是 | Suppress | **手指不擦** |
| 手 | 任意 | 任意 | Suppress | 墨迹层同时 `IsHitTestVisible = false` |

两条容易写错的顺序约束，代码里靠次序固定下来：

1. **Touch 判断必须排在"橡皮工具"之前**。否则手指拖一下就擦掉一片批注 —— 而且手掌蹭过屏幕
   不会有人立刻发现，等发现时批注已经没了。
2. **`Hand` 判断必须排在最前面**，且视图侧还要关掉 `IsHitTestVisible`：`EditingMode = None`
   只是"不采集墨迹"，它是否仍然吞掉鼠标事件属于 InkCanvas 的内部实现细节。

### 2.3 橡皮半径用 world 单位（与笔宽同语义）

`EraserProfile.WorldRadius = 10`（world = PDF point ≈ 3.5 mm），
转成 `StylusShape` 时 **直径 = 半径 × 2**（`StylusShape.Width` 与 `DrawingAttributes.Width`
同为"笔尖粗细"语义，默认值就是 8×8）。

因为 `InkCanvas` 挂在被矩阵缩放的 `WorldHost` 下，10 world 的橡皮在屏幕上会跟着缩放同步变大，
"擦掉纸上一块"这个等价关系才成立。**若写成屏幕像素**：放大后橡皮只能擦掉笔画的一小段，
使用者会以为"擦不动"；缩小后一擦擦掉半页。这类错误事后极难回查，所以 harness 专门断言
`EraserShape.Width == WorldRadius × 2`。

### 2.4 压感：只做开关与回退，不做自定义曲线

WPF 在 `IgnorePressure = false` 时按压力因子线性缩放笔宽，**映射曲线是内建的、不可自定义**
（要自定义就得在笔画落下后重建几何 —— 又是"几何永不重算"的禁区）。

真正的坑：**鼠标与一部分不报压力的电容笔，压力因子恒为 0.5**。于是"开了压感"在这些设备上
的表现不是"轻写细重写粗"，而是**整块笔迹统一变成一半粗**。

对策 `PressurePolicy`：抬笔时检查这根笔画的压力样本是否**全等**，是则认定该设备无压感，
把这一根笔画按恒定笔宽处理 —— **只改 `DrawingAttributes`（一次属性赋值），不碰 `StylusPoints`**。

**默认关**：默认关掉就不会有老师遇到"笔迹突然变细"的困惑；想用压感的人在一体机上试过再打开。

视觉代价（仅在主动打开压感后可能出现）：无压感设备上会看到笔迹在**抬笔瞬间由细变粗**。
之所以只能放在抬笔时判断，是因为"压力到底存不存在"要拿到整串采样点才知道，落笔那一刻看不出来。

### 2.5 墨色笔宽即时生效，但只影响新笔画

`ApplyPenSettings()` 只改 `InkCanvas.DefaultDrawingAttributes`，即**只影响之后新落下的笔画**。
已经画好的笔画不跟着变色变粗 —— 那不是偷懒，而是"墨已经落在纸上了"的正确语义。
反过来说，这个设计顺便保证了改笔设置**不触发任何几何重算**。

界面上摆哪几个色、哪几档笔宽，统一来自 `InkPalette`（纯数据），按钮只是它的投影。
harness 断言"出厂默认笔 == 调色板标着默认的那一档"，排除"按钮写着中、实际笔宽是别的值"这类
只有肉眼才能发现的不一致。

### 2.6 M4.1 替换点：笔尾反转探测

`StylusInputInfo.From(StylusDevice)` 是**全工程唯一**把 WPF 设备对象翻译成策略输入的地方。

一体机上如果日志显示 `inverted` **恒为 false**（部分一体机笔驱动不向 WPF 报反转标志），
只需换掉这一处的取值来源（挂 `WM_POINTERUPDATE` 读 `PEN_FLAG_ERASER`），策略层与 UI 层零改动。

刻意**不引入接口**：只有一个实现、且"驱动到底报不报"尚未被实测证实时，接口只是一层没有收益的间接。

### 2.7 光标控制权收归自己

`InkCanvas` 在 `UseCustomCursor = false`（默认）时会按 `EditingMode` **自动覆盖 `Cursor`**，
我们在 `ApplyTool` 里设的值就不作数了。而"现在能写还是能擦"必须准确反映在光标上
—— 一体机上使用者全靠它判断当前工具。所以显式设 `UseCustomCursor = true` 并接管三个光标：

| 工具 | 光标 |
|---|---|
| 笔 | `Cursors.Pen` |
| 橡皮 | `Cursors.Cross`（WPF 没有内置橡皮光标） |
| 手 | `Cursors.Hand` |

## 4. 验收 harness 断言与实测数据

`dotnet build` 生产工程与 harness 均 **0 warning / 0 error**；harness **全部检查通过**（退出码 0）。

### 4.1 M3 段（回归）
「笔 / 手指 / 手掌分工」表扩到 12 组合，含新增的橡皮 4 行与笔尾反转的新期望值。

### 4.2 M4 段

| # | 断言 | 实测结果 |
|---|---|---|
| 1 | 笔：`EditingMode=Ink`、参与命中、笔形光标 | PASS |
| 2 | 橡皮：`EditingMode=EraseByPoint`、参与命中、十字光标 | PASS |
| 3 | 手：`EditingMode=None`、退出命中、手形光标 | PASS |
| 4 | 橡皮形状直径 = 半径 × 2 | 半径 10 world（直径 ≈ 7.1 mm）→ `EraserShape = 20.0 × 20.0` |
| 5 | 笔尾反转模式 = `EraseByPoint` | PASS |
| 6 | 改墨色笔宽立即落到墨迹层 | 设为「蓝 / 特粗 4 world」→ `rgb(11,95,208)`、宽 4 |
| 7 | 出厂默认笔 == 调色板默认档 | 「红 / 中 1.5 world」一致 |
| 8 | 压感回退判据（恒定 / 变化 / 单点） | 三例全部判定正确 |
| 9 | `InkChanged` 事件接线 | 放 1 条 → 1；清空 → 0；期间收到 2 次通知 |
| 10 | 端到端光栅：换墨色后新笔画真的是新颜色 | 蓝色像素 **4900** 个，外接框 **(149,412)-(850,418)** = 701 × 6 px |
| 11 | 且蓝色像素恰好构成一根横线 | 理论线长 696 px、笔宽 6.4 px → 与 701 × 6 吻合 |

第 10、11 条是最强的证据：**默认笔是红色**，所以"蓝色像素数量 > 0"本身就证明墨色切换真的生效；
外接框同时满足"够宽（701 px ≈ 线长）"与"够扁（6 px ≈ 笔宽）"，排除了"把整页误判成蓝"的可能。

### 4.3 像素级复核

用 Node 直接解 PNG 采样（本机没有图形库可用）确证：

```
x=500 y=411  rgb(255,255,255)
x=500 y=412  rgb(163,195,237)   ← 抗锯齿边缘
x=500 y=413  rgb(11,95,208)     ← 设定的蓝 #0B5FD0
x=500 y=418  rgb(11,95,208)
x=500 y=419  rgb(255,255,255)
```

6 px 纯色 + 1 px 抗锯齿 = 6.4 px，与 `4 world × 1.60 缩放` 的理论值完全一致。

**证据图**：`artifacts/m4-smoke/ink-blue-thick.png`；完整验收输出 `artifacts/m4-smoke/verify-m4.txt`。

## 5. 一体机实测清单 ★

以下五件事**本机（只有鼠标、无触摸屏、无笔）根本制造不出来**，必须在一体机上验证。

诊断日志位置：`%LOCALAPPDATA%\MathPhys.Ink\logs\YYYY-MM-DD.log`
每种设备签名只记一次（上限 12 条），格式：

```
===== 2026-09-20 14:32:10.123 [INFO] =====
stylus: type=Stylus name="..." inverted=True → 擦除
```

### 清单

| # | 操作 | 期望结果 | 日志应显示 | 失败时怎么办 |
|---|---|---|---|---|
| 1 | 笔尖在试卷上写字 | 正常落墨，位置不漂移 | `inverted=False → 落墨` | 检查 app.manifest 的 PerMonitorV2 |
| 2 | **笔尾（橡皮头）按在字迹上拖动** | **擦掉字迹，且不出现红字** | `inverted=True → 擦除` | 日志若为 `inverted=False` → 走 §2.6 换 `WM_POINTER` 探测 |
| 3 | 手掌压屏 + 用笔写字 | 只有笔落墨，手掌不产生任何痕迹 | `type=Touch → 抑制` | 若手掌落墨，说明 Touch 未被识别 → 需要换触摸识别路径 |
| 4 | 单指拖动 / 双指捏合 | 平移 / 缩放画布，**不落墨** | `type=Touch → 抑制` | 同上 |
| 5 | 切到「橡皮」工具后用笔尖擦 | 能擦掉笔迹（十字光标） | — | 检查 `EditingMode` 是否为 `EraseByPoint` |
| 6 | 切到「橡皮」工具后用**手指**擦 | **擦不掉**（这是有意的） | `type=Touch → 抑制` | 这不是 bug，见 §2.2 |
| 7 | 勾选「压感」：轻写、重写 | 轻写细、重写粗 | — | 若粗细不变则本机笔无压感（正常，会自动回退）；若整体变细一半 → 回退逻辑没生效 |
| 8 | 缩放到 200% 后写字、擦字 | 字变粗、橡皮视觉同步变大 | — | 若橡皮大小不变 → 半径被写成了像素 |
| 9 | 换墨色 / 换笔宽后继续写 | 新笔画用新色新粗细；**旧笔画不变** | — | 旧笔画跟着变了 = 语义错误 |

### 判定规则

- **第 2 条是 M4 的关键指标**。若日志中 `inverted` 恒为 `false`，则本里程碑的笔尾擦除要换实现
  （§2.6 的单点替换），其余功能不受影响。
- 第 3、4、6 条都依赖"WPF 会把触摸提升成 `TabletDeviceType.Touch` 的笔事件"这一行为。
  若日志里根本看不到 `type=Touch`，说明这条假设在一体机驱动上不成立，需要额外的触摸识别方案。
