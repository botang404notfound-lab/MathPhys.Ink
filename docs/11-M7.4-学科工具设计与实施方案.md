## 1. 需求复述（我理解的样子）

### 1.1 你在讲台上真正要干的四件事

| 场景 | 现在怎么做 | M7.4 之后 |
| --- | --- | --- |
| 讲函数题 | 拿直尺比着画两条歪歪扭扭的轴，刻度靠嘴说 | 拖一个**坐标系**出来，直接在卷面上画**函数图像**，改 a/b/c 看图像怎么动 |
| 讲力学题 | 手绘受力箭头，长度全凭感觉 | 拖出**矢量箭头**，屏幕上直接读"大小 6.0 N、方向 37°"，多力自动给**合力** |
| 讲电学题 | 手绘电路 | （P1）元件库 |
| 讲解析几何 / 光学 / 计量 | 手绘 | （P1/P2）圆锥曲线、单位圆、光路、游标卡尺 |

共同点：**图形要规范**（不是手抖线）、**能改**（拖动/旋转/缩放/换参数）、**不打断书写节奏**（一到两下就出来）。

### 1.2 你给的清单与我的批次划分

- **P0（本里程碑要做）**：量角器、三角板、坐标系、函数图像、矢量箭头
- **P1**：圆锥曲线、单位圆与三角函数、电路元件库、运动学图像
- **P2**：波形图、光学光路、游标卡尺/螺旋测微器、立体几何基础

### 1.3 硬约束（我按这些做取舍）

1. 插件式：一个工具一个独立模块，**可单独启用/禁用**，加工具**不改宿主**。
2. 复用直尺的架构与交互模式（`ITool` + `IToolContext` + 预览层 + 指针转发），**不另起炉灶**。
3. 矢量渲染（WPF `Shape` / `DrawingVisual`），**不用位图**；工具状态必须参与画布平移缩放。
4. 工具之间共存，可单独选中、拖动、旋转、删除。
5. 不整合希沃 SDK，不找"学科工具大礼包"，不引入未经验证的大库（要用先说明理由 → 见 §5）。
6. 关键逻辑中文注释，代码必须可编译。
7. 命名/单位沿用既有不变量：**世界坐标 = PDF point（1/72 inch）**。

### 1.4 我这边的交付纪律（沿用前几个里程碑）

一次只做一个工具 → 每个工具做完先给验证步骤和边界用例 → 需要你在一体机上试的东西一律打成**免安装测试包**（自包含发布 + 包内一份面向非技术人员的操作卡）。

## 2. 关键差距：现有架构只能"落墨"，装不下"对象"

这是本方案最重要的一段，也是必须先做地基的原因。

现有工具（直尺）的输出通道只有一条：

```
ITool.OnPointer → IToolContext.CommitStrokes(StrokeCollection)
                          ↑
                 宿主用一次撤销事务包裹 → 一条 Stroke 进 InkLayer
                 免费继承：世界坐标 / 撤销重做 / 橡皮 / .tbink 持久化
```

这条设计对直尺是**最优解**（它真的只是"一条线"）。但 P0 的五个工具都不满足它：

| 需求 | 一条 `Stroke` 能表达吗 |
| --- | --- |
| 量角器要能**拖动/旋转**、要半透明、要读数跟着转 | ✗ 笔画是死的几何，没有位姿、没有半透明、没有文字 |
| 坐标系要能改 x/y 范围、要网格和刻度数字 | ✗ 同上，而且几何随参数变化 |
| 函数图像要**参数滑块实时联动** | ✗ 必须重新求值重画 |
| 矢量箭头要显示大小角度、要算合力 | ✗ 要读参数、要对象间关系 |
| 五个工具**共存、单独选中/删除** | ✗ 笔画层面没有"对象"这个概念 |

**结论：M7.4 必须先补一层"画布对象层"（持久图形对象模型 + 选择/操作工具）。**
不做这一步，五个工具里的每一个都得自己写一遍"拖动/旋转/选中/持久化"，
写五遍代码、出五处不一致的 bug —— 正是你说的"另起炉灶"。

而对象层一旦就位，**每个 P0 工具就退化成"一个纯几何类 + 一次注册"**，
和直尺的 `RulerGeometry`（纯数学）+ `RulerTool`（薄壳）一模一样。这才是复用。

### 3.2 图层栈：新层插在哪，为什么

```
RootGrid (白底，不缩放，裁剪)
└── WorldHost  ← 全程序唯一的 RenderTransform（世界→视口）
    ├── PdfPageLayer      纸 + PDF 位图
    ├── GfxLayer      ★新  学科工具对象（坐标系/函数图/量角器/矢量…）
    ├── InkLayer          手写笔迹（IsHitTestVisible 由工具决定）
    └── ToolPreviewLayer  拖动中的临时预览（M7.1 已有）
```

**为什么 `GfxLayer` 放在 `InkLayer` 下面**：手写永在最上层。

- 主力用法是"批注"：老师在图上层写字，字必须清晰可见；图形（网格、量角器）压在字上面会脏。
- 反过来的代价：在图形上面写的标注，拖动图形时不会跟着走。这是**几何上正确**的行为
  （标注钉在卷面上），和"用红笔在印好的图上写字，图挪了字不会挪"是一样的。

> 备选是把 `GfxLayer` 放在 `InkLayer` 上面（像 Excalidraw 那样"图形永远是前景"）。
> 我倾向下面，但这条**列进待拍板**（§7-Q1），因为它影响手感且事后改起来只是换个位置。

**`GfxLayer` 整体 `IsHitTestVisible = false`**（和预览层同一条教训）：
命中测试**我们自己算**（世界坐标几何运算），不依赖 WPF 命中测试。
理由有三条，都很硬：
1. 不让图形抢输入 —— 一旦抢，就会出现 M7.3 那种"看着笔在纸上却写不出字"；
2. 命中半径要按**屏幕尺寸**算（手柄 12 DIP ⇒ 世界半径 = 12 / Scale），WPF 命中测试给不了这个语义；
3. **自算的命中测试可以脱离渲染在 harness 里断言**（本机没触摸屏，这条路径只能这样验）。

### 3.3 一个"对象"是什么

```csharp
// 契约层只给只读视图（插件能看、不能改别人的）
public interface IGfxObjectRef
{
    string Id { get; }
    string Kind { get; }              // "protractor" / "coordsystem" / "function" / "vector"
    Point  Center { get; }            // 世界坐标：对象本地原点在世界里的位置
    double RotationDegrees { get; }
    double Scale { get; }             // 1.0 = 插件定义的"标准尺寸"
    Rect   BoundsWorld { get; }       // 外面那圈虚线框（拖动/删除按钮定位用）
    double GetNumber(string key, double fallback = 0);   // 参数（量角器半径、坐标系步长…）
    string GetText(string key, string fallback = "");
}
```

宿主内部的 `GfxObject` 在它之外还有：`IReadOnlyDictionary<string,double> Numbers`、
`IReadOnlyDictionary<string,string> Texts`、`ZIndex`、`IsVisible`、`RendererKey`、`PluginName`。

**一个对象 = 一个视觉元素**（不是一堆元素拼的）：

- 渲染器产出**一个** `FrameworkElement`（通常是 `Path`，几何用 `StreamGeometry` 装好，
  坐标系这种实在需要分层的用一层 `Canvas` 包 `Path` + 刻度文字）。
- 拖动/旋转/缩放时**只改 `RenderTransform` 矩阵，不重建视觉树**（这是流畅度的命门）。
- 只有"参数变了"（函数表达式、坐标系范围、量角器半径）才重建几何。

**位姿的唯一真相源**（新增不变量，写进 `docs/06`）：

```
世界点 ↔ 对象本地点 的唯一换算 = GfxTransform.MatrixOf(object)
渲染：Canvas.SetLeft/Top = Center；RenderTransform = Matrix(Rotate(θ) · Scale(s))，Origin = (0,0)
命中：把世界点用同一个矩阵的逆变换到本地，再套几何公式
```

单一真相源是 `CanvasViewport.WorldToViewport` 已经验证过的模式 —— 渲染和命中各算一遍矩阵，
迟早会出现"看着在这、点着不在"，而且只在某个缩放/旋转组合下复现，最难查。

### 3.4 新增的四条不变量（放 `docs/06`）

1. 对象位姿只有一个矩阵来源 `GfxTransform.MatrixOf`；渲染与命中测试都必须用它。
2. `GfxLayer` 与其内所有元素 `IsHitTestVisible = false`（命中自算，绝不抢输入）。
3. 拖动/旋转/缩放**只改矩阵**；只有参数变化才重建几何。
4. 对象参数只存**世界坐标 + 无量纲参数**，绝不存屏幕像素 —— 与笔迹同源，缩放不漂移。

### 3.5 契约扩展：全部用"可选接口"，`ITool` 一个成员都不加

这是 M7.4 唯一有风险的动作（契约一旦破坏，
已分发出的 `ruler.dll` 会以 `TypeLoadException` 的形式在别人机器上炸），所以规则定死：

- **`ITool` / `IToolContext` / `IToolRegistry` / `IWhiteBoardPlugin` / `ToolPointer` / `ToolEnums` 一个字节都不改。**
- 一切新能力走**新接口**，宿主"有则用、无则按默认值行事"：

| 新接口 | 谁实现 | 宿主怎么用 |
| --- | --- | --- |
| `IToolMetadata` | 工具（可选） | 读 `Category` / `Order` / `ShortLabel`，决定按钮分组与顺序；没有就用默认（顺序=注册顺序） |
| `IGfxTool` | 创建型工具 | 标记"这个工具产出对象"，宿主在 `Deactivate` 时确保预览清空、按钮给出"用完即回"提示 |
| `IGfxObjectFactory` | 插件 | `Kind` + `DisplayName` + `CreateDefault()` —— 反序列化和"新建"都靠它 |
| `IGfxObjectRenderer` | 插件 | `CreateVisual(obj, ctx)`（产出视觉树）+ `RebuildGeometry(...)`（参数变化时重画） |
| `IBoardQuery` | **宿主**（插件只读用） | `SegmentsNear` / `PointsNear` / `Objects` —— 吸附基准的唯一来源 |
| `IGfxObjectHost` | **宿主** | 对象的增删改查（受控：`Add` / `Update` / `Remove` / `Selected` / 选中变化事件） |
| `IToolPanelProvider` | 需要参数的工具 | `CreatePanel(IGfxObjectRef?, IPanelHost)` —— 坐标系的"范围/步长"、函数图像的"表达式键盘 + 滑块" |

**版本策略（顺手修一个真实的坑）**：
现在 `PluginContract.DescribeIncompatibility` 只比**主版本**。
若插件引用了 v1.1 契约（用到 `IGfxObjectHost`）而宿主还是 v1.0，
按现有规则**会被放行**，然后在 `GetTypes` 时炸成 `ReflectionTypeLoadException`，
被加载器当"坏类型"跳过 —— 表现是"插件好像没加载、面板里找不到按钮"，**而且是静默的**。
所以规则改成：

```
Major != host.Major            → 拒绝，理由："插件针对契约 v2，本程序是 v1"
ReferencedMinor > host.Minor   → 拒绝，理由："插件需要契约 v1.1，本程序是 v1.0，请更新程序"
其余                            → 放行
```

契约程序集 `Version` 从 `1.0.0` → **`1.1.0`**（主版本不动 ⇒ 现有 `ruler.dll` 照常加载）。
`PluginApi.Version` 常量保留，但注释改写为"仅供日志/文档显示，判定一律以程序集版本为准"
（避免下一个读代码的人又被 `const` 内联这件事骗一遍）。
harness 加两条断言钉住上面两条新增规则。

### 3.6 两类工具：创建型 vs 编辑型

**这是 P0 交互设计的骨架，先立起来**：

| 类别 | 有哪些 | 生命周期 | 输入声明 |
| --- | --- | --- | --- |
| **创建型** | 量角器、三角板、坐标系、函数图像、矢量箭头 | 按一下 → 拖出形状 → **抬笔落成一个对象** → 工具按钮自动弹回"选择" | `UsesInkLayer=false, NeedsPointer=true`（与直尺完全一致） |
| **编辑型** | **选择**（宿主内置，`id="gfx-select"`）、笔、橡皮、手 | 常驻，按键/按钮切换 | 选择工具同上：`false / true` |

**为什么创建型工具"用完自动回到选择"**：老师画完一个坐标系，下一个动作 90% 是"挪一下/改一下"，
而不是"再画一个"。自动弹回能省一次点击，且不打断节奏（Excalidraw 的图形工具也是这个行为）。

**选择工具做什么**（一次写对，五个工具都受益）：

| 动作 | 交互（一体机可完成，不依赖键盘） |
| --- | --- |
| 选中 | 在对象上按下即选中（**不要求"先选中再拖"**，少一步就少打断一次） |
| 拖动 | 按住拖，实时跟手；松手前给吸附提示（网格/线段/角度） |
| 旋转 | 选中框外侧的圆形手柄（固定 24 DIP，不随缩放变小） |
| 缩放 | 选中框右下角方形手柄（等比） |
| 删除 | 选中后浮出的"✕"按钮 + `Del` 键（一体机上用按钮） |
| 取消选中 | 点空白处 |
| 覆盖别人的对象 | 后添加的在上面（Z 递增）；选中时临时提到最上层（只影响显示，不改 Z） |

**手柄命中半径要按屏幕算**：`世界半径 = 12 DIP / Scale`。
一体机上手指触点是"胖"的（M4.2 的实测结论），手柄太细就是"点了没反应"。

### 3.7 输入通道：零改动复用

这是 M7.1 设计红利最直接的兑现 —— 创建型工具和选择工具都只是
`UsesInkLayer=false, NeedsPointer=true`，于是：

- `InkLayer.IsHitTestVisible = false` ⇒ 输入根本不路由到墨迹层（M4.2 的"不落墨"正确姿势）；
- `IsManipulationEnabled = false` ⇒ 触摸被提升成笔事件（一体机上被动笔 = 触摸，已统一）；
- 宿主的 `OnPreviewStylus* / OnMouse* → ForwardToTool → DispatchPointer` 已经把**世界坐标**递给工具，
  且已用 `_toolPointerActive` 做过 Stylus/Mouse 双链去重。

**⇒ 宿主输入代码一行不用改。** 新增的对象层完全靠"工具收到指针事件后自己算"接入。

### 3.8 `IBoardQuery`：吸附基准的唯一来源

量角器要"吸附到已有直线"，三角板要"靠到已有直线"，坐标系要"吸附网格"，
矢量箭头要"吸到端点/交点" —— 都需要**看见画布上已有的东西**。给一个只读门面：

```csharp
public readonly record struct BoardSegment(Point From, Point To, BoardSegmentSource Source);

public interface IBoardQuery
{
    IReadOnlyList<Rect> PageRects { get; }                       // 页框（贴边、居中、中心吸附）
    IReadOnlyList<BoardSegment> SegmentsNear(Point world, double radiusWorld);
        // ↑ 来源合并：① 墨迹层里的笔画（拆成线段，直尺画的线在这里）
        //             ② 对象层里的线段（别的工具画的线）
        //   直尺画的辅助线能被量角器吸附 —— 这条链路是"工具协作"的最小证明
    IReadOnlyList<Point> PointsNear(Point world, double radiusWorld);   // 端点/圆心/交点
    IReadOnlyList<IGfxObjectRef> Objects { get; }                        // 函数图像要靠它找到坐标系
}
```

**只读，且没有"改别人对象"的成员** —— 与 `IToolRegistry` 只给 `Add` 是同一条原则：
一个插件能删/改别人的对象，出问题就没人说得清是谁干的。

性能约束：`SegmentsNear` 必须**只扫视口附近**（传入 radius 就是给它一个界），
并且对墨迹用**包围盒粗筛**后再做线段距离。一节课下来几百条笔画，逐条精算会在拖动时掉帧。
（实现方式：宿主维护一个"笔画包围盒 + 分页索引"的轻量缓存，`StrokesChanged` 时增量重建。）

### 3.9 参数面板：一体机上没有键盘，这是硬约束

坐标系要选范围、函数图像要敲表达式、矢量箭头可能要填数值 —— 都在"需要打字"的边界上。
**M4.2 的结论是一体机上的键盘完全不可依赖**，所以：

- 宿主在工具栏下方提供一条**参数区**（默认折叠，工具激活或对象被选中时展开，高度 56~72 DIP）。
- 面板内容由插件提供（`IToolPanelProvider.CreatePanel`），宿主只负责摆放与生命周期（切换工具/取消选中即销毁）。
- **面板内容一律"点得出来"**：
  - 范围/步长/笔宽这类 → **固定档位按钮组**（如 x∈[-10,10] 步长 1 / [-5,5] 步长 0.5 / [0,2π] 步长 π/2）
  - 数值参数 → `Slider`（WPF 原生，触摸可拖）+ 两侧 ± 微调按钮
  - **函数表达式 → 插件自绘的函数键盘**（`0-9 x ( ) + − × ÷ ^ .`、`sin cos tan ln log √ π e`、退格、清空）
- 表达式**只用键盘能拼出的语法**（见 §6.5），这样"能敲出来的"与"能解析的"永远一致。

### 3.10 撤销与重做：统一时间线

现状：`InkHistory` 的真相源是 `StrokeCollection.StrokesChanged`（M6 验收过，**不动它**）。
对象层的增/删/改也需要撤销。若各管各的，老师按 `Ctrl+Z` 时**无法预知**撤的是字还是图。

**方案（推荐）**：

```
BoardHistory（新增，宿主）
├── 时间线：LinkedList<BoardOp>   { Ink | Gfx }，按真实发生顺序
├── Ink 步：由 InkHistory 的 Changed 事件通知进来（顺序天然正确）
├── Gfx 步：快照式 —— 操作前把对象集合序列化成一份 JSON 快照（几十个对象 ≈ 十几 KB）
│            撤销 = 还原上一份快照；重做 = 还原下一份
└── Ctrl+Z / Ctrl+Y 一律问 BoardHistory，问完再分派给对应的子历史
```

**为什么对象层用"快照"而不是"命令"**：对象图很小（一节课几十个对象），快照法
**几乎不可能有 bug**（没有"反做"逻辑要写对），而命令式撤销最容易出的错就是
"移动撤销回去了、旋转没回去"这种半还原状态。M6 在墨迹层上已经付过一遍代价，
对象层没必要再付一次。内存上限设 60 步（超出丢最老的），一节课够用。

自检断言（harness）：
`画一笔 → 放一个量角器 → 拖走它 → Ctrl+Z ×3` ⇒ 依次回到"量角器原位 / 量角器消失 / 笔迹消失"。

### 3.11 持久化：`.tbink` v2（一个侧车文件里装两样东西）

现有的 `.tbink` 是自研容器：`magic(6) + version(u16) + jsonLength(i32) + manifest.json + ISF 载荷`。
**v2 只是加一段**（不新增文件 —— 老师拷试卷时只需要拷一个侧车，这条很实际）：

```
v1:  TBINK\0 | ver=1 | manifestLen | manifest.json | ISF 笔迹
v2:  TBINK\0 | ver=2 | manifestLen | manifest.json | objectsLen | objects.json | ISF 笔迹
                                                        ↑ 新增这一段
```

- `objects.json`：`[ { id, kind, plugin, x, y, rot, scale, numbers{}, texts{} } ]`（世界坐标）。
- **读时按 version 分支**：v1 → objects 为空（老文件照常打开，零回归）。
- **写时按版本决定**：
  - 有对象 ⇒ 写 v2；
  - 没有对象 ⇒ **仍写 v1**（这样"新程序存的纯笔迹文件"还能被旧版本打开，不制造无谓的不兼容）。
- v2 文件被旧程序打开 ⇒ 现有代码已经会拒绝并说清原因
  （"批注文件版本 2 高于本程序支持的 1，请升级程序后再打开"）—— 正好是"绝不静默"的体现，不用加活。
- **未知 `kind` 不能丢**：某个插件被禁用/删掉时，它留下的对象要
  ① 画成一个虚线占位框（标明"缺少插件：protractor"），② 状态栏提示有几个图形缺少插件，
  ③ **保存时原样写回**。丢了老师一节课的板书，比少个按钮严重得多。
- 落盘沿用现有约定：**临时文件 + 原子替换**；对象与笔迹都为空 ⇒ 删侧车。

### 3.12 启用 / 禁用某个工具

用**目录约定**，不引入配置解析：

```
plugins\protractor\protractor.dll        ← 启用
plugins\_disabled\protractor\protractor.dll  ← 禁用（挪进来即可）
```

加载器只需跳过 `_` 开头的目录（一行判断）。好处：无配置文件可漂移、老师拖个文件夹就完成操作、
`说明.txt` 里两句话讲清楚。**不再另做"插件管理器"界面**（P0 不需要，收益不值那个成本）。

```
常量   π (pi)   e
运算   + - ×(或*) ÷(或/) ^(幂)  一元负号
函数   sin cos tan asin acos atan sinh cosh tanh
       ln log(以10为底) log2 sqrt abs exp floor ceil round sign
括号   ( )
隐式乘法  2x  3sin(x)  2(x+1)   （★ 中国人的默写习惯，必须支持）
定义域   sin(x), x∈[-2,2]        （逗号 + x∈[a,b]）

```

**交互**

- 创建：点函数图像工具 → 若当前页已有坐标系，**直接绑定最近的那个**（并把采样范围按它的 x 范围走）；
  没有坐标系 ⇒ 先自动放一个默认区间 [-10,10] 的坐标系（降低门槛），状态栏说明。
- 面板：表达式输入框（**只读**，纯由键盘按钮拼写，避免系统软键盘弹出来遮住画布）+
  `sin cos tan ln log √ ( ) x π e` 键盘 + 退格/清空 +
  参数滑块（自动列出表达式里出现的参数字母，每个一根 `Slider`，范围默认 [-5,5] 步长 0.01，档位可换）+
  选项（网格/零点/交点/极值开关）。
- **多函数叠加**：一个坐标系对象可以关联多个函数对象（每个函数对象自己一条曲线 + 自己的颜色）。
- 滑块拖动时：**只重算这一个函数**，且节流到每帧一次（`Dispatcher` Background，不要每次 `ValueChanged` 都重算）。
- 曲线颜色取当前墨色；同一坐标系里的第二条曲线自动换色（避免全叠在一起看不清）。

**验收断言（不靠肉眼）**

| 断言 | 钉住 |
| --- | --- |
| 解析：`sin(x)`、`x^2`、`1/x`、`log(x)`、`2x`、`3sin(x)`、`x∈[-2,2]`、分段 `x<0: -x; x>=0: x^2` 全部无错误解析 | 语法 |
| 求值：`sin(π/2)=1`、`2^10=1024`、`1/0 → NaN`（不抛）、`log(-1) → NaN` | 数值 |
| **奇点断开**：`1/x` 在 x∈[-1,1] 采样 ⇒ 生成 **2 段**不连续路径（绝不能连成一条竖线） | 函数绘图最经典的坑 |

## 5. 第三方库取舍（逐条给理由）

### 5.1 我建议**不引入**的（以及为什么）

| 候选 | 结论 | 理由 |
| --- | --- | --- |
| **OxyPlot / ScottPlot** | ❌ 不引入 | 它们自带**独立的轴、缩放、平移、命中测试**，与"世界坐标系 + 单一 RenderTransform"这套架构正面对撞：要么把它的坐标系塞进我们的矩阵（两个坐标系打架、每次缩放都要跟它同步），要么放弃我们的视口语义。而我们真正需要的只是"采样 N 个点 → 一条 `StreamGeometry`"，约 100 行。引入它 = 拿一个大依赖换 100 行代码，还附送一堆不可控行为。 |
| **NCalc** | ❌ 不引入 | 三个具体理由：① `^` 在 NCalc 里是**位异或**不是幂（老师敲 `x^2` 会得到怪结果）；② 不支持**隐式乘法**（`2x`、`3sin(x)` 是中国人写数学的默认习惯，必须支持）；③ 错误信息是英文的、且没有"第几个字符"的位置信息，没法给老师可读的中文提示。自己写递归下降约 300~400 行，完全可控、可单测、零依赖、还能当"函数键盘"的唯一语法真相源。 |
| **xaml-math (WPF-Math)** | ⏸ 本期不用 | 它解决的是"把 LaTeX 排成漂亮的数学版式"。P0 阶段我们要显示的是 `y = a·sin(bx+c)` 这种**单行表达式**，普通 `TextBlock` + 等宽字体完全够用且更好调（反缩放/反旋转）。等 P1 要做"分式/根号/求和号"排版时再评估，那时它的价值才真实。 |
| **SpiceSharp** | ⏸ 本期不用 | P1 的电路元件库要的是"**画**电路 + 改元件参数"，不需要解节点方程；实时显示电压电流也是"读数"而不是"求解"。等真要做"电路仿真"再说，届时可评估。 |
| **WebView2 嵌入 Web 工具** | ⚠️ **条件性采用**（2026-09-22 改判，见 `docs/12`） | **只允许用于"独立演示面板"形态（GeoGebra），不得用于"参与画布变换的工具"。**改判理由：把定位从"随画布缩放平移的工具"改成"独立面板"之后，下面三条**两条自动消失、一条降级**。**以下三条仍是硬前提，违反任一条即退回"不采用"**：① **触控穿透**（仍存在但可控）：WebView2 是独立进程消费笔/触摸 ⇒ 面板**不得与画布重叠**，必须是全屏接管或停靠让位；面板激活时必须互斥抑制画布墨迹输入（`InkLayer.IsHitTestVisible = false`）；② **性能**（已消除）：面板不参与画布变换 ⇒ 平移缩放**不需要**跨进程同步；但如果将来要求"实时跟随"，本条立即复活 ⇒ **禁止**；③ **不参与 `RenderTransform`**（已消除）：我们**不再要求**它参与 —— GeoGebra 用自己的坐标系是它的天性。**若哪天要让它"跟着卷面缩放平移"，本否决立即恢复。** |

**一句话总结选型原则**：凡是"自带坐标系/自带窗口/跨进程渲染"的库，都与"世界坐标 = 唯一真相源"这条不变量冲突；
P0 全部自绘（`Path` + `StreamGeometry`），依赖只增加**零个**。

> **补充（2026-09-22，M7.5）**：唯一例外是 **GeoGebra**，它以**"独立演示面板"**形态接入 —— 明确**不参与**画布变换，从而不与上述原则冲突。
> 完整论证、触控互斥方案、通信契约与许可合规见 **`docs/12-M7.5-GeoGebra整合方案.md`**。
> 注意：**现有 6 个原生学科工具一个都不改**（继续保持自绘），GeoGebra 只补**"动态几何/约束联动"**那一类原生做不到的活。

### 5.2 顺带说明：为什么不给每个工具建独立类库

你现在只有 1 个插件工程，P0 后会变成 6 个（Ruler + 5 个）。**建议保持"一个工具一个工程"**（不合并）：
独立工程 = 真正的可单独启用/禁用、可单独发版、坏一个不影响别的 —— 这正是插件式的价值。
代价是 `.sln` 项目数变多，可以接受（放进 `src/plugins/` 目录形成一组，视觉上就整齐了）。

## 6. 已预见的坑（提前写下来，省一轮返工）

### 6.1 性能
- 坐标系满屏网格 + 3 条函数曲线 + 5 个对象 ⇒ 视觉元素要**少而大**（一个对象一个 `Path`，几何用 `StreamGeometry`）。
- 拖动只改矩阵；参数变化才重建几何；重建时先 `Freeze()` 几何与画笔（WPF 会跳过变更通知）。
- 函数采样点数按**缩放自适应**（缩小时少采：屏幕上一个点采一次就够），并设硬上限。
- `IBoardQuery.SegmentsNear` 必须粗筛（包围盒 + 视口裁剪），**绝不能**每次 Move 都遍历全部笔画。

### 6.2 触控（一体机）
- 手柄/按钮的命中半径按**屏幕 DIP** 算（≥ 12 DIP），不要按世界单位写死。
- 一切操作都要有屏幕入口：删除、旋转、参数微调 —— **不能只有快捷键**。
- 旋转手柄要在"选中框外侧"（避免与拖动冲突），否则会"想转却在拖"。

### 6.3 排序与输入
- `GfxLayer` 及其所有元素 `IsHitTestVisible=false`（抢输入 = M7.3 的同款灾难）。
- 选中工具下，**左键归工具**（与直尺相同取舍）：想平移请用中键或切"手"（状态栏要给提示语）。
- 对象 Z 序在"选中时临时提到最上层"只影响显示，不改真实 Z（否则每选一次 Z 就漂）。

### 6.4 数据与兼容
- `.tbink` 加段必须**按版本分支读**，老文件零回归；无对象时仍写 v1。
- 未知 `kind` 绝不丢：占位显示 + 原样写回。
- 契约只加新接口、`ITool` 不动；次版本纳入兼容判定。

### 6.5 函数绘图的三个经典坑（不防就会"看起来对、其实是错的"）
1. **奇点连线**：`1/x`、`tan(x)`、`log(x)` 在定义域外/奇点附近，采样点跨过去会被连成一条**竖直假线**。
   必须在"值变 `NaN`/`∞`，或相邻两点跨度超过阈值"处**断开路径**。
2. **采样密度 vs 高频函数**：`sin(1000x)` 会退化成锯齿。做采样上限 + 状态栏提示"该区间采样不足，图像仅供参考"，
   **不假装它是真的**。
3. **隐式乘法的歧义**：`2e` 是 `2·e` 还是科学计数法 `2e`（缺指数）？定死规则：
   **`e` 只在"前面不是数字"时当常量**；`2e3` 按 `2000` 处理（科学计数法优先），并在键盘上不提供 `E` 按钮避免歧义。

### 6.6 工程约定（沿用既有教训）
- 同一文件不要并行 Edit（M7.2.1 踩过第三次）—— 本里程碑同样只串行改文件。
- 跑 dotnet 前先 `$env:DOTNET_CLI_UI_LANGUAGE="en"`。
- 需要 `Add-Type` 的本机验证走 Python（沙箱会拦 `Add-Type`）。
- 交付包压缩用 `Compress-Archive -Path "dist/tablet/*"`，压完校验"产物是文件 + 无同名目录残留"，
  并且**不删** `dist` 里疑似用户已解压的那份目录。

### 9.3 过程中发现并修掉的两个真 bug

1. **`PluginLoader` 的次版本规则缺失**（§3.5 预告的那个）。
   `DescribeIncompatibility` 原先只比主版本 ⇒ "插件引用 v1.1、宿主只有 v1.0" 会一路走到

2. **`MainWindow` 加载插件时没交渲染器注册表**。
   `PluginLoader.LoadAll(ViewportHost.PluginRegistry)` 少第二个参数 ⇒
   插件提供的渲染器一个都登记不上 ⇒ **插件的图形全变成虚线占位框，而日志一片正常**。
   这正是 §3.5 预判的"最难查的失败方式"，已在接线阶段就堵掉并写进注释。

3. **`HostGfxObjectHost.Add` 必须自己记一步历史**（计划里没写清）。
   撤销的正确姿势是"改之前先存快照"，而"新建"没有"改之前"可给工具调用。

   现由宿主在 `Add` 内部先 `Capture` 再入库。

### 10.3 过程中发现并修掉的三个真 bug

1. **拖动中的预览盘面整体偏了一条半径。**
   预览用"以圆心为原点"的几何（`[−R,R]×[−R,0]`），摆进预览层时写成
   `Canvas.SetLeft(preview, 圆心.X + 几何包围盒.X)` —— 这是"元素左上角 = 包围盒左上角"的直觉。
   实测（本机）结论：**`Stretch=None` 的 `Path` 不把负坐标几何平移到非负区，元素原点就是几何原点**，
   于是整把盘面飘到笔尖的**左上方 110 world（≈3.9 cm）**处。
   这个 bug 不报错、不写日志、代码里怎么看怎么对，**只有"盯着笔尖看"或量像素才发现**。
   修法：`Canvas.Left/Top` 直接给**圆心**。同时在 harness 里立了一条纯蓝填充 + 逐像素外接框的断言（第 8 段）。
   > 顺带记住：`Canvas` 默认不裁剪子元素，所以偏出去的几何照画不误 —— 它不会用"缺一块"来提醒你。
2. **抬笔那条路上的"调用顺序陷阱" ⇒ 吸附静默失效。**
   `Commit` 的正确顺序是"先把状态读成局部变量 → 清预览 → `Reset()`"；而 `ResolveOrientation`
   当初读的是 `_center` 字段，`Reset()` 已把它归零 ⇒ 抬笔时拿着 `(0,0)` 去问"圆心附近有什么线"
   ⇒ 永远吸不上。**屏幕上没有任何异常，只是没对齐** —— 而"自动对齐"是这把工具唯一的存在理由。
   修法不是"记得先调用"，而是**不共享可变状态**：`ResolveOrientation` / `ResolveCenter` 都改成
   `static` + 显式传 `center`（注释里把这次踩坑写成了"为什么必须传参"）。
3. **`TrySnapOrientationToSegments` 在不该吸的时候也返回 `true`。**
   归一化之后的候选值被当成"已吸附"返回 ⇒ 工具会把"没吸上"的状态栏提示成"已对齐卷面上的线"。
   修法：只有 `bestDelta <= tolerance` 才 `return true`，否则 `snapped = normalized; return false`。
   （这条 bug 是第 4 段断言里"容差边界 31° 吸 / 30.9° 不吸"逼出来的。）

1. **几何画的是数学坐标而不是世界长度**（**`BuildGrid/BuildAxes` 没乘 `unitWorld`**）。

3. **`PageSnapCandidates` 是固定 9 个点（页角 + 页边中点），不是"按下点 x/y 处的页边最近点"** ——

   修法：4 条页边的候选改成**按 `world.x/world.y` 算** —— "按下点那列的那条边"。这样 (120, 10)

### 13.3 过程中发现并修掉的真 bug（4 个）

1. **csproj 漏 `<ImplicitUsings>enable</ImplicitUsings>`** → 5 个 CS0246（`Exception`/`Func<>`/`List<>`/`IReadOnlyList<>`/`UniformGrid` 找不到）。
   根因：新建插件用了这些 BCL 类型却无显式 `using`（坐标系/三角板等老插件恰好没用到）。修：csproj 加 `ImplicitUsings`，并为 `UniformGrid`(→`System.Windows.Controls.Primitives`)、`Path`(→`System.Windows.Shapes`) 补显式 `using`。
2. **词法隐式乘法把 `sin(x)` 误插成 `sin * (x)`** → 解析器报"函数后面要跟括号"。根因：`NeedsImplicitMul` 把"Name 后跟 LParen"也补了 `*`，
   但函数调用 `sin(` 不应补。修：左为 Name、右为 LParen 时**不补乘号**（仅 `2(x+1)`/`(x+1)(x-1)` 这类 Number/RParen 后跟 LParen 才补）。
3. **`1/0` 断言写错**：浮点 `1/0=+Infinity`（不是 `NaN`），原断言 `IsNaN` 误判失败。修：求值器行为正确，改测试为 `IsInfinity`；此 bug 暴露了"预期值写错"而非逻辑错。
4. **端到端红色不渲染**：check 10 只注册了函数渲染器，坐标系渲染器没登记 → 坐标系几乎不画（仅 43 红像素）。修：补 `RegisterGfxRenderer(new CoordSystemRenderer())`；
   同时把对齐断言从"绝对像素/翻转敏感"改为"对视口变换不敏感"（用 `Viewport.ToViewport` 取原点真实屏幕位置 + 检查曲线过原点 + 水平居中），避免视口默认缩放/翻转导致误判。

**§14.1 绑定机制（关键设计）**

- **为什么必须落在宿主**：渲染器只拿得到**自己这一个对象**（`IGfxObjectRef`），看不到画布上的别人。
  "我要跟着谁、他现在在哪"只有掌握全部对象的 `GfxObjectStore` 答得出来。
- **怎么声明**（零契约改动）：`Texts["bindTo"] = 目标Id` + `Numbers["bindRelX"/"bindRelY"/"bindRelRot"]`
  （相对目标原点的偏移与额外旋转；当前工具恒为 0,0,0）。
  用 `Texts` 字符串键而不是给契约加成员 —— 契约一改，已分发出去的插件 dll 有 `TypeLoadException` 风险
  （M7.4 Step 1 起立的规矩）。`"systemId"` 作为旧存档兼容键保留。
- **怎么推导**（`GfxObjectStore.RecomputeAttachments()`，在 `RaiseChanged()` 里跑，**先重算再通知**）：
  ```
  Scale   = 目标的 unitWorld × 目标的 Scale      // 1 数学单位 = 目标的世界单位长
  Rotation = 目标旋转 + bindRelRot
  Center  = 目标.LocalToWorld(bindRelX, bindRelY) // 偏移 0 时就是目标原点
  LineWorldWidth = 目标.LineWorldWidth × 目标.Scale  // 轴的粗细随目标缩放变，曲线得一样粗
  ```
  放进 `RaiseChanged()` 而不是让每个改位姿的地方自己记得调：漏一处的表现是"偶尔有几帧曲线没跟上轴"，肉眼几乎抓不住。
- **拖被绑对象 = 拖整幅图**：`UpdatePose` 检测到目标是绑定的，就把位姿改动**转嫁给目标**（缩放按比例转嫁）。
  否则用户抓住曲线一拖、下一帧又被拉回去，表现成"手柄在、拖不动"，比不让拖更困惑。
- **目标被删 ⇒ 曲线留在原地**（不静默丢数据），并变回可自由拖动。

```
obj.Scale = unit × targetScale
```

这是为**函数曲线**设计的 —— 曲线的本地几何 = 数学坐标，乘 Scale 后正好得到世界长度。
箭头如果照搬"本地几何 = 世界长度"，就会被这个公式**再乘一次 unit**。

实测症状：箭头跟随坐标系后 **世界长度被放大 28.35 倍**（unitWorld 的典型值），从 370 世界单位变成 2284.5，
画面上是一根戳出屏幕的巨杆；而 `LengthWorldKey` 读数仍然正确 —— **数据对、画面对**。

**修法**（零契约改动、零宿主改动）：箭头也遵守"本地几何 = 数学单位"这条约定：

```csharp
// 本地长 = 世界长 ÷ 一个数学单位的世界长度
double lengthLocal = LengthWorldOf(obj) / UnitOf(obj);
```

**规律（写进 `docs/06`）**：凡是绑到坐标系上的对象，本地几何一律按"数学单位"画；
`LengthWorldKey` 这类"给宿主和人看的量"仍存世界值，两者靠 `unitWorld` 换算。
这样任何对象都能零改动复用同一套跟随机制。

**§15.5 `const` 借用：编译期内联，不产生运行时 dll 依赖**

箭头要复用直尺的吸附常量（`SnapStepDegrees` 等），但**不能**让 `vectorarrow.dll` 依赖 `ruler.dll`：

```csharp
public const double SnapStepDegrees = RulerGeometry.SnapStepDegrees;   // 编译期取值并内联
```

`const` 的取值发生在**编译期**，结果作为字面量烧进 IL ⇒ 生成的 dll 里**不含**对 ruler 的引用。
验证方式（双重）：① 字节级 —— `vectorarrow.dll` 里 `ruler` 出现 **0 次**；② 交付目录 —— `plugins/vectorarrow/` 下**没有** `ruler.dll`。
（csproj 仍需 `ProjectReference` 才能编译，所以配 `<Private>false</Private>` + `<ExcludeAssets>runtime</ExcludeAssets>` 阻止它被复制出来。）

**注意：只复用常量，不复用函数。** 直尺的 `SnapAxisDegrees` 是"直线轴向 [0,180)"语义（178°→0°），
矢量方向是 [0,360) 极角语义，两者含义不同，各写各的。

### §17.2 设计：一个"一对多"难题

宿主既有绑定区（`BindKey="bindTo"`）**只认单个 Id**，而合力是"一根箭头取决于 N 根分矢量"。
两条路：

- 让宿主绑定区支持多目标 → 要动宿主绑定模型，面大。
- **合力对象自己记下"我由谁组成"，由插件侧渲染器实时求和** → 宿主只需"在合适时机提醒我重算"。

选后者。约定：

```
Texts["sumOf"] = "id1,id2,id3"      // 逗号分隔的分矢量 Id
```

- 求和发生在 **`ArrowRenderer`**（插件侧），不占用宿主绑定区；
- 合力对象**不设** `BindKey`，`Scale=1.0`、`RotationDegrees=0` ⇒ **不跟随坐标系**（有意的：
  合力是把"已经画在卷面上的几根箭头"加起来，跟背景网格无关）；
- 冗余存档 `magnitudeN` / `angleDeg` / `lengthWorld` / `unitWorld`，供排查与将来复用。

### §17.3 补的两个宿主级结构缺口（都是合力"逼"出来的）

合力是本项目**第一个"我画什么取决于别人"**的对象，它同时暴露了两处宿主缺陷：

**缺口 1 — `GfxObjectLayer.Sync()` 参数变了不重建几何。**
原本只在"视觉不存在"时 `Build`，参数变了只 `ApplyPose` ⇒ 几何**永远不重画**
（函数图像没暴露，是因为它当时还没有参数面板）。
改为 **"几何签名（`LocalSize`）变了就重建"**：
`LocalSize` 由渲染器 `Measure` 算出、与 `CreateVisual` 读同一份参数；
纯位姿变化不改 `LocalSize` ⇒ 拖动仍只改矩阵、**不重建几何**（保住流畅度）。

**缺口 2 — 渲染器看不到画布。**
求和要知道"别人在哪"。新增**可选**契约接口（只加不改）：

```csharp
// src/MathPhys.Ink.Plugin.Abstractions/IGfxBoardAwareRenderer.cs
public interface IGfxBoardAwareRenderer
{
    void SetBoard(IReadOnlyList<IGfxObjectRef>? objects);
}
```

宿主用 `is` 判断后调用（`GfxObjectStore.FeedBoard`、`GfxObjectLayer.CreateContent`）；
**不实现该接口的渲染器零影响**，已分发的旧插件 dll 照常工作。

★ 注意：该接口**必须实例实现**，不能用静态字段缓存画布 ——
同一进程里有多个 `ArrowRenderer` 实例（harness 就造了好几个 catalog），
静态字段会互相踩快照。开发中途自我纠正过一次。

### §17.4 刷新通路（用户选"1"）

```
GfxObjectStore.RaiseChanged()
   └─ RecomputeAttachments()
        ├─ …既有绑定区重算…
        └─ RefreshSumObjects()          // 新增：凡是带 sumOf 的对象，重算 LocalSize
             └─ MeasureSize(obj)
```

### §17.6 ★ 一处我自己写错的物理断言（非代码 bug）

初版断言写「3 N 东 + 4 N 北 = 5 N、36.87°」→ 4 条 FAIL，报 `5.000000 N、53.130102°`。
先怀疑 `VectorSum` 有镜像 bug，用独立 Python 复刻 `UnitVector` + `DirectionDegrees` 手工验算，
结论 **代码完全正确**：

- **`36.87° = atan(3/4)` ⇒ 对应【4 N 东 + 3 N 北】**；
- `3 东 + 4 北` ⇒ `atan2(4,3) = 53.13°`。
- 根因：规格里只说"3-4-5 ⇒ 5 N、36.87°"，**没说哪条边朝哪**，我配对配反了。

**修法（值得记的套路）**：不只改对，还**同时断言互为反例的另一条**
（`4东+3北 ⇒ 36.87°` 与 `3东+4北 ⇒ 53.13°` 并列）——
这样"角度镜像"这类错误**无论往哪边偏都跑不掉**。

### §17.7 harness 实测

`RunM74S5SumChecks`（第 20 组），**13 小节 / 20 条断言，0 失败**。逐条：

- `VectorSum` 纯函数：`4东+3北 ⇒ 5 N、36.87°`；`3东+4北 ⇒ 5 N、53.13°`（反例）；
  三力合成同通路；零合力判定生效。
- `sumOf` 解析：去空项、去重（**重复会让合力翻倍，肉眼看不出来**）；无 `sumOf` 不当合力。
- 渲染器真实路径：合力线长 = 5 N 对应世界长度；**虚拟树构造不抛**；
  `ReadShaftPen` 反射读出 Pen 对账 ⇒ 合力是 Dash、普通箭头是 Solid；合力线更粗（×1.25）。
- 自动跟随：**分矢量改了合力跟着重算**（不是钉在旧值）；删分矢量后按剩下的重算；
  全删光后合力仍在且尺寸为正（**不会变成删不掉的一条线**）。

### §18.2 批次 ④ 的设计：把“读图”变成“算图”

老师的真实诉求是「画完函数，我想直接看到它跟 x 轴交在哪、最高点多高、跟另一条线在哪儿相交」。
这四件事全是**数值求根**，不是渲染问题，所以单独立一个纯数学类
`Expr/FeatureFinder.cs`，与渲染器解耦（渲染器只负责把结果画成小圆点 + 读数）。

- `FindZeros`：粗扫 2000 格找变号区间 → 折半 200 次。
- `FindExtrema`：对导数求根。**导数用中心差分**，再按符号变化判极大 / 极小。
- `FindIntersections`：把两条曲线相减得 `BinaryNode(a, '-', b)`，再对它求根。
- 三者都收 `maxResults`（默认 64），防止 `sin(1000x)` 把画面糊满。

表达式引擎同步扩了三类节点（**只加不改**，旧 `case` 的 `default:` 恰好返回 NaN = 「未定义」，语义自洽）：

| 新节点 | 语法 | 用途 |
| --- | --- | --- |
| `DomainNode(Inner, Condition)` | `x^2 where x>0` / `x^2 if x>0` | 限定定义域 |
| `PiecewiseNode(IReadOnlyList<PieceBranch>)` | `{x<0: -x, else: x}` | 分段函数 |
| `CompareNode(Left, Op, Right)` | `<` `<=` `>` `>=` `=` `==` `!=` | 条件表达式 |

### §18.3 ★ 批次 ④ 踩到的四个真坑（都已进 `docs/06` §8.14）

**1）中心差分的系统偏差淹没驻点真零。**
朴素中心差分 `D(x, h) = [ f(x+h) − f(x−h) ] / (2h)` 的截断误差是 `h²/6` 乘三阶导数。
在 `x³` 的驻点 `x = 0` 处真导数明明是 0，差分值实测却有 `1e-6` 量级 ——
比“判零阈值”大两个数量级，于是**三阶函数的驻点永远找不到**。
改用**理查森外推**：`D_R = [ 4·D(x, h/2) − D(x, h) ] / 3`，误差降到四阶。

**2）分段断点靠“幅值跳变”永远断不开。**
采样器原本的断开判据是「相邻点 y 差值 > 2 乘以 (yMax − yMin)」。
可 `{x<0: -1, else: 1}` 的跳变只有 2，而典型坐标系幅值差是 10 —— 判据差 5 倍，
结果画出一条**从 −1 匀速爬到 +1 的斜坡**，看着像函数、其实是错的。
修法：`CollectBreakpoints()` 解析求出断点，配 `forceBreak` **强制**在断点处起新 Path。
另有个细节：注入条件必须写 `breaks[k] <= x` 而不是 `<` ——
格点经常正好落在断点上，用 `<` 会让该点先被右侧分支求值。

**3）交点的 Y 必须是真实函数值，不是残差。**
求根是对 `a − b = 0` 做的，解出来的“函数值”恒为 0（残差）。
最初直接用它填 `FeaturePoint.Y`，于是**所有交点都被画到 x 轴上**。
修法：拿到根 x 之后回代原函数 a 取真实 y。

**4）`where` 被词法切成了乘法。**
`x^2 where x>0` 报「无法识别的符号 where」。真因不是语法，是**词法**：
`NeedsImplicitMul` 在 `)` 与标识符之间自动补了乘号，于是 token 流成了 `x^2 * where * ...`。
修法：给 `NeedsImplicitMul` 加关键字排除 —— `IsKeyword(name) => name is "else" or "where" or "if"`。

### §18.4 ★ 一处“圆点在、字没了”的渲染坑（外观类，但极易漏测）

小圆点画出来了，**读数文字整片消失**，且不抛异常。
逐层剖开视觉树，发现文字 `Path` 的 `Data.Bounds` 完全正常（0.9 × 0.32 数学单位）——
几何没问题，问题在**描边**。

原写法是「给文字加一圈白色 `Stroke` 当背景，让字压在曲线上也看得清」。
但 WPF 的描边是**骑在轮廓线上、内外各一半**：
`0.18 × 字号` 的描边单边就有 `0.06` 数学单位，而这个字号下数字的笔画整条才约 `0.08` 宽 ⇒
**白边从两侧把字芯吃光**，屏幕上只剩“看不见的字”。

修法：改用**实心白衬板**（一块 `Rectangle` 垫在读数下面，尺寸取自几何变换后的真实 `Bounds`），
文字只 `Fill` 不 `Stroke`。

> **教训（已进 `docs/06`）**：小字号文字要“看得见地压在曲线上”，靠的是**底色块**，不是**描边**。
> 描边宽度是“单边”语义；底色块是“整体”语义 —— 想当背景就一定用后者。

### §18.5 ★ 补的永久回归网

原断言只数了「椭圆个数」，于是“圆点在、字没了”能**全绿通过**。这是典型的
“断言贴着实现细节、没贴用户感知”。本批补了两组新断言，把感知钉死：

- **批次 ④** `24) 读数标注可见性`：实心填充 `Path` 至少 2（曲线 + 读数）、
  白描边 `Path` 恰好 0（旧写法会大于 0）、白衬板 `Rectangle` 至少 2。
- **批次 ⑤** `16) 绑定穿过存档`：存 `.tbink` → 读回 → `Restore` 进新 store →
  `UpdatePose(sys, ..., 2.0)` ⇒ 断言 `bindTo` 原样还原 **且** 曲线缩放跟到 `unit × 2`。
  补这条是因为原「绑定跟随」断言只走**内存里的 store**，而老师的真实用法是
  「存盘、明天打开、拖坐标轴」—— 存档里漏掉 `bindTo` 的现场表现是

## §19 现场修复：矢量箭头「大小不对」（2026-09-22 用户验收反馈）✅

### §19.1 现象与复现

用户在一体机验收时报：「**矢量箭头大小不对**」。复现条件：把箭头**挂到坐标系上**
（`bindTo` 指向 `coordsystem`），拖一根 2~3 cm 的短箭头 ⇒ 现场看到的是
**一个大三角疙瘩，箭杆几乎看不见**。证据图 `artifacts/_regress/m74s5-正交分解.png`
里那个小箭头配超大三角头就是它。

### §19.2 根因：三角常量是「世界长」，本地几何却是「数学单位」

这是本项目**第三次**踩同一类坑（前两次：线宽、虚线节距），只是这次漏在箭头三角上。

绑定坐标系后，宿主 `RecomputeAttachments()` 对绑定对象一律设
`Scale = unitWorld × 坐标系.Scale`，而**渲染器本地几何按数学单位画**
（`lengthLocal = lengthWorld ÷ unitWorld`）。`ArrowGeometry` 里：

```csharp
public const double HeadLengthWorld   = 11.0;  // ← 世界长常量
public const double HeadHalfWidthWorld = 5.5;  // ← 世界长常量
```

`ArrowVisual` **直接把这两个世界常量塞进了数学坐标系**，于是：

| 量 | 修复前 | 期望 |
|---|---|---|
| 本地箭头总长 | 5.0（数学单位） | 5.0 |
| 本地三角长 | **11.0**（世界常量没除 unit） | 11.0 ÷ 28.35 ≈ 0.388 |
| `shaft = 总长 − 三角长` | 5 − 11 = **−6** ⇒ 被 `MinShaftWorld` 截断到 0.1 | 4.612 |

⇒ 现场表现：**只剩一个 11 单位长的巨大三角，箭杆退化成 0.1 的点**。

**同一个根因还带出第二个缺陷**：`ArrowGeometry.Measure()` 的高度也用世界常量
`HeadHalfWidthWorld`（= 11 全宽）没除 unit ⇒ 绑定态下**命中区包围盒高被抬高 28.35 倍**，
表现成"箭头周围一大片看不见的区域，点旁边的空白也会选中它"。

### §19.3 修法（两处，同一句式）

```csharp
// ArrowRenderer.cs —— ArrowVisual 构造器新增 unitWorld 参数
double safeUnit = unitWorld > 0 && !double.IsNaN(unitWorld) && !double.IsInfinity(unitWorld)
    ? unitWorld : 1.0;
double headLenLocal  = ArrowGeometry.HeadLengthWorld  / safeUnit;   // ★ 关键
double headHalfLocal = ArrowGeometry.HeadHalfWidthWorld / safeUnit; // ★ 关键
_shaft = ArrowGeometry.BuildShaft(lengthLocal, angleDegrees, headLenLocal);
_head  = ArrowGeometry.BuildHead (lengthLocal, angleDegrees, headLenLocal, headHalfLocal);
```

```csharp
// ArrowGeometry.cs —— Measure 加 unitWorld 参数，高度也按本地单位算
public static Size Measure(double lengthLocal, double unitWorld = 1.0)
{
    double safeUnit = unitWorld > 0 ? unitWorld : 1.0;
    double headHalfLocal = HeadHalfWidthWorld / safeUnit;   // ★ 关键
    double minLocal = 1.0 / safeUnit;
    return new Size(Math.Max(lengthLocal, minLocal),
                    Math.Max(headHalfLocal * 2.0, minLocal));
}
```

三处 `Measure(...)` 调用点、两处 `new ArrowVisual(...)` 调用点一并补 `unitWorld: unit`。
**契约零改动**（全是插件内部），宿主不动。

### §19.4 ★ 断言教训：`ArrowVisual` 用 `OnRender` 画，视觉树里没有 `Path`

第一版断言我沿用了别处"递归 `VisualTreeHelper` 找 `Path`"的写法 —— **量出来恒为 0×0**，
因为 `ArrowVisual : FrameworkElement` 是在 `OnRender(DrawingContext)` 里
`DrawGeometry` 直接画的，**没有 `Path` 子元素**。改用**反射读私有字段 `_shaft` / `_head`**
才拿到真几何。教训：**"看起来通用的量法"要先确认它量的对象长什么样**。
