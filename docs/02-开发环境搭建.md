### csproj 关键配置与理由

| 配置 | 值 | 理由 |
|---|---|---|
| `TargetFramework` | `net8.0-windows` | 教室一体机为 Win10/11，.NET 8 可用；单文件自包含发布更方便 |
| `UseWPF` | `true` | 必开 |
| `UseWindowsForms` | **`false`** | 显式关闭。PDF 走离屏渲染，**禁止 `WindowsFormsHost`**（见设计方案 §3.4：WinForms 层不参与 WPF 矩阵变换，必然与笔迹错层） |
| `PlatformTarget` | `x64` | 希沃一体机为 x64；pdfium 原生 DLL 只提供 x64 |
| `RuntimeIdentifier` | `win-x64` | 同上，并让原生 DLL 能正确落到输出目录 |
| `ApplicationManifest` | `app.manifest` | 见下 |

> **不用 `Platforms` 属性**：`<Platforms>x64</Platforms>` 会与解决方案的 "Any CPU" 默认配置映射冲突，制造无谓的构建噪音。单工程方案里只留 `PlatformTarget` 即可。

### DPI 感知为什么在 M0 就要定死

`app.manifest` 中声明：

```xml
<dpiAware>true/pm</dpiAware>
<dpiAwareness>PerMonitorV2</dpiAwareness>
```

整个方案依赖「视口 DIP ↔ 世界 PDF point」的精确换算。若进程未声明 DPI 感知，Windows 会按系统 DPI 对窗口做**位图拉伸**——此时鼠标/触控坐标与渲染坐标之间会多出一层缩放，笔迹与 PDF 底图必然错位，且是那种"看起来差一点点"的隐蔽 bug。
事后补这一条要重测所有坐标逻辑，所以放在 M0 定死。

### 全局异常兜底为什么在 M0 就加

目标机是教室一体机，崩了没有调试器可用。`App.xaml.cs` 做了三件事：
1. UI 线程异常 → 写日志 + 弹提示 + **`e.Handled = true`**（上课中途整个程序退出是最糟的情况，宁可带错继续跑）；
2. 非 UI 线程异常 → 写日志；
3. 日志落盘到 `%LOCALAPPDATA%\MathPhys.Ink\logs\yyyy-MM-dd.log`。

## 5. 本机操作注意事项（踩过的坑）

| 现象 | 处理 |
|---|---|
| bash 工具不可用（`dirname: command not found`） | 一律用 PowerShell 工具 + Read 工具组合 |
| PowerShell 的 stdout 有时不回传 | 把输出**重定向到 `$env:TEMP` 下的文件**，再用 Read 工具读 |
| 命令行含 `csc.exe` / `MSBuild.exe` 字样会被安全拦截 | 探测工具链时绕开这些字符串（用 `Test-Path` + 目录列举） |
| 日志文件出现乱码 | PowerShell 用 `Out-File -Encoding utf8`，读取时同样指定 utf8 |
