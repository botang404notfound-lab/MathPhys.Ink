# M9 导出试卷（PNG / PDF）—— 设计与实施方案

> 目标：把当前打开的试卷（PDF 页面 + 笔迹 + 学科工具图形）导出成
> **PNG 单页**或**PDF 整卷**，让老师能把批注好的卷子带走、打印、发群里。
>
> 插件完全冻结（M9 期间不动 7 个插件、零契约新增）。

## 0. 范围与边界

### 0.1 做什么

- **PNG 单页**：弹选页对话框（默认当前页）→ 存成一张图片
- **PDF 整卷**：一次导出所有页到一份多页 PDF
- 固定 **200 dpi** 一档
- 导出产物 = 屏幕上看到的画面（页面 + 笔迹 + 图形对象）

### 0.2 不做什么

- **不做批注的矢量复刻**：笔迹与图形一律按栅格贴图进 PDF（见 §4.1）
- **不做 DPI 选择**：单档 200 dpi（一体机与打印场景够用；多档意味着多一套 UI 与验收面）
- **不做范围筛选**：PNG 限定单页、PDF 限定整卷，不做"导出第 3~7 页"
- **不做板书回放 / 演示模式**（留给后续里程碑）
- **不做导出取消**：一次导出几秒，不值得为它引入可取消的后台任务体系

### 0.3 与 M8 的关系

`.twb` 工程里的内嵌 PDF 也要能导出（S3 处理）。当前阶段默认走"打开的 PDF 路径"，
即 M7.x 行为；S3 加"内嵌 PDF 解到临时文件再走同一流程"的分支。

## 2. 三个数：world / 像素 / dpi（★ 最容易写错的地方）

world 单位就是 **PDF point（1/72 英寸）**。导出涉及三个不同的量，它们不是一回事，
混用不会崩、只会让产物又糊又裁：

| 量 | 值（200dpi） | 用途 |
|---|---|---|
| `RenderDpi` = 200 | —— | 输出分辨率，算 **world → 像素** |
| `ZoomForDpi(dpi)` = dpi / 96 | ≈ 2.0833 | 喂给 `IPdfDocumentService.RenderPage`（该接口 **zoom=1 ⇒ 96dpi**） |
| `BitmapDpi(dpi)` = 96 × dpi / 72 | ≈ 266.67 | 喂给 `RenderTargetBitmap` 构造参数 |

**像素尺寸**：`像素 = world × dpi / 72`（A4 `595.28×841.89` ⇒ `1654×2339`）。

**`BitmapDpi` 为什么是 96 × 200/72**：`RenderTargetBitmap(pxW, pxH, dpiX, dpiY, fmt)` 的
逻辑尺寸（DIP）= `pxW ÷ dpiX × 96`。我们要它**等于页面 world 尺寸**（视口摆在 `scale=1` 时
1 world 单位 = 1 DIP），于是 `dpiX = (200/72) × 96`。
用 96 会得到 96dpi 的图（糊）；用 200 会让逻辑尺寸缩成 `96/200`，内容放大到超出画面、
**右下角整块被裁掉**。两者都不报错。

**渲染档位**：`RenderLevels` 是离散档（最高 6.0）。200dpi 的 zoom ≈ 2.083 会落到
**3.0 档**（"不小于的最小档"）—— 属于超采样，页面位图比导出所需更清晰，不会欠采样变糊。

全部换算收在 `Export/ExportGeometry.cs` 的纯函数里，与 `CanvasViewport`（world↔视口）并列：
**每层只有一个真值源**。

## 4. 导出算法

### 4.1 一页怎么变成位图

```
① 借画布（ExportSession）：
     · 冻结宿主的渲染需求重算
     · 视口摆成 scale=1，并把**目标页左上角**对齐渲染目标的 (0,0)
② new RenderTargetBitmap(页宽像素, 页高像素, BitmapDpi(), BitmapDpi(), Pbgra32)
③ rtb.Render(WorldHost)          ← 屏幕上那条渲染链，含页位图 + 图形 + 笔迹
④ PngBitmapEncoder → MemoryStream
⑤ 归还画布（还视口 + 解冻）
```

★ 平移量必须是 `-页左上角`，**不是 (0,0)**：排版把页面放在 `(960,960)` 起排
（四周留可写留白，`WorldLayout.DefaultPageMargin`），"世界原点对齐"只有第 1 页碰巧能对上，
**第 2 页起会整页偏出画面** —— 导出成一张白纸。（计划稿里写的是 `SetView(1,0,0)`，此处修正。）

### 4.2 为什么借现成的可视树，而不是另搭一棵离屏树

屏幕上的画面是 `RootGrid → WorldHost → PdfPageLayer + GfxLayer + InkLayer` 这条链算出来的。
离屏重搭 = 把这条链再实现一遍：墨迹粗细、图形对象的渲染器、页位图档位全都要再对一次，
两处一旦不同就是「屏幕上好好的、导出少一层」。借用现成视觉树 ⇒ 导出与屏幕**共享同一份渲染代码**。

### 4.3 ★ 两件必须做的事（否则导出是白纸）

1. **视口快照 / 还原**（`CanvasViewport.Save/Restore`）。
2. **冻结渲染需求重算**（`CanvasViewportHost.BeginRenderFreeze()`）。
   视口一变，宿主就会重算"哪些页要什么档位"，而那次重算会把**视口外**的页
   `Source` 清成 `null` 省内存 —— 1:1 视口看不见的页全在其中。这个清空排在
   `Background` 优先级、平时肉眼看不见（下一帧就补回来），所以不做冻结的症状是
   **"偶尔导出成白纸"**，比稳定失败难查得多。

   冻结用**计数**而非 bool（导出可能嵌套）；释放到 0 时补排一次需求，
   让画面按还原后的视口重算。

## 5. 错误处理矩阵

| 场景 | 行为 |
|---|---|
| 无文档 | 按钮 `IsEnabled=false`（`CanExport`） |
| 选文件对话框取消 | 静默（`ExportResult.UserCancelled`，不弹窗、不报黄字） |
| 磁盘满 / 只读 / 无权限 | 弹窗 + 状态栏黄字 + `AppLog.Warn` |
| PdfSharpCore 内部异常 | 同上 |
| 导出中再点 | 按钮置灰（`IsBusy`）；不实现取消 |
| PNG 过大（>50MB） | 仍落盘；状态栏提示「文件较大：N MB」 |
| `.twb` 加载但 PDF 缺失 | 沿用 M8 的「定位 PDF」对话框，M9 不重复弹 |

**实施中两次自我纠错（都是"代码对、断言错"）**

1. **`BitmapDpi` 的自检点选错**：第一版断言 `BitmapDpi(96) == 96`，实际是 `96×96/72 = 128`。
   实现是对的（`BitmapDpi(dpi) = 96×dpi/72`），自检点应当取 **72 dpi** ——
   那时"1 world 单位 = 1 像素"，逻辑尺寸恰好等于像素数，构造 dpi 必须正好是 96。
2. **★ 观察点选错，被同段的反向对照当场揭穿**：第一版拿**第 2 页**当"借出后看不见的页"，
   结果"冻结生效"绿、"反向对照"红。原因是可见区带 **256 DIP 预渲染余量**
   （`CanvasViewportHost.PrerenderMargin`），1:1 视口下第 2 页仍落在余量里、**压根不会被清**
   ⇒ 那条"冻结生效"是**假通过**。改用**最后一页**（实测可见区 `704,704 1512×1212`，
   第 7 页 `Y=6155..6997`），并补一条**观察点自检**断言 —— 把"这条断言本身有没有意义"
   也变成一条会红的断言。

   这两件事合起来说明反向对照的价值：它不只证明机制存在，还会**当场指出上一条断言测错了对象**。

1. **★★ 真 bug：`RenderTargetBitmap` 是"同步抓帧"，换完 `Source` 必须 `UpdateLayout()`**（否则 7 页里 5 页白纸）。

2. **★ `RenderTargetBitmap` 背景是全透明（alpha=0、RGB=0）⇒ 判"是不是白纸"必须先合成到白底。**

3. **★ 观察点顺序踩了宿主"永不降级"规则 ⇒ "两图一致"变成空断言。**

**★ S3 抓到的两个真缺陷（M8 起就存在）**

1. **临时试卷从来没被删掉过。** 释放出来的临时 PDF 交给 pdfium 打开，而清理排在
