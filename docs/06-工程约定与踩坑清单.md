# 工程约定与踩坑清单

> 从项目记忆 `MEMORY.md` 归档而来（2026-09-20）。这里的每一条都是**实际踩过并付出代价**的，
> 不是理论推演。新增踩坑请追加到对应小节。
> 记忆文件只保留索引，细节看这里。

## 1. 工具链与环境

- **NuGet 还原必须在沙箱外跑一次**：沙箱代理会让 NuGet 报
  `NU1301 Unable to get repository signature information`（PowerShell 走同一代理却是 200）。
  包进全局缓存后 build 即可全离线。
- **`dotnet` 在中文环境输出 GBK**，落盘后读出来是乱码（错误行号能认、描述全废）。
  定死：跑 build/run 一律先 `$env:DOTNET_CLI_UI_LANGUAGE = "en"`。
- **PowerShell 的 `*>` 重定向写出的文件 Read 工具会认作二进制**（编码为 UTF-16/其它）。
  定死写法：`$text = & cmd args 2>&1 | Out-String`，再 `Out-File -Encoding utf8`，
  写入**工作区内**的文本文件（`$env:TEMP` 亦可但更易踩编码）。
- **`Add-Type` 被安全策略拦截**（"compiles and loads .NET code at runtime"）⇒
  不能用 `System.Drawing.Bitmap` 读 PNG。
  替代：**Node 内置 `zlib` 手写最小 PNG 解码**（IHDR + IDAT + 5 种滤波含 Paeth），零依赖、可靠。
- **bash 工具在本机不可用**，用 PowerShell；其 stdout 常不回传，需重定向到文件再读；
  命令行含 `csc.exe` / `MSBuild.exe` 会被安全拦截。
- **每次 build 后必须检查 `$LASTEXITCODE` 再决定是否 run**：否则 `dotnet run --no-build`
  会拿旧 dll 跑出**"假通过"**（踩过）。
- harness 输出中文要 `Console.OutputEncoding = UTF8` **且** PowerShell 侧
  `[Console]::OutputEncoding = UTF8`，否则重定向到文件是乱码。

## 2. 语言 / 框架陷阱

- **WPF `ManipulationDelta.Scale` 是 `Vector` 不是 `double`**（WPF 允许各向异性缩放）
  ⇒ 取 `.X` 分量。踩过一次，编译报 CS1503 / CS0029 才发现。
- **`TabletDeviceType` 只有 `Stylus` / `Touch` 两个值，没有 `Mouse`** ——
  WPF 把鼠标也报成 `Stylus`。
  更要紧的是它**不能用来区分笔和手指**：红外触摸框一体机上，被动笔与手指**同为 `Touch`**
  （M4.2 实测：设备清单里只有一个 `name="HID Interface"` 的 Touch 设备，从无 `Stylus`，
  `inverted` 恒为 false）。靠设备类型区分笔/手指的策略在这类机器上必然失效。
- WPF 项目的隐式 using **不含 `System.IO`**，需要时显式 using。
- 领域层公开 API **不要出现 `System.Drawing` 类型**（`UseWPF` 的隐式 using 已带
  `System.Windows.Media`，会类型歧义）⇒ 统一用 WPF 的 `Size`/`Point`/`Rect`。
- `StylusPointCollection` 属 `System.Windows.Input`，**不属** `System.Windows.Ink`。
- `StylusShape.Width` 是**直径**，与 `DrawingAttributes.Width` 同为"笔尖粗细"语义。
- **中文字符串里写直双引号 `"` 会把 C# 字符串截断**（`CS1003: Syntax error, ',' expected`）。
  典型场景：想表达"用户改了东西"这种带引号的强调，写成
  `$"...不会被当成"用户改了东西"..."` ⇒ 编译器在第二个 `"` 处认为字符串结束。
  解法：中文里一律用 **「」** 或 **""**，不要用 `"`。
- **`Near(double, double)` 这类辅助重载记得给默认容差**：只给 `Near(Point,Point)` 写默认值的话，
  两个 double 的调用点会因缺参编译失败（CS1503）。重载家族要么都带默认值，要么都不带。

## 3. 命名空间与目录

- 目录名**不要叫 `Canvas/`**：命名空间 `MathPhys.Ink.Canvas` 会与 WPF
  `System.Windows.Controls.Canvas` 全面歧义 ⇒ 用 `Viewport/`。
- XAML 里禁用 `StringFormat` 带 `{}`（如 `共 {0} 页`）⇒ 改用 ViewModel 属性。
- 手写 `ObservableObject` + `RelayCommand`，不引 CommunityToolkit.Mvvm。

## 4. 编辑与协作工具

- **同一条消息里对同一文件发多个 Edit 会丢改动**（并行写同一文件，最后写入者赢）。
  **每个 Edit 都返回"成功"，但只有一处真正落地。** 踩过四次：
  ① M3 时 `RunFitWidthChecks` 的定义写进去了、Main 里的调用却没了 ⇒
  跑出来"函数从未被调用"且**毫无报错**；
  ② M6 时对 `CanvasViewportHost.xaml.cs` 发两个 Edit，注释那处生效了、
  `SnapshotStrokes`/`ReplaceStrokes` 那处没了 ⇒ 编译报 CS1061 才发现。
  ③ M7.2.1 对 `MainWindow.xaml.cs` 发两个 Edit：先加"启动模式跟随上次选择"的分支、
  再加 `UpdateWindowModeButton` 与状态写盘。**后者生效、前者被吞掉** ⇒
  程序照样 0 错 0 警，只是行为完全是旧的（每次启动仍强制全屏）——
  差点被我当成"读取逻辑有 bug"去改 `UiStateStore`。
  ④ M9 S0 对 `CanvasViewportHost.xaml.cs` **连发三个** Edit（冻结计数字段 /
  `QueueRenderUpdate` 早退 / `UpdateRenderDemand` 早退）：**只有中间那个落地**，
  字段与第二处早退都被吞 ⇒ 若不复核就是 `CS0103: 名称 "_renderFreezeDepth" 不存在`，
  而且会让人以为是"新加的方法写错了"。**三处只活一处**，可见不是偶发冲突而是后写覆盖先写。
  **规则：同一文件必须逐个 Edit 串行发；跨文件可以并行。**
  **复核动作**（每次都做）：同一文件多轮改动后，用 Python **读字节**逐个确认关键新符号在不在
  —— `Edit` 返回的"成功"不能当证据。
  （③ 的正确诊断路径值得记住：**先怀疑"改动没落地"，再怀疑"逻辑写错了"**。
  一次 `grep -n` 就能分清 —— 后者要读代码、加日志、重跑，成本高一个数量级。）
- **"图上没看见"不等于"图上没有"**：6px 的细线在对话预览的缩略图里会被吃掉，
  夹在密集文字行间更认不出。定死：光栅结论**必须用像素采样确证**（本机用 Node 探针），不靠肉眼。

## 5. 测试 harness（`tools/PdfSmokeTest`）

- **验证不靠肉眼**：harness 不开窗口直接把 PDF 渲染成 PNG 并断言尺寸换算 / 排版 / 视口往返 /
  锚点缩放。后续里程碑继续往里加断言，作为回归套件。
- 它**引用了生产工程**（`ProjectReference` + `UseWPF`），所以能实例化真实的
  `CanvasViewportHost` 控件树并对其做 `TransformToAncestor` / `RenderTargetBitmap` 断言
  —— 比镜像一份逻辑可靠得多。
- **无窗口跑真实控件树的关键**：`new CanvasViewportHost()` + 手动 `Measure`/`Arrange`/`UpdateLayout`；
  BAML 靠 `"/MathPhys.Ink;component/..."` 相对 pack URI 加载，**不需要 `Application`**；
  visual 树用 `VisualTreeHelper` 递归枚举。
- **端到端光栅断言法（杀手锏）**：`RenderTargetBitmap` 渲染整棵树 → 扫像素。
  笔迹用品红（`R>140 && B>140 && G<110`，试卷上不可能出现该色）识别，质心按像素中心 `(x+0.5)` 累计；
  纸面用白（`>240`）取外接框。**一次比对完渲染 / 布局 / 变换 / 笔迹四层。**
- **harness 里画笔迹一律用「页矩形 + 偏移」算绝对世界坐标，禁止写死裸坐标** ——
  页面从 `(PageMargin, PageMargin) = (960, 960)` 起排，所以 `new Point(200, 300)`
  **不在纸上，而在页面左上方的页外留白里**；按宽度适配后它根本不在屏幕上，
  扫出来是"0 个像素"，看起来像"笔迹根本没画上去"。
  踩过两次：M3 的裸偏移断言（留白 96→960 时整页被推出视口、三条断言一起**静默挂掉**）、
  M6 的端到端光栅（`y=300` 落在页外 ⇒ 0 像素）。
  **正确写法**：`var page0 = host.Layout.PageRects[0];` 然后
  `new Point(page0.X + 60, page0.Y + 300)`。
- **"白纸外接框"类定位断言在白色底色下会变成恒真**（期望值也 = 整个视口）⇒
  必须用**黑底对照**跑：harness 里临时 `host.CanvasBackground = Brushes.Black`，
  断言完立即切回 `White`。黑底只是验证手段，不是生产默认。
- **反向断言要选"与缩放无关"的量**：M3.6 想证明"页面内容没被涂白"，一开始卡"深色像素 > 5000"，
  `scale=0.5` 下笔画被抗锯齿拉成中灰只剩 2264。改用"页面内非白像素 > 1000"才与缩放解耦。
- **证明"某类区域全为 X 色"要用全图扫描，不用抽点采样** ——
  采样只能证明"我挑的那几个点是白的"。扫描时对相邻元素的抗锯齿溢出留约 4px 豁免
  （如页矩形 0.6 world 单位描边）。
- **断言不了的东西要诚实标注**：M4 的擦除动作本身无法自动断言
  （`StylusEventArgs` 构造不出来、本机无笔）⇒ 只断言配置与策略，端到端靠一体机清单。
- **ISF 不是位精确格式 ⇒ 往返断言不能用 1e-6**（M6 实测）：
  存入首点 `(100,120)`、笔宽 `4.0`，读回是 `(100.00629921259842,120)`、笔宽 `3.9999874017370027`。
  ISF 内部按量化的物理单位存储，往返必然带来约 **0.006 world 单位**的误差。
  两条推论：
  - 位置容差取 **0.05 world**、笔宽容差取 **0.01 world**（比格式精度宽松，又远小于可见差异）；
  - **光栅断言也不能要求像素数严格相等**（实测 10708 → 10707，一个抗锯齿边缘像素翻边）
    ⇒ 用 **1% 相对容差**：既能抓住真问题（笔迹丢了/位置错了都是量级差异），
    又不会被一个边缘像素绊倒。
  另外这条经验可推广：**当断言比被测格式本身更严时，是断言错了，不是代码错了。**
- **"已知取舍"要写成一条显式断言，而不是假装它不存在**：
  M6 的内容指纹只取首尾各 1 MiB。样本 4.47 MiB ⇒ 只改中间字节时指纹**不变**。
  与其在文档里含糊其辞，不如在 harness 里直接断言"改中间字节时指纹不变"，
  并注明这是部分哈希的代价 —— 这样日后没人会误以为它是密码学哈希。
- **断言"某个副作用发生了"之前，先确认触发条件真的被满足**（M7.1 踩）：
  M7.1 里我想断言"切换工具时宿主清空预览"，而按 `ITool` 的设计，
  **重复切到同一个工具是 no-op**（用户点已选中的按钮不该重置工具状态），
  自然也就不会清预览。可我在上一节末尾顺手切回了「笔」，
  下一节的"切走"于是变成 no-op ⇒ 两条断言一起挂
  （Deactivate 计数、预览数）。**看起来像代码坏了，其实是测试自己把前提吃掉了。**
  症状特征：打印出来的中间量（如"Deactivate 次数=1"）与断言里那个变量不是同一时刻的值。
  顺带：这条 no-op 语义本身值得单独断言 —— 它保护的是"拖着直尺时被重复点按钮不会断"。

### 5.1 本机 UI 验证（点按钮 / 截图）—— M7.2.1 新立

一体机上没有调试器，所以"某个按钮点了到底有没有用"必须在本机先验证掉。结论与手法：

- **沙箱禁止 `Add-Type`，也禁止 `[Reflection.Assembly]::LoadWithPartialName()`**（被判定为
  "运行时编译/加载 .NET 代码"）⇒ **UI Automation 这条路走不通**，别在上面耗时间。
- 可行路径：**Python（ctypes + Pillow）**，不走 .NET：
  `user32.GetWindowRect / SetForegroundWindow / SetCursorPos / mouse_event` 模拟点击，
  `PIL.ImageGrab.grab()` 截图，脚本放 `artifacts/`（见 `click_winmode.py`、`shot_winmode.py`）。
- ★ **必须先 `user32.SetProcessDPIAware()`**（本机 150% 缩放）：
  否则 Pillow 截到的是**物理像素**（2560×1440），而 `SetCursorPos` 收的是**虚拟化坐标**（1707×960），
  坐标一混，点击落到屏幕外 —— 表现是"点了没反应"，
  **会让你去怀疑产品代码，而产品是好的**。这一条花了两个来回才定位。
- **别硬编码按钮坐标**：用像素扫描（从右往左找第一块亮度 > 120、宽度 > 40 的浅色区段）
  取几何中心。窗口尺寸/DPI 一变，硬编码坐标就点空。
- **断言认"产品自己写的日志"，不认窗口矩形**：跨 DPI / DWM 外扩下 `GetWindowRect` 的数字
  （最大化时是 `(-11,-11,2582,1402)`）解释起来很绕；
  "模式切换记录行数 +1"是一句话的硬证据。为此 `EnterFullScreen`/`ExitFullScreen` 各记一行日志。
- **别让 harness 碰真实用户数据**：状态文件（`ui-state.txt`）的读写测试不能被"顺手写进
  `%LOCALAPPDATA%`"——那会把老师"上次是窗口模式"的选择重置掉。
  `UiStateStore.ReadFullScreen/WriteFullScreen` 因此开了一个**只给 harness 用**的路径覆盖参数。
- **不是所有东西都该进 harness**：窗口模式这条链路拆成两半 ——
  状态文件（纯逻辑）进 harness 断言；"点按钮真的会切窗口"（要桌面环境）用 Python 脚本验证。
  把窗口塞进 harness 会让回归套件依赖桌面，早晚在没人盯着的地方挂掉。
- **要落墨，先得有打开的文档**（M7.3 踩到）：`CanInteract()` 的定义是
  `_document is not null && _document.IsOpen`。所以本机脚本里凡是"拖一条线看看"的动作，
  前面都必须先真的把试卷打开 —— 否则拖了毫无反应，日志里连一条输入记录都没有，
  极容易误判成"工具没接到指针"，然后去改本来是对的产品代码。
  打开方式：`Ctrl+O` → 剪贴板 + `Ctrl+V` → 回车。
  **中文路径没法用 `keybd_event` 逐字敲**（要处理 shift、IME、非 ASCII），
  把文件先复制到一个纯 ASCII 路径、再用 `Set-Clipboard` 送进去是最省事的绕法。
- **定位功能优先用键盘快捷键，不要用像素找按钮**：按钮位置会随工具栏内容变化 ——
  这次多了「直尺 / 直尺·自由角」两颗，原来"屏幕最右那颗浅色块"的定位逻辑当场失效。
  工具都有单键快捷键（1/2/3/4/5），`keybd_event` 发一个 VK 就完事，不受布局影响。
- **PowerShell 会话的 stdout 有时会整个丢失**（连最后那句 `"done"` 都不打印），
  但**写文件始终可靠** ⇒ 脚本一律 `Out-File` 之后再 `Read` 那个文件，
  不要靠 stdout 判断"这条命令到底跑了没有"。harness/打包类命令尤其如此：
  曾经因为"看起来没输出"而重复跑了一遍发布。

## 6. 运行时 / 线程

- 给 `PdfiumDocumentService` 的所有公开方法加锁 ⇒ UI 线程与渲染线程互斥 ⇒
  换文档时**无需**阻塞等待渲染线程退出。
- 后台渲染线程记日志走 `Infrastructure/AppLog`
  （它不能弹窗，也不能把异常抛给 UI 线程）。
- `PdfDocument` 非线程安全且需显式 Dispose（否则漏 GDI 句柄）。
- 手势数学（`ViewportGestureRouter`）**不能引用 UI 元素** ——
  本机没触摸屏，只有把它做成可构造的纯逻辑，捏合的正确性才能被 harness 断言。

## 7. 自包含发布与交付测试包

用户已明确要求：**凡需要测试，一律打包好再交付**（不是丢几个文件过去）。
定式：

```
1) dotnet publish <主工程> -c Release -r win-x64 --self-contained true -o dist/tablet
   · 首次会下载 runtime pack（~120MB）⇒ **必须沙箱外**，沙箱内 NuGet 会 60s 超时反复重试
   · 包齐之后加 `--no-restore` ⇒ 沙箱内也能秒过（实测 3 秒）
2) 本机启动验证：**用 Python 跑**（见下面那条禁令），进程存活 + 日志关键行即算通过
3) Compress-Archive -Path "dist/tablet/*" -DestinationPath dist/<新名>.zip
4) **压缩后必须做两项校验**：①结果是「文件」；②dist 下**没有**同名的目录残留
5) 同步更新包内的「怎么测试.txt」清单
```

- ★ **不要用 PowerShell 的 `Start-Process` 启动 exe**（M7.2.1 实测）：工具规则明确不鼓励
  用 PowerShell 启动 GUI/分离进程，**整条命令会被判失败（Exit 1、无 stdout、连日志都不写）**。
  更坑的是它可能"执行了一半"：我因此**丢过一次刚压好的 77 MB zip**（失败发生在
  `Compress-Archive -Force` 之前那一步，`-Force` 已经把旧 zip 删了）。
  ⇒ 冒烟启动改用 `artifacts/smoke_publish.py`（`subprocess.Popen` + 读日志 + `terminate`），
  顺便还能截图。**结论：冒烟/截图这类"要动桌面会话"的活都交给 Python 脚本。**
- ★ **一条命令只干一件事**（同上的教训）：`publish + 拷插件 + 归档 + 压缩 + 启动冒烟`
  写在一起时，任何一步失败都会让整条中止，**留下一个"看起来做过一半"的 dist**。
  分步跑，并且**每步把结果写进 artifacts 的证据文件**——失败时才有东西可看。
- **`Compress-Archive` 加 `-ErrorAction Stop` 并用 try/catch 记下失败原因**：
  它的失败模式是"先把目标 zip 删掉、再压缩失败"，于是目标文件**凭空消失**，
  如果不捕获，你只会看到"上次明明打好了、这次没了"。
- **`Compress-Archive` 的 `-Path` 用「目录\*」，并且压缩后一定要校验产物形态。**
  > 这条结论**修正过一次**，记下两次的实测事实，免得再来回摇摆：
  > - `-Path "dist/tablet/*"` ⇒ 产出单个 zip 文件（实测 77.1 MB / 470 个文件），**无残留**。✔
  > - `-Path "dist/tablet"`（目录本身）⇒ 除了 zip，**还会在 dist 下留下一个同名目录**
  >   （`dist/白板M5一体机测试包/tablet/…`，470 个文件、约 188 MB）。
  >   当时只看到 zip 就以为成功了，那个大目录一直躺着没被发现，直到 M6 打包时清理才暴露。
  >
  > 教训比命令更重要：**压缩这类"会顺手产生一堆东西"的操作，不能只看目标文件在不在，
  > 还要看它周围有没有多出东西。** 所以流程里加了第 4 步的两项校验。
  >
  > 第三次踩（M4.2）：清理时**只删了当时那一个名字**（`白板M5一体机测试包`），
  > 而 `白板M6一体机测试包` 那个目录（470 文件 / 179.7 MB，创建于前一天 23:47）
  > 一直躺在 dist 里，直到下一轮打包才被翻出来。
  > **规则：清理残留要按「白板*测试包」这个前缀整片扫，不要只查当前那一个名字。**
- **`Compress-Archive` 前先 `$ProgressPreference = 'SilentlyContinue'`** ——
  否则进度条会把命令输出刷屏几万行（实测把返回内容整个冲掉）。
- **目标 zip 用一个新名字**，不要复用上次的名字（旧文件可能存在/被占用，导致静默失败）。
- **安全策略会拦截「`Add-Type` + `Remove-Item -Recurse -Force`」出现在同一条命令里**
  （提示 "compiles and loads .NET code at runtime / may recursively force-remove files"）。
  拆成两条：先只做删除，再单独跑压缩。
- **PowerShell 对象模型可能骗人**：判断某个路径到底是文件还是目录，用
  `[System.IO.File]::Exists()` / `[System.IO.Directory]::Exists()`，
  不要靠 `Get-ChildItem` 的 `PSIsContainer`（zip 出现在 shell 里时容易看错）。

## 8. 工具系统与插件（M7）

- **插件契约必须单独成一个类库**（`MathPhys.Ink.Plugin.Abstractions`），
  宿主与**所有**插件都引用同一份。理由不是洁癖：插件用 `AssemblyLoadContext` 单独加载，
  若它自带一份契约副本，运行时就会存在两个同名不同类型的 `IWhiteBoardPlugin`，
  `as` 转换**静默返回 null** ⇒ 现象是"插件 dll 明明在，一个工具都没注册，还不报错"。
  加载器里要显式让契约走默认上下文共享（M7.2）。
- **契约里不要放会变的实现类型**：`ITool` 用自定义的 `ToolInkMode` 而不是 WPF 的
  `InkCanvasEditingMode`。一旦绑死，M4.1 预留的 `WM_POINTER` 路线（`docs/05` §2.6）
  就得改所有插件。翻译责任放宿主（`CanvasViewportHost.MapInkMode`）。
- **契约表达的是"意图"，宿主保证兑现**：工具只说"我要提交这些笔画"（`CommitStrokes`）、
  "我要放个临时预览"（`AddPreview`），由宿主保证入撤销栈（事务包裹）、保证清预览
  （切工具时宿主**主动清**，不指望插件自己在 `Deactivate` 里记得）。
  `IToolContext` 里**没有**改视口 / 开关文档 / 清空历史的 API —— 插件不该有这些权力。
- **工具的生命周期有两个容易漏的点**：
  ①拖动中被切走也必须 `Deactivate`（否则内部状态残留，表现为"线从莫名其妙的地方开始"）；
  ②重复切到同一个工具是 **no-op**（保护拖动中的状态不被重置），
  所以"清预览"只在**真的换了工具**时发生。
- **`AddTool` 必须在界面生成按钮之前调用**（M7.2 的加载顺序约束）：
  顺序反了会表现为"插件工具能按快捷键切到、却没有按钮"，看起来像插件没加载成功。

### 8.1 插件加载（M7.2）

- **版本判定不能用 `PluginApi.Version` 常量**：`const` 在编译期被**内联**进插件自己的 IL，
  运行时反射**读不到**"插件编译时用的是哪一版契约"。
  要用 `assembly.GetReferencedAssemblies()` 里对契约的引用版本 —— 那是元数据，可靠。
- **契约 dll 没有强名称 ⇒ .NET 按简单名绑定 ⇒ 版本不匹配既不会崩、也不会报错。**
  "插件引用 v2、宿主只有 v1"会被**静默**解析成 v1 交出去。这种"能加载但行为诡异"最难查，
  所以必须自己显式检查并拒绝，且理由要能直接念给用户听（`插件针对契约 v2，本程序是 v1`）。
- **`AssemblyLoadContext.Load` 里，契约与宿主程序集必须在最前面显式排除**
  （返回 `null` ⇒ 交给默认上下文）。不能省，也不能挪到后面：
  插件目录里带一份契约副本是**最常见的分发方式**，一旦被采用就回到
  "dll 明明在、工具没注册、还不报错"。
- **类库项目不生成 `.deps.json`** ⇒ `AssemblyDependencyResolver` 基本是空壳。
  依赖解析要"resolver 优先 + 插件目录同名 dll 回落"，
  否则"插件把自己和依赖一起拷过来"时依赖全解析不到。resolver 构造失败要降级，不要报错。
- **一个插件类炸了不该拖垮同 dll 里的另一个**：按类型逐个 try/catch。
  并且"注册了 0 个工具"要记 `Failed` 而不是 `Loaded` ——
  报告写着成功、用户却找不到按钮，比直接报错更让人上火。
- **`Assembly.GetTypes()` 会整体抛异常**（一个坏类型就能炸掉整个调用）。
  改用 `ReflectionTypeLoadException.Types`（里面是"加载成功的那些类型"）继续，
  并把 `LoaderExceptions` 的前几条写进日志。
- **测试必须用真 dll**：手工 `new` 一个工具塞进注册表等于什么都没验证。
  harness 里专门建了 `tools/PdfSmokeTest.Plugin`，其中**故意放了一个"注册即抛异常"的插件类**
  —— 一条断言同时证明"异常被隔离"和"同 dll 的另一个插件类不受影响"。

### 8.2 交付包校验（M7.2 顺带发现）

- **不要用 PowerShell 的 `-contains` 比 zip 里的中文条目名**：
  实测把 `怎么测试.txt`、`plugins\说明.txt` 判成"缺"，其实是编码不匹配的**假阴性**。
  用 Python `zipfile.namelist()` 复核最省事。
- **`Add-Type` 会被沙箱安全策略拦住**（"compiles and loads .NET code at runtime"），
  所以别用 `Add-Type -AssemblyName System.IO.Compression.FileSystem` 去读 zip。
- **别在一条命令里同时删目录和压缩**：安全策略对
  "`Add-Type` + `Remove-Item -Recurse -Force` 同现"敏感，会把整条命令否掉
  （表现为 `Exit Code: 1`、stdout 空、后续步骤一个都没跑）。拆开执行。
- **旧测试包与用户解压出来的同名目录不要顺手删**：`dist` 里出现 `白板M7.1测试包` 目录
  很可能是使用者已经解压的那一份（他在用它测试）。清理只针对**本次压缩可能产生的同名残留**，
  按前缀扫出历史残留时也要先看一眼创建时间与内容，别把人家解压的那份删了。

### 8.3 画图元的工具（M7.3 直尺）

- **角度吸附的容差必须小于半步宽**：粒度 15° ⇒ 半步 7.5°，容差取 5°。
  容差 ≥ 7.5° 时**任意**角度都在某个倍数的容差内，那不是吸附而是"强制量化"。
  harness 里有一条 `容差 × 2 < 粒度` 的不等式断言守着这个意图（细节见 `docs/10` §12.2）。
- **轴角有方向歧义，重建终点时要按点积判号**：`178°` 与 `0°` 是同一条轴，
  但把往左拖的 178° 直接按 0° 重建，线会**翻到右边**去。
  取"与原始向量同向的那个解"（`dot < 0` 就把向量取反），不要用"角度是否同号"之类的小聪明。
- **世界坐标层里的固定字号要挂 `LayoutTransform = ScaleTransform(1/Scale)`**：
  预览层在 `WorldHost` 内部就是世界坐标层，直接放 `TextBlock` 会随缩放一起糊掉；
  挂上反向缩放后，**位置**仍跟世界坐标走、**字号**在屏幕上恒定。
- **预览图元一律 `IsHitTestVisible = false`**：它们挂在墨迹层上面，
  一旦参与命中测试，用户就会"看着笔尖在纸上，却写不出字"。
- **抬笔与切工具时都要 `ClearPreview`**，两边都做不是重复劳动：
  宿主清的是"画布上的残留图元"，工具自己复位的是"私有拖动状态"（上一次的起点）。
  少任何一边，下一次拖动都会从莫名其妙的地方开始。
- **误触要显式判掉**：`按下 → 抬起` 距离 < 2 world（≈0.07 cm）就不落墨。
  没有这一条，老师每次想切工具在卷面上点一下，卷面就会被小墨点慢慢铺满。
- **长度单位换算只用一处常量**：世界坐标 = 1/72 inch。
  `A4 宽 595 world ⇒ 20.99 cm` 是一条很好的自检断言 —— 量不对，说明整条链上哪儿错了。

### 8.4 画"对象"的工具（M7.4 量角器）

- **`Stretch=None` 的 `Path` 不把负坐标几何平移到非负区：元素原点就是几何原点。**
  摆一个"以圆心为原点"的盘面（几何范围 `[−R,R]×[−R,0]`）时，`Canvas.Left/Top` 要给
  **圆心本身**；给成 `圆心 + 几何包围盒左上角`（"元素左上角 = 包围盒左上角"的直觉）会整体偏
  **一条半径**（默认 110 world ≈ 3.9 cm）。它不报错、不写日志，只是拖动时盘面飘在笔尖左上方 ——
  属于"盯着笔尖看才发现"的那一类。harness 用"纯蓝填充 + 逐像素外接框比圆心±R"钉住了
  （`RunM74S1Checks` 第 8 段，`m74s1-预览摆位.png`）。
  补充事实：`Canvas` 默认不裁剪子元素，所以偏出去的几何照样画得出来，不会缺一块来提醒你。
- **"调用顺序陷阱"：凡是会读私有字段的方法，都要能在 `Reset()` 之后的那条路径上工作。**
  量角器 `Commit` 先读局部变量、再 `Reset()`；而 `ResolveOrientation` 当初读的是 `_center` 字段 ⇒
  抬笔时拿着 `(0,0)` 去问"圆心附近有什么线" ⇒ **吸附静默失效**——屏幕上没有任何异常，
  而"自动对齐"恰恰是这把工具唯一的存在理由。
  解法不是"记得先调用"，而是**不共享可变状态**：需要什么就从参数拿
  （`ResolveOrientation` / `ResolveCenter` 都改成 `static` + 显式传 `center`）。
- **"挤不挤"这类视觉判断必须量化成断言，不能靠眼睛。** 双圈共 38 个数字，两两之间的**净缝**要
  ≥ 2% 半径（实测最紧的一处是 `30`(0.860R) 与 `150`(0.745R)，3.43 world）。
  只断言"矩形不相交"不够 —— 1 px 的缝在屏幕上看就是挨在一起；字号往下调一档就会滑回"糊成一团"，
  断言是唯一防线。为了能量，把排布从绘制代码里**抽成可查询的 `LayoutLabels()`**（返回每个数字的
  `Bounds`），绘制改为消费它 —— 同一份数据既画又测。
- **`CanvasBackground` 是"纸面"底色，不是视口底衬。** 空宿主（无文档）改它对画面毫无影响。
  光栅断言的判据不要建立在"底衬是什么颜色"上，要**按颜色认墨**：谁画的用什么颜色，就只认那个颜色
  （量角器的光栅段只数"红像素"，因为那个对象是用 `#FFFF0000` 落的；
  按"非白即墨"数会把整块底衬算成墨，外接框立刻撑满画布）。
- **一个对象 = 一个视觉元素。** 181 条刻度 + 38 个数字合成一个自绘 `FrameworkElement`
  （`OnRender` 里三次 `DrawGeometry`），不做 220 个 `Path`：拖动时 WPF 要逐个算变换与命中，
  一体机上"拖不动"当场就能感觉到。顺带绕开 `Shape.Stretch=None` 把几何平移到元素原点、
  于是"几何坐标"与"画在哪"变成两件事的坑（那是"看着在这、点着不在"的温床）。
- **半圆盘的对象包围盒声明成 2R×2R 正方形（原点 = 圆心，盘面只占上半边）。**
  代价：选中框比盘面高一倍、基线下方那块空白也能按住（一体机手指粗，反倒好按）；
  收益：**绕原点旋转 = 绕圆心旋转**（量角器的核心用法）。
  日后若嫌框松，正确解法是给对象层加"非中心包围盒"，不是在这个插件里打补丁。

**对象层四条不变量**（M7.4 立，改对象层代码前先确认没破坏）

1. **位姿只有一个矩阵来源** `GfxTransform.MatrixOf`；渲染与命中测试都必须用它，
   任何地方自己再乘一遍变换就是"看着在这、点着不在"的起点。
2. **`GfxLayer` 与其内所有元素 `IsHitTestVisible = false`**；命中由 `GfxObjectStore` 自己算
   （世界坐标几何运算）。理由有三条，都很硬：不让图形抢输入（M7.3 的教训）、
   手柄命中半径要按**屏幕**像素算（WPF 命中测试给不了这个语义）、自算的命中测试能脱离渲染在 harness 里断言。
3. **拖动 / 旋转 / 缩放只改矩阵**；只有**参数**变化才重建几何。
   181 条刻度 + 38 个数字只建一次视觉元素，拖动时改的是矩阵而不是重画。
4. **对象参数只存「世界坐标 + 无量纲参数」**，绝不存屏幕像素 —— 与笔迹同源，缩放/换机不漂移。
   量角器的半径存成 `Numbers["radius"]`（而不是 `Scale`）：`Scale` 是"老师整体放大"，
   `radius` 是"多大的量角器"，两件事混在一起，日后做参数面板就没法区分了。

### 8.5 画"对象"的工具（M7.4 Step 3 坐标系 新坑）

1. **对象层渲染器画的是世界长度，不是数学坐标。** 量角器/三角板的"半径/边长"本身就是世界长度，没踩过这个坑；
   坐标系的"网格 / 轴 / 标签"按数学坐标 `[-10, 10]` 画，几何比 `Measure` 返回的 `2W × 2H` 容器小 `2 × unitWorld` 倍 ——
   `Measure = 1600×1600` 但内容只有 `20×20`，光栅只看到原点附近一团（`m74s3-坐标系.png` 第一版）。
   **经验**：先看 `Measure` 算什么，再看几何画的"世界长"还是"参数值"；坐标系/网格类的工具必须
   `BuildGrid/BuildAxes/BuildLabels` 全都乘 `unitWorld`。
2. **`Geometry.Freeze()` 后再写属性抛 `InvalidOperationException`**（"它处于只读状态"）。
   标签 `BuildGeometry` 返回的 `Geometry` 被我先 `Freeze()` 再设 `Transform = TranslateTransform` ——
   WPF 抛异常。**顺序必须是：先设属性再 Freeze()**。让 `MakeText` 把 transform 作为参数传进来，不要事后赋值。
3. **`PageSnapCandidates` 要按"按下点 x/y"算**，不能是固定的 9 个点。第一版我给的是"页角 + 页边中点"那 9 个固定点 ——
   按下点 (120, 10) 想吸上页边，候选只有 (0,0) / (595,0) / (297.5,0)，离 (120, 10) 都太远。
   **改成"按 `world.x/world.y` 算"**：4 条页边的候选 = (world.x, page.Y) / (world.x, page.Bottom) /
   (page.X, world.y) / (page.Right, world.y)。这样 (120, 10) ⇒ (120, 0)，自然吸上。
4. **`IToolContext.PageRects` 在 Step 1 时就已经预留**（契约 v1.1），注释原话"工具据此做吸页、贴边、跨页判断" ———
   坐标系是它的第一个真使用者。**这次开工前我花时间"评估要不要扩接口"，纯属多虑** —— 接口早就有了。
   看代码先问"这个能力是不是已经在接口里"，再决定加新接口。
5. **harness 的真宿主测试要手动 `Layout.Rebuild(pageSizes)` 注入页框**：宿主 `CanvasViewportHost` 默认
   `Layout.PageRects` 是空（没打开 PDF 就不调 Rebuild）。坐标系工具要拿页框吸页中心，不注入就退化自由摆放。
   量角器/三角板不读 PageRects 所以没踩到。

### 8.6 画"对象"的工具（M7.4 Step 4 函数图像 新坑）

1. **新建插件工程别漏 `<ImplicitUsings>enable</ImplicitUsings>`**。契约/Ruler/CoordSystem 等老工程"恰好没用到" `Exception`/`Func<>`/`List<>`/`IReadOnlyList<>`/`UniformGrid`，
   缺了也能过；一旦用了这些 BCL 类型就炸成 5 个 CS0246。新插件工程统一显式加 `ImplicitUsings`，
   并对 `UniformGrid`→`System.Windows.Controls.Primitives`、`Path`→`System.Windows.Shapes` 补 `using`（WPF 全局 using 不一定覆盖这两）。
2. **隐式乘法的词法补全：函数名后跟 `(` 是调用，不是乘法。** 第一版 `NeedsImplicitMul` 把 `Name + LParen` 也补了 `*`，
   结果 `sin(x)` 被切成 `sin * (x)` → 解析器误报"函数后面要跟括号"。**铁律**：左为 Name、右为 LParen 时**绝不补乘号**；
   只有 `Number + LParen`（`2(x+1)`）和 `RParen + LParen`（`(x+1)(x-1)`）才插 `*`。
3. **浮点 `1/0` 是 `+Infinity` 不是 `NaN`**（`0/0` 才是 NaN）。断言"除以 0 应 NaN"会误判失败 —— 求值是**对的**，要改的是预期值用 `IsInfinity`。
   写断言前先想清 IEEE 754 语义，别把"不抛"当成"返回 NaN"。
4. **端到端渲染 harness 必须把两个对象的渲染器都 `RegisterGfxRenderer`**：check 10 只注册了函数渲染器，坐标系没注册 → 红色只渲染了 43 像素（占位/未渲染）。
   同时端到端对齐断言要对**视口变换不敏感**：用 `Viewport.ToViewport(world)` 取原点真实屏幕位置，再断言"曲线过原点 + 水平居中"，
   别用写死的屏幕坐标（宿主默认视口带缩放/翻转，写死坐标必误判）。

### 8.7 现场实测两个 bug（S4 包后，一体机反馈）

1. **函数图输入窗解析异常没接住 → 弹窗崩**。第一版 `FunctionInputWindow.TryParse` 写成
   `ast = ExpressionParser.Parse(_expr.Text); return true;`——**永远 return true 且从不 catch**。
   用户在弹窗里拼到一半的表达式（如刚按了 `(` 的 `sin(`、或多敲一个 `)`）就让 `ParseException`
   一路冒泡成 `DispatcherUnhandledException`，窗直接崩、日志里 5 条报错。
   **修法**：`TryParse` 内 `try { ast = Parse(...); 清红字 } catch (ParseException ex) { ast = null!; 显示"表达式有误："+ex.Message; 返回 false }`；
   调用方（RebuildParams / RefreshPreview / Confirm）按 false 跳过重建/预览、不再崩。
   **铁律**：任何"边输入边解析"的 UI，解析失败必须就地消化成提示，绝不能抛到 Dispatcher 层。
2. **坐标系箭头画在原点、不在轴末端**。第一版 `BuildAxisArrows(arrowSizeLocal)` 把箭头三角形顶点落在
   `(s,0)`（X）与 `(0,-s)`（Y），s≈0.35×unitWorld，也就是原点附近 10 个世界单位 —— 而轴延伸到 ±283 世界单位，
   于是原点处冒出一对不该有的小箭头。正确位置在轴正方向**末端**（xMax·unit, 0）/(0, FlipY(yMax)·unit)。
   **修法**：`BuildAxisArrows` 加 `xMax/yMax/unitWorld` 三个参数，箭头整体平移到轴末端、尖端朝轴外；
   同步改渲染器调用点与 smoke-test 调用（旧签名 1 参 → 新签名 4 参，否则 CS7036）。
   **铁律**：几何"以原点为中心画"≠"装饰元素都堆在原点"；轴箭头、标签这类定位于轴端的元素，坐标必须显式算到末端。

### 8.8 工具会「静默失手」：Edit 报成功但目标内容没变（2026-09-21）

`Edit` 工具偶发返回 `Successfully edited: <path>` 而**目标内容根本没落盘**。本轮给函数窗接虚拟键盘时，
"窗 `600×480` → `940×720`"与"把 `_vk.Build()` 嵌进 Grid"两处 Edit 都报成功、实际未改；
偏偏同一批编辑里的 `Append` → `InsertText` 那处**真的生效了**（且 `VirtualKeyboard` 类本身存在、`InsertText` 引用了它的 token 常量），
于是**编译照过、回归照过** ⇒ 极易把"键盘根本没接上"当成"做完了"（本轮就是这么差点交付了个假功能）。
更早的 `Row` 去 `static` 也连失手两次（读回仍是 `static`）。

**铁律**：任何**结构性改动**（改字段声明 / 改布局树 / 往可视化树加元素 / 改方法签名）之后，
**必须用 Python 读源文件字节、逐条断言关键行在场**，不要相信编辑器或工具的"已修改"回执；
`Read` / `Grep` 已多次观测到返回**旧内容**，三者要交叉验证。典型断言（本轮用到的）：
`Width = 940; Height = 720;`、`private readonly VirtualKeyboard _vk;`、`new VirtualKeyboard();`、
`_vk.KeyPressed += InsertText;`、`grid.Children.Add(keyboard);` 各恰好出现 1 次；
**DLL 层面的最终证据**：把新构建产物与包内文件做 SHA-256 比对 + 断言关键 token 常量（UTF-16LE）在 dll 里。

### 8.9 函数图像「点了没反应」：UI 构建路径没被 harness 覆盖（2026-09-21 现场反馈）

**现象**：一体机点「函数图像」（键 0）后，在卷面上单击**毫无反应**，弹窗根本不出现。日志：
`[WARN] 工具调用失败（function.OnPointer）：IndexOutOfRangeException Index was outside the bounds of the array.`（连 8 条）。

**根因**：`FunctionTool.OnPointer`（Up 且位移达标）→ `ShowInputDialog` → `new FunctionInputWindow(...)`，
**异常就出在弹窗构造函数里**（宿主把整段 `OnPointer` 包在 try/catch，所以报成"OnPointer 失败"）。
罪魁是 `VirtualKeyboard.Numpad()`：把键位写成 `K[][] layout`，**最后一行只有 3 个键**（`0` 跨 2 列、`.`、`+`），
但遍历写成了硬编码 `for (r<4) for (c<4)` ⇒ `layout[3][3]` 越界抛 `IndexOutOfRangeException`。
**修法**：按每行实际长度遍历 —— `for (r < layout.Length) for (c < layout[r].Length)`。

**为什么漏掉了（更重要的教训）**：Step 4 的 harness 只调 `tool.ApplySpec(spec, anchor)`（数据路径：绑定/孤立/滑块），
**从来没把输入 UI 建出来**（既不 `Build()` 键盘、也不构造弹窗），于是"构造函数抛异常"这条路径完全没被覆盖 ——
而它恰恰是用户唯一的入口 ⇒ **"点了没反应"**。已补第 11 组断言（`tools/PdfSmokeTest/Program.cs`）：
1. `new VirtualKeyboard().Build()` 不抛、递归数出按键数（实测 **92** 个键）且 `>= 80`；
2. `new FunctionInputWindow(null, _ => {})` **构造不抛异常**（不 `ShowDialog`，只构造后 `Close()`；harness 是 `[STAThread]`，可安全建 `Window`）。

   **铁律**：**"UI 入口能否被打开"必须有一条断言**。数据层断言再全，也挡不住"按钮点下去什么也不发生"。
   凡"点 X 弹窗/开面板"的功能，harness 至少要**构造一次那个 UI**（能构造就不抛），别只测它背后的纯逻辑。
   另外：**遍历不规则二维数组一律用 `Length` 而不是常量维度**。

### 8.10 函数图像第二轮现场修复：四个坑 + 一条"假对象说谎"

现场反馈四条：① 「能画了，但**点很多次才弹出**窗口」；② 「函数的线**太粗**」；③ 「颜色和坐标轴**一样**」；
④ 「图像要和坐标轴**绑定**，多函数画在同一坐标系且**颜色区分**」。逐条记坑：

1. **选锚点型工具，绝不能抄"拖出尺寸"的门槛**
   `FunctionTool.OnPointer` 的 `Up` 分支原本照抄直尺：`if ((world - _anchor).Length < MinDragWorld /*2.0*/) return;`
   —— 直尺要靠拖动定长度，**函数图像只需要一个锚点**（决定绑到哪张图上）。
   后果：单击被静默丢弃（只 `SetStatus` 一句，日志里什么都不留），而鼠标单击的抖动恰好在 2 世界单位上下，
   **过不过全凭运气** ⇒ 用户看到的就是"点很多次才偶尔弹出一次"。
   **铁律**：工具分两类 —— **拖出尺寸型**（直尺/三角板/量角器/坐标系）才需要阈值；
   **选锚点型**（弹窗输入、标记点）**按下过就必须响应**，误触要靠"弹窗能取消"来兜，不是靠吞掉点击。
   现场日志的读法：`M4.2 输入事件汇总` 里 `mouse.down.Left = 93`（点了 93 次）却只有零星几次 `工具切换` 回 `gfx-select`（创建成功的标志）。

2. **几何用"数学坐标"时，线宽也要反缩放**
   曲线几何是"1 单位 = 1 世界点"，而宿主按 `Scale = unitWorld ≈ 28.35` 放大整个视觉 ⇒
   `StrokeThickness = obj.LineWorldWidth` 渲染出来的**世界粗细 = 1.5 × 28.35 ≈ 42.5**，粗了 28 倍。
   **修法**：`StrokeThickness = obj.LineWorldWidth / obj.Scale`（含占位框的虚线框）。
   这与 M7.3 直尺"长度数字要反缩放"、`GfxPlaceholder` 文字反缩放是**同一条规则**：
   **凡是固定尺寸的图元（线宽、字号、短横、箭头），在会被 `Scale` 放大的视觉树里都必须除掉 `Scale`。**
   断言方式：不要写死数值，比"曲线世界粗细 vs 坐标轴世界粗细"（`stroke × Scale` vs `LineWorldWidth × Scale`）。
   坐标系是**一个自绘 `FrameworkElement`**（网格/轴/标签都在 `OnRender` 里画），视觉树里**没有 `Path` 可量** ——
   它的轴粗细直接取自模型的 `LineWorldWidth`（渲染器就是这么用的），别去视觉树里找。

3. **★假对象（fake）只要有一处不忠实，测试就开始说谎**
   `S4FakeRef.Color` 原本写死 `=> Colors.Black`，而它对应的 draft 明明是红的。
   于是"按轴色避开撞色"的逻辑在**假 host** 下拿到假轴色：第 1 条走"新建坐标系"分支拿到真笔色（红），
   第 2/3 条走"已有坐标系"分支拿到假的黑 ⇒ 候选色表从 5 色变 6 色 ⇒ 第 2 条取到与第 1 条相同的颜色，
   测试报 FAIL，而**生产代码完全正确**。
   **排查手法（值得复用）**：把可疑量与结论**一起写进状态栏**（`SetStatus`），让插件自己"自报"内部真实值 ——
   `函数图像：y = 2*x（本图第 2 条，蓝色）` 一打出来，"数对了(第2条)、取色错了(蓝)"立刻把范围锁死在取色那一步，
   比盯着断言猜快得多（顺带还是个对老师有用的提示）。
   **铁律**：假对象必须**逐字段忠实转发** draft（`Kind/Center/Scale/Rotation/Numbers/Texts/**Color**/LineWorldWidth`）；
   凡是"从假对象读出来"的字段，都要能从 draft 追到源头。

4. **配色：先在候选里筛，再取模**
   想避开与轴色过近的颜色，写成"按序取模，撞色就往后挪一格"会让**第 1 条和第 2 条撞成同一个颜色**
   （第 1 条跳过红得蓝；第 2 条取模正好也是蓝）。
   **修法**：先滤出 `allowed = 配色板里不与轴色过近的那些`，再 `allowed[used % allowed.Count]`。
   阈值取 **160**（逐通道绝对差之和）：与黑/深色轴的距离都 ≥ 274 不吃亏，而红笔画的轴会把配色板里的"红"判为撞色跳过。
   另外：`S4FakeRef.BoundsWorld` 只有 2×2，**任何"点在图里"的吸附逻辑在假 host 下都退化成"取原点最近"** ——
   想测"包含优先"必须换真 host 或把 fake 的 `BoundsWorld` 写实。

5. **"跟随"（绑定）只能落在宿主层**
   渲染器只拿得到**自己这一个对象**（`IGfxObjectRef`），看不见画布上的别人 ⇒ "我要跟着谁、他现在在哪"只有
   `GfxObjectStore` 答得出来。落地方案见 `docs/11` §14（`Texts["bindTo"]` + `bindRel*` + `RecomputeAttachments()`）。

### 8.11 画"对象"的工具（M7.4 Step 5 矢量箭头 新坑）

1. **★宿主唯一的跟随公式，决定了"绑坐标系对象"的本地几何语义**
   `GfxObjectStore.RecomputeAttachments()` 里只有一条公式：`obj.Scale = unit × targetScale`
   （`unit = 目标坐标系一个数学单位的世界长度`）。它当初是**为函数曲线**写的：
   曲线本地几何 = 数学坐标，乘 Scale 后正好是世界长度。
   箭头若照搬"本地几何 = 世界长度"，就会被**再乘一次 unit**。
   实测症状：箭头跟到坐标系后**世界长度被放大 28.35 倍**（370 → 2284.5 世界单位），画面上是一根戳出屏幕的巨杆；
   而 `lengthWorld` 读数**仍然正确** ⇒ 典型的"数据对、画面对"。
   **规律**：凡是绑到坐标系上的对象，**本地几何一律按"数学单位"画**（`lengthLocal = lengthWorld / unitWorld`），
   `Numbers["...World"]` 这类"给宿主和人看的量"仍存世界值，两者靠 `unitWorld` 换算。
   遵守这条约定就能**零宿主改动、零契约改动**复用同一套跟随机制（箭头与函数曲线现在共用它）。
   **代价**：所有"固定屏幕尺寸"的量（文字字号）除 `Scale` 之外还要再除一次 `unitWorld`
   （`fontLocal = 14.0 / (Scale × unitWorld)`），否则字会跟着数学单位一起被放大。

2. **`const` 借用：编译期内联，不产生运行时 dll 依赖**
   想复用直尺的吸附常量又**不能**让 `vectorarrow.dll` 依赖 `ruler.dll`：
   ```csharp
   public const double SnapStepDegrees = RulerGeometry.SnapStepDegrees;  // 编译期取值并内联
   ```
   `const` 在**编译期**求值，作为字面量烧进 IL ⇒ 生成的 dll 里**不含**对 ruler 的引用。
   **双重验证**：① 字节级 —— `vectorarrow.dll` 里 `ruler` 出现 **0 次**；
   ② 交付目录 —— `plugins/vectorarrow/` 下**没有** `ruler.dll`。
   csproj 仍需 `ProjectReference`（否则编译不过），配 `<Private>false</Private>` + `<ExcludeAssets>runtime</ExcludeAssets>`
   阻止它被复制到输出目录。
   **只借常量，不借函数**：直尺 `SnapAxisDegrees` 是"直线轴向 [0,180)"语义（178°→0°），
   矢量方向是 [0,360) 极角语义 —— 含义不同，各写各的，别为了"复用"把两种语义搅在一起。

3. **方向角只进了文字、没进几何**（"读数 37°，箭头却是水平的"）
   世界 y 轴向下 ⇒ 屏幕向上的方向是 **90°**，`DirectionDegrees` 必须对 `dy` **取负**（`Atan2(-dy, dx)`）。
   更要命的是：算完角度后**别忘了真的旋转几何** —— 第一版把 `directionDegrees` 只传给了文字渲染，
   箭杆/箭头仍是水平的，而读数写着 37°，**看起来像"角度算错了"，其实是"角度根本没接上"**。
   修法：`ArrowGeometry.BuildShaft/BuildHead` 加 `directionDegrees` 参数，内部
   `sg.Transform = Rotation(dir)`（`RotateTransform(-dir)`），**先设 `Transform` 再 `Freeze()`**
   （`Geometry.Freeze()` 之后再写 `Transform` 抛 `InvalidOperationException`，M7.4 Step 3 已记过一次）。
   **断言要落到顶点坐标**，不要只断言"文字里写了什么度"：`37°` 的尖端应在 `(L/2·cos37, -L/2·sin37)` 附近。

4. **文字锚点不要跟着方向转**
   第一版锚点取"箭头左侧法向 `(-sinθ, -cosθ)`"（跟方向一起转），朝左（180°）时锚点翻到箭杆上，
   读数被箭杆戳穿。**修法**：锚点固定在箭头**屏幕正上方** `(mid.X, mid.Y - gapWorld)`，
   渲染器与预览两处**同步改**（渲染器 `_labelAnchor` 与 `ArrowTool.PlaceLabel` 是两份实现，容易只改一处）。

5. **文档里的断言值也可能写错 —— 先算一遍再信**
   `docs/11` §4 Step 5 原本写"29°→30°、37°→37°、**353°→0°**"，与同句的"容差 5°"自相矛盾
   （353° 距 360° 是 7° > 5°，**不该吸**）。实现按容差写是对的，**文档笔误**。
   修：文档改 `357°→0°`（距 360° 仅 3°），并补一条"353°→353°（超容差不吸）"把边界钉住。
   **教训**：验收断言里的数值示例，落地时要当成"待验证的命题"而非"标准答案"。

6. **打包前固定检查：每个插件目录只能有 `<name>.dll`**
   `dist/tablet/plugins/ruler/` 里躺着历史遗留的 `MathPhys.Ink.Plugin.Ruler.dll`（源自 S4 包），
   原因是早期打包脚本没有清空 plugins 目录。这类残留会让"插件目录 = 文件名"的对应关系失效，
   排查插件加载问题时极容易误判。**发布前一律清理 plugins 下所有子目录再重新复制**。

### 8.12 删功能时别把"参数"一起删掉；断言要贴着真实调用链（M7.4 Step 5 修订）

用户要求"矢量箭头旁边不要显示文字"，本轮只该删**渲染**，结果引入了 1 个真 bug。
两条坑都值得单独记：

1. **★"省参数"的重载 = 给 bug 留后门**
   删文字时 `CreateVisual` 的构造调用从 8 参缩到 5 参，我顺手加了个便利重载：
   ```csharp
   public ArrowVisual(Color c, double w, double scale, double lenLocal)
       : this(c, w, scale, lenLocal, angleDegrees: 0.0) { }   // ← 后门
   ```
   结果 `CreateVisual` 正好落到这个重载上 ⇒ **方向角恒为 0**，
   画面上两根箭头齐刷刷朝同一个怪角（实测朝右下 60°）。
   这正是 §8.11-3 那个"角度没进几何"的老毛病**换了个入口又回来**。
   **铁律**：多参数构造器**不要**提供"省略关键语义参数"的便利重载。
   少写几个字符的代价是"这个 bug 可以悄无声息地复发"，不划算。
   删掉重载后，少传参数会**编译不过** —— 让编译器替你守这道门。

2. **★断言贴着"真实调用链"，别只验底层纯函数**
   为什么上一轮全绿、这一轮也全绿，却还是有 bug？因为"几何朝向"那条断言验的是
   ```csharp
   var tip = ArrowGeometry.Rotation(37).Transform(ArrowGeometry.TipLocal(100));   // 直接调几何
   ```
   —— 它绕过了**渲染器**。渲染器漏传方向角，这条断言完全看不见（它验的纯函数本身没错）。
   抓到这个 bug 的是**证据图**（我肉眼看图发现两根箭头朝向一样），不是断言。
   **修法**：补一条走公开路径的断言 —— "对象的 `angleDeg` ⇒ 渲染器画出的尖端方向"。
   **判断标准**：一条断言如果"把被测代码换成等价实现"仍然通过，那它大概率没测到你想测的那一层。
   本项目的对应原则：**"点 X 弹窗"的功能必须构造一次那个 UI**（§8.9）、
   **"渲染器不抛"必须真的调用一次 `CreateVisual`**（§8.10），同一条思路。

3. **删渲染 ≠ 删计算**
   "不要显示文字"删掉的是 `OnRender` 里的绘制与 `FormattedText`；
   `VectorMath.Describe()`（拼"大小 4.9 N　方向 37°"）**必须留着** ——
   它是状态栏的数据源。一起删掉的表现是"卷面干净了，状态栏也空了"，
   属于**把功能做退步**却以为在满足需求。
   判断口诀：**问"这个函数除了我删的那条去路，还有没有别的调用者"**（`Grep` 一下调用点）。

4. **给"越界绘制为零"留一条断言**
   文字删掉后，箭头的视觉**完全落在 `Measure()` 的包围盒内**。
   这条不是废话：文字一旦回来而 `Measure` 没跟着长高，命中区域就与视觉不一致
   （老师点箭头旁边的空白会**选不中**它）。
   断言形式：`Measure().Height == HeadHalfWidthWorld * 2`，注释写明"含文字必然更大"。

### 8.13 画"对象"的工具（M7.4 Step 5 第二轮 · 合力 新坑）

**背景**：合力是本项目第一个「**我画什么取决于别人**」的对象 ——
一根箭头的内容由 N 根分矢量决定。它一次暴露了两个**宿主级**结构缺口，
两个都不是 plugin 的错，而是宿主"从来没遇到过这种对象"。

**坑 1 — `GfxObjectLayer.Sync()` 改参数不重建几何**

- 症状：合力对象的 `LocalSize` 明明变了（`RecomputeAttachments` 里重算过），
  屏幕上那根线却还是**旧长度/旧方向**。
- 根因：`Sync()` 的逻辑是
  `if (!_visuals.TryGetValue(id, out v)) { Build(obj); } else { ApplyPose(v, obj); }`
  —— **只在视觉不存在时 Build**；参数变了只 `ApplyPose`（只改矩阵）⇒ 几何永不重画。
- 为什么到这一轮才暴露：函数图像也有"参数"（表达式），但它当时**还没有参数面板**，
  改参数 = 删了重画，从不走"同一对象改参数"这条路。合力是第一个真走这条路的。
- **修法**：给每个对象记一份「几何签名」（用 `obj.LocalSize`），
  `Sync()` 里当签名变了就**移除旧视觉 → 重新 Build**。
  选 `LocalSize` 当签名是因为它由渲染器 `Measure` 算出、与 `CreateVisual` **读同一份参数**。
- **为什么不会拖累拖动性能**：纯位姿变化（拖 / 转 / 缩放）**不改 `LocalSize`**
  ⇒ 只走 `ApplyPose`，一行几何都不重建。这是本坑最容易被做错的地方
  （如果拿"位姿"当签名，拖动就会每帧重建视觉，一体机上必卡）。
- 反向对账分支（删对象）里也要 `_geometry.Remove(id)`，否则下次同 Id 复用会误判。

**坑 2 — 渲染器看不到画布（新增可选契约接口）**

- 症状：合力渲染器要遍历"所有对象"才能求和，但它手上只有自己那一个 `obj`。
- 修法：新增**可选**接口 `IGfxBoardAwareRenderer { void SetBoard(IReadOnlyList<IGfxObjectRef>?); }`，
  宿主在 `CreateContent` 与 `MeasureSize` 前用 `is` 判断后喂给它。
  **契约只加不改** ⇒ 已分发的旧插件 dll 零影响（这是本项目铁律）。
- ★ **必须实例实现，禁止静态字段缓存画布**：同一进程里可以有多个渲染器实例
  （harness 就造了好几个 catalog），静态字段会**互相踩快照** ——
  表现是"后建的对象把先建的画布覆盖了"，且**单实例测试永远测不出来**。
  本轮开发中途自我纠正过一次（从 `static` 改成实例实现）。

**坑 3 — 一对多跟随别硬塞进宿主绑定区**

宿主既有绑定区 `BindKey="bindTo"` **只认单个 Id**。合力要"取决于 N 个"，
最省事的做法是改宿主绑定模型支持多目标 —— 但那是**动地基**。
本轮选的是：**对象自己用 `Texts["sumOf"]="id1,id2,id3"` 记组成，插件侧渲染器实时求和**，
宿主只负责"在 `RaiseChanged` 时提醒重算一下"（`RefreshSumObjects`，<15 行）。
**口诀：宿主提供"何时重算"，插件决定"怎么重算"。**

**坑 4 — 中文断言串里禁止 ASCII 双引号（又踩一次）**

批处理改写时把 `? （无 = 实线） :` 的引号误删，C# 三目表达式里出现裸中文，
报 `CS1073: Unexpected token '（'` 等 12 个语法错。**症状指向"引号"，不是"中文"。**
写断言串里要表达"无（实线）"就老老实实 `"无（实线）"`。

**坑 5 — 断言写错时，先手工验算再改断言（本轮实例）**

合力初版断言「3 东 + 4 北 = 36.87°」是**我配对配反了**（`36.87° = atan(3/4)` 其实是 4 东 + 3 北）。
处理流程值得复用：**先怀疑断言、再怀疑代码** →
用独立脚本（Python 复刻 `UnitVector` / `DirectionDegrees`）**手工把数算一遍** →
确认代码对 → 改断言。
**并且顺手补一条"互为反例"的断言**（3东+4北 ⇒ 53.13° 与 4东+3北 ⇒ 36.87° 并列），
让"角度镜像"这类错误**无论往哪边偏都跑不掉**。

### 8.14 数值看"图"的三个坑 + 一个渲染坑（M7.4 六批次补全）

函数图像补「零点 / 交点 / 极值」时，三个坑全在**数值**侧、一个在**渲染**侧。
四个都具备同一个特征：**不抛异常、程序照跑、画面看着像对的**。

**坑 1 — 中心差分的系统偏差会淹没驻点（`x³` 在原点找不到极值）**

- 朴素中心差分 `D(x, h) = [ f(x+h) − f(x−h) ] / (2h)`，截断误差是 `h²/6` 乘三阶导数。
- `x³` 在 `x = 0` 处真导数为 0，但差分值实测 `1e-6` 量级 ——
  比判零阈值大**两个数量级**，于是「三次函数的驻点」永远判不出来。
- **修法**：理查森外推 `D_R = [ 4·D(x, h/2) − D(x, h) ] / 3`，误差降到四阶。
- **可复用判据**：凡"用差分求导再做零判定"的地方，先问一句
  「我的差分误差比判零阈值大吗？」大就得外推，或者把阈值绑到函数值尺度上（本次阈值取 `yScale × 1e-9`）。

**坑 2 — 分段断点靠"幅值跳变"永远断不开**

- 采样器原断开判据：「相邻点 y 差值 > `2 × (yMax − yMin)`」。
- `{x<0: -1, else: 1}` 的跳变只有 2，典型坐标系幅值差是 10 —— 判据差 5 倍 ⇒
  画成一条**从 −1 匀速爬到 +1 的斜坡**，看着像函数、其实是错的。
- **修法**：`CollectBreakpoints()` 解析求出断点 + `forceBreak` **强制**打断（不靠幅值猜）。
- **★ 附带细节**：断点注入条件必须写 `breaks[k] <= x` 而不是 `<` ——
  格点经常**正好落在断点上**，用 `<` 会让该点先被右侧分支求值，于是断点"挪"了一格。
  这类"边界该开该闭"的低级错误，在几何上表现为"图往一边偏了半个格"，极难肉眼发现。

**坑 3 — 求根返回的是"残差"，不是"函数值"**

- 交点是对 `a − b = 0` 求根，解出来的值恒为 0（就是残差）。
- 最初直接拿它填 `FeaturePoint.Y` ⇒ **所有交点都被画到 x 轴上**（`y` 全 0，视觉上"看着还挺对"）。
- **修法**：拿到根 x 后**回代原函数**取真实 y。
- **可复用判据**：凡是"解方程得到 x，然后要画点"的地方，y 一律**回代求值**，绝不用求解过程的中间量。

**坑 4 — 小字号文字要"看得见地压在曲线上"，靠底色块不是描边**

- 症状：小圆点画出来了，**读数文字整片消失**，且不抛异常。
- 剖开视觉树：文字 `Path` 的 `Data.Bounds` 完全正常（0.9 × 0.32 数学单位）⇒ 几何没问题。
- 真因在**描边**：原写法是「给文字加一圈白色 `Stroke` 当背景」。
  但 WPF 描边**骑在轮廓线上、内外各一半**：`0.18 × 字号` 的描边单边 `0.06` 数学单位，
  而该字号下数字笔画整条才约 `0.08` 宽 ⇒ **白边从两侧把字芯吃光**。
- **修法**：用**实心白衬板**（`Rectangle` 垫在读数下面，尺寸取自几何变换后的真实 `Bounds`），
  文字只 `Fill` 不 `Stroke`。
- **可复用判据**：**描边宽度是"单边"语义，底色块是"整体"语义**。
  想当背景就一定用底色块；用描边当背景，宽度得小于笔画宽度的一半才行。
- **★ 这条还暴露了一个断言设计错误**：原断言只数「椭圆个数」，
  于是"圆点在、字没了"能**全绿通过**。补了 `24) 读数标注可见性`（实心 `Path` ≥ 2、
  白描边 `Path` == 0、衬板 ≥ 2）把**用户感知**而不是**实现细节**钉死。
  **教训：断言数"元素个数"是最弱的断言；要数"元素长什么样"。**

**坑 5 — 绑定跟随必须验"穿过存档"（原断言只走内存）**

- 原「绑定跟随」断言直接在内存里的 `GfxObjectStore` 上 `UpdatePose`，全绿。
- 但老师的真实用法是「存盘 → 明天打开 → 拖坐标轴」。
  存档里漏掉 `bindTo`（或写进去读不回）的现场表现是
  「昨天还好好的，今天打开就不跟了」，极难当场复现。
- **修法**：补 `16) 绑定穿过存档`：存 `.tbink` → 读回 → `Restore` 进新 store →
  `UpdatePose(sys, ..., 2.0)` ⇒ 断言 `bindTo` 原样还原 **且** 曲线缩放跟到 `unit × 2`。
- **可复用判据**：凡是"对象之间有关系"的功能，**必须有一条断言穿过序列化边界**。
  内存内自洽不代表存盘后自洽。


### 8.15 ★ `dotnet publish` 不会刷新 `plugins/` —— 差点发包发了个旧的（M7.4 收尾新坑）

**症状**：改了 `functionplot` 的代码、Release 构建 0 错、全量回归 424 PASS，
`publish` 也成功 —— 但 `dist/tablet/plugins/functionplot/functionplot.dll` 还是**上一次**的。
本批实测：源 dll 时间戳 `14:07`，包里的还是 `13:18`，**批次 4 的代码一个字节都没进去**。

**为什么**：`publish` 只处理宿主的 `ProjectReference` 图。
插件是**运行时**用 `AssemblyLoadContext` 从 `plugins\` 目录扫进来的，
在宿主的 csproj 里**没有**引用它们 —— 所以 publish 眼里它们不存在，自然不更新。
而 `dist/tablet/plugins/` 里**恰好有**同名旧文件，于是静默"保持原样"。

**为什么危险**：
- **编译不报错**（旧 dll 当然能编译过 —— 它根本没参与编译）。
- **冒烟也能过**（旧 dll 照样 `[Loaded]`、工具数照样对 —— 只是功能是旧的）。
- 现场表现是「我明明改了，一体机上还是老样子」，而你在开发机上怎么试都是好的。
- 只有两件事能发现它：**比对时间戳**，或者**读 dll 里的符号**（本批用后者实锤：
  在包里那个 dll 里搜 `FeatureFinder` / `PiecewiseNode` 才确认代码进没进）。

**正确流程（每次发包都照做）**：

1. 先把**整个解决方案** Release 构建一遍（不能只 publish 宿主）：
   `dotnet build MathPhys.Ink.sln -c Release`
2. **清空 `dist/tablet/plugins/` 下所有子目录**（保留像 `说明.txt` 这样的文件）。
3. 从各插件工程的 `bin\Release\net8.0-windows\` 把 dll 复制过去，**一个插件一个目录、一个 dll**。
4. **回读校验**：每个目录里必须**恰好一个** dll；再抽查新写的类型名在不在 dll 里。
5. 再压缩打包（`Compress-Archive -Path "<包目录>\*"`，**必须 `/*` 形态**）。
6. 压缩后校验：zip **顶层**能直接看到 `MathPhys.Ink.exe`（扁平，不是套一层目录）。

**可复用判据**：凡是"产物不在主工程的引用图里"（插件、资源、手工收集的文件），
**打包流程必须显式复制 + 显式校验**，不能指望 publish 顺手带上。

**旁注（本批同时确认）**：`Plugin.VectorArrow` 在 sln 整体构建时，日志里可能显示它输出到
`bin\Debug\`（构建图把它当成某个 Debug 配置链的依赖）—— 单独用
`-c Release` 构建该 csproj 即得到正确的 Release 产物。复制时按**显式 Release 路径**取，
不要依赖 sln 输出行里那个路径。

### 8.16 ★ "世界长常量"塞进"数学单位本地几何" ⇒ 被 unitWorld 放大（M7.4 现场修复）

**症状**：矢量箭头挂到坐标系上以后「大小不对」—— 只剩一个巨大三角，箭杆几乎看不见。

**根因**（本项目**第三次**同源）：`ArrowGeometry.HeadLengthWorld = 11.0` /
`HeadHalfWidthWorld = 5.5` 是**世界长**常量，而 `ArrowVisual` 的几何按**数学单位**画
（`lengthLocal = lengthWorld ÷ unitWorld`）。直接把世界常量写进数学坐标 ⇒
绑定坐标系（`unitWorld ≈ 28.35`）时三角被放大 28.35 倍，
`shaft = 5 − 11 = −6` 被 `MinShaftWorld` 截断 ⇒ 只剩三角。
同一根因还让 `Measure()` 的高度（也用世界常量）把**命中区抬高 28 倍**。

**铁律**：

> **凡"世界长常量"，只要它进了"按数学单位画的本地几何"，就必须除 `unitWorld`。**
> 已踩过的清单：**线宽**、**虚线节距**、**箭头三角（本次）**。
> 还没踩但同类：刻度短横、字号（`FormattedText`）、圆点半径。

**修法句式**（两处即可，契约零改动）：

```csharp
double safeUnit = unitWorld > 0 && !double.IsNaN(unitWorld) && !double.IsInfinity(unitWorld)
    ? unitWorld : 1.0;
double headLenLocal  = ArrowGeometry.HeadLengthWorld  / safeUnit;
double headHalfLocal = ArrowGeometry.HeadHalfWidthWorld / safeUnit;
```

**★ 配套的断言教训**：`ArrowVisual : FrameworkElement` 是在 `OnRender(DrawingContext)`
里 `DrawGeometry` 直接画的，**视觉树里没有 `Path` 子元素** ⇒
沿用"递归 `VisualTreeHelper` 找 `Path`"的量法会**恒量出 0×0**（我第一次就这么写的，
三条断言全 FAIL，但值是 0 而不是错值，一眼能看出是"量法错"而不是"代码错"）。
正确量法：**反射读私有字段 `_shaft` / `_head`**。
**通用教训：看起来通用的量法，先确认它量的那个对象长什么样。**

**★ 非空验证（防假绿）**：改完顺手把 bug 注回去跑一遍，确认断言真的会 FAIL 且失败值
精确复现症状（本次：`429 → 426 PASS / 3 FAIL`，`箭杆 0.1000`、`三角 11.0000`），
再还原。**这一步比断言本身更值钱** —— 它证明这张网不是空转的。

## 9. 工程文件存读（M8）

### 9.1 ★ `.NET ZipArchive` 读 stored 条目不校验 CRC ⇒ 自己存 SHA-256（M8 S0 实测）

**实测事实**：把内嵌的 `document.pdf`（在包里以 `stored` 不压缩方式存放）**改掉 1 个字节**，
用 `new ZipArchive(stream, ZipArchiveMode.Read)` + `entry.Open()` 读出来，
.NET **一声不吭地把坏内容交给你**（harness 里打了一行 `[事实] … ZIP 层静默放行`）。
`entry.CompressedLength == entry.Length == 524345` 也照样成立 —— 长度对不上不是可靠判据。

**为什么这是原则问题**：工程文件是老师这一节课的**唯一成果载体**。
"卷面悄悄花掉""批注莫名少几笔"却没有任何提示，现场无从追查 —— 正是本清单反复强调的**静默损坏**。

**做法**：`manifest.json` 里存各段载荷的 `sha256`（`integrity` 段），读取时比对，不符就明确拒绝并
**说清是哪一段坏了**（`内嵌 PDF` / `批注`）。校验值缺席时**跳过**而不是判损坏（增强项，不是必需品）。

```csharp
manifest.Integrity = new TwbIntegrity {
    PdfSha256        = embedding == Embedded ? Sha256Hex(pdfBytes!) : string.Empty,
    AnnotationSha256 = tbinkBytes is { Length: > 0 } ? Sha256Hex(tbinkBytes) : string.Empty,
};
// 读侧：VerifyIntegrity(...) 不符 ⇒ "工程文件内容已损坏（内嵌 PDF 与保存时的校验值不符）"
```

**可复用判据**：**只要容器格式里有一段"外部给的、体积可观的原始字节"，就别指望压缩库替你验完整性。**
代价（一份 30 MB 卷面约 100 ms 的哈希）换"绝不静默给出坏内容"，划得来。

**★ 配套的断言写法**：不要断言"ZIP 库会报错"（库行为随版本变，将来修好了反而变成红）。
断言**我们自己的保证**（"改坏 1 字节 ⇒ 必被拒绝且指明段名"），
把库的行为**只打印成一行事实**、不参与 PASS/FAIL。

### 9.2 ★ 临时文件：删除与替换都必须在**流关闭之后**（M8 S0 两连踩）

同一个方法里栽了两次，症状完全不同、根因同源：

| 写法 | 症状 | 原因 |
|---|---|---|
| 在 `using` **内**调 `File.Delete(tmp)` | 留下 0 字节 `.tmp` 残骸 | 自己句柄未关，Windows 拒绝删除（异常被吞掉） |
| 在 `using` **内**调 `File.Replace/Move(tmp, target)` | 直接抛 `The process cannot access the file because it is being used by another process` | 自己还开着写句柄 |

**正确顺序**（`TwbFile.Write` 的最终形态）：

```csharp
bool written;
using (var stream = new FileStream(tmp, FileMode.Create, FileAccess.Write, FileShare.None))
{
    written = Write(stream, ...);      // 只写，不动文件系统
}                                      // ← 流在这里关闭
if (written) { File.Replace(tmp, target, null); return true; }   // 替换在 using 之外
SafeDeleteFile(tmp);                   // 失败清理也在 using 之外
```

**配套断言**：`保存失败不留残骸：临时文件已清理`（检查 `<name>.tmp` 不存在）——
这条断言是**这次修 bug 的固化**，以后谁把顺序改回去都会立刻红。


### 9.3 ★ 真机冒烟的判据必须拿真实截图**先标定**（M8 S2/S3 两次假 FAIL）

同一个毛病栽了两轮，两次都是"产品做对了、脚本报红"：

| 场景 | 凭感觉拍的阈值 | 实测噪声 / 信号 | 结果 |
|---|---|---|---|
| S3「鼠标真落墨了没有」（画布灰度平均绝对差） | `1.5` | 同一内容跨进程 **0.01**；多三笔 **0.59** | 两条假 FAIL（证据本身却显示三笔真进了包，982 字节） |
| S2「打开工程是不是白屏」（画布灰度标准差） | —— 先做了标定 | 纯白 **0.00 / mean=255**；有内容 **54.06** | 阈值取 5，干净 |

**做法（两轮都验证过）**：

1. 先跑一遍**把数打出来**（把差异值 / 标准差连同 PASS/FAIL 一起打印）；
2. 拿**已知的坏图与好图**定阈值，留 3~10 倍余量（`0.01 vs 0.59` ⇒ 取 `0.2`；`0.00 vs 54` ⇒ 取 `5`）；
3. 能用**相对比较**就别用绝对阈值：`diff(重开后, 有墨) < diff(重开后, 无墨) × 0.3`（实测 0.01 vs 0.59）
   —— 它不依赖截图内容的明暗程度。

**判据要自检**：白屏判据本身写成纯函数 `IsViewUsable(...)`，再单独断言它的三条边界
（视口 0×0 时不否决、缩放 ≤ 0 必否决、落在页外必否决）—— 判据坏了，上面那几条断言就全是空转。

**★ 比截图更硬的一层**：同一件事能用"产物里的一个数"证明时，优先用它。S4 的"三笔真落墨并保存"
最终落在 `annotation.tbink` 解出来的 **`"StrokeCount":3`** 上 —— 一条断言同时证明了
"鼠标落墨"与"保存写盘"，而截图差分只能证明"画面变了"。

**辅助函数的返回值也要先看清楚**：`find_message_box()` 没找到时返回 **`0`**（不是 `None`）、
`draw_marks()` **没有返回值**。S4 第一轮把它们猜错了，一次造出三条假 FAIL
（"产品明明做对了、脚本报红"比漏测更费时间）。

### 9.4 ★ "什么算改动" = 笔迹 **+** 图形对象（M8 S3 真 bug）

**实测事实**：`CanvasViewportHost.InkChanged` 原来**只从 `OnStrokesChanged` 触发**。
图形对象（坐标系 / 函数图像 / 三角板 / 矢量箭头）长在另一个层（`GfxLayer` + `GfxObjectStore`）上，
它们的新增、拖动、改参数、删除**一个都不上报**。后果：

- 工程模式：不置脏 ⇒ 老师**拖一下坐标系直接关窗口，既不提示也不会被存下来**；
- 快速模式：不通知 `AutoSaveScheduler` ⇒ 侧车也不重写。

即 **M7 起的一等公民（学科工具）从来没进过"会被保存"的范畴**，而界面上"什么都没发生"。

**做法**：宿主加 `OnGfxContentChanged`（刷参数面板 + 触发 `InkChanged`），
`_gfxStore.Changed += OnGfxContentChanged`；事件文档改成"批注内容 = 笔迹 **+** 图形对象"。

**没改名**：`InkChanged` 不在插件契约 `IGeoGebraHostHooks` 里（只有 Enter/Exit/SetStatus），
但 harness 有 4 处引用 —— 改名是无谓风险，语义写进注释即可。

**安全性核对（装载期也会触发）**：`GfxObjectStore.Restore` 会 `RaiseChanged`，
但 `ApplyLoadedProject` 里 `_autoSave.IsSuspended = true`、且 `ReplaceObjects` 排在
`_project.Apply + MarkClean` **之前** ⇒ 不会"工程一打开就显示未保存"。

**配套断言**：5 条（笔迹回归 + 图形对象的新增 / 拖动 / 改参数 / 删除），每条都断言**恰好一次**上报 ——
多报会让自动保存被无谓重置，少报就是静默丢。

### 9.5 ★ 复原存档视口必须走语义化入口（M8 S2 真 bug：存档位置白存 + 首屏白屏）

两个问题叠在一起，靠 `TB_RENDER_TRACE=1` 的渲染追踪日志才分开：

1. **存档视口可能落在页面之外。** 排版把页面放在 `(960,960)` 起排、四周留 960pt 可写留白
   （`WorldLayout.DefaultPageMargin`），所以 `100%@(0,0)` 看到的是**一片纯白留白区**
   （实测 `std=0.00 / mean=255`）—— 在老师眼里与"文件根本没打开"**完全无法分辨**。
2. **更要紧的：正确的视口会被随后的自动适应覆盖。** `CanvasViewport.SetView` **不触发**
   `ViewportMutated` ⇒ `_autoFitWidth` 仍为 `true` ⇒ 窗口下一次改尺寸就把存档位置整个算掉。
   也就是"我停在第五题那个缩放"**从来就存不住**，只是平时不易察觉。

**做法**（都在宿主里，窗口侧只调一个入口）：

- `CanvasViewportHost.RestoreView(scale, x, y)` —— **复原 = 用户意图 ⇒ 显式 `_autoFitWidth = false`**；
- 纯函数 `ProjectComposer.IsViewUsable(...)` 判"按存档摆好后可见范围是否与页面相交"，
  坏档兜底回「适应宽度」并留痕（`[视图] 存档视口 … 看不到任何页面，已退回「适应宽度」`）。

**为什么要做成纯函数**：这段判定在界面上的唯一表现就是"白屏和白纸长得一样"，肉眼验收碰不出来。

**配套断言（含一条防假通过）**：「复原之后窗口改尺寸，视口必须原地不动」很容易变成假绿
（若 `SizeChanged` 压根没触发，断言照样过）⇒ 补**反向对照**：
自动适应模式下同一个"改尺寸"动作**必须**改变缩放（实测 `1000→900` 宽：`1.599 → 1.432`）。

### 9.6 ★ 构造里绝不弹模态框（M8 S2 真 bug：主窗口"不可见"）

`ApplyStartupArgument()` 原本在窗口构造函数里同步执行。命令行带 `.twb` 启动、工程是 `referenced`
且试卷不在原位时，装载过程会弹「定位试卷」模态对话框 —— 而此时**主窗口还没显示**，
结果对话框孤零零挂在桌面上、主窗口根本不存在（真机冒烟的"主窗口起来"那条因此 FAIL，
脚本在对话框弹着的时候找不到主窗口）。

**做法**：入口挪到 `Loaded` 事件后（一次性退订）。

**判据**：这条毛病**不会崩**，只让用户看到半截界面 ⇒ 只有真机冒烟能发现。

### 9.7 ★ 交付链三件事（M8 S4 发布时踩到）

1. **`dotnet build <sln> -c Release` 不保证所有插件都编到 Release。** 实测日志里
   `VectorArrow` 输出到 `bin\Debug\`，而铺装脚本按 `bin\Release` 找 ⇒
   表现是"插件明明编译过了、包里偏偏没有那个工具"，且日志一片正常。
   ★ **根因（M9 S4 补齐）**：`VectorArrow`（以及 `PdfSmokeTest.Plugin`）**根本不在 `.sln` 里**
   —— sln 只有 10 个工程。所以"整体 sln Release 构建"**永远不会**刷新它的 Release 产物，
   而它之所以还会被编译，是被别的工程引用拉进来的，走的是默认配置（Debug）。
   ⇒ 真正的修法是**把插件工程都加进 sln**；没加之前，只能按"逐个核 Release 产物 + 缺了就单独补构建"兜。
   M9 S4 又一次踩到同一处（说明"记下来了"不等于"下次不会踩"）。
   **做法**：铺装前**逐个插件**核 `bin\Release\net8.0-windows[\win-x64]\<dll>` 是否存在，
   缺了就单独 `dotnet build <该插件.csproj> -c Release` 补一次。
   这是 §8.15（publish 不刷新 plugins）的同族问题。
2. **`webview2\`（Fixed Runtime，860.8 MB / 917 文件）不是 publish 产物**，是随包带的第三方运行时。
   本机只有上一个里程碑包里有同一版本 ⇒ `robocopy /E` 取过来并**回读文件数**（917 = 917）。
3. **`Assets/geogebra`、`plugins\说明.txt`、署名文件已由 csproj 纳入发布流程**
   （`Content` / `None` + `TargetPath`），publish 自动带出 —— 校验过包内 `geogebra/` 28 个文件与源码
   逐条同名同大小。**手工只剩"插件 dll + webview2"两项**，别再手工复制那三样（会双份）。

### 9.8 ★ 包本体冒烟 + zip 回读终检（M8 S4 新立）

**"Debug 过 = 交付过"不成立**：交付的是 Release **自包含**那一份（配置不同、运行时是随包自带的）。
所以打包前把同一套冒烟再跑一遍，exe 换成**包目录里的**（`dist/.../MathPhys.Ink.exe`），
并且**顺手验随包样例文件**（老师拿到包第一件事就是双击它）：

- 随包的外挂样例工程能不能被打开（日志出现"工程已打开…（外挂…）"）；
- 随包那份**手写 PDF** 能不能被 pdfium 解析（日志给出"共 N 页"）；
- 指纹对不对得上（不报"不是同一份文件"）；
- 写文件类场景**在临时副本上做**（`shutil.copytree` 整份样例到临时目录），别把包里原版改脏。

**zip 终检**：压包用 PowerShell 的 `Compress-Archive -Path "<包目录>\*" -DestinationPath "<zip>"`，
★ `\*` **不能漏** —— 漏了会把包目录本身当一级目录塞进去，老师解压出来是 `包名\包名\程序.exe`。
压完**回读条目名**再判定（别只看"文件存在"）：

```python
names = zipfile.ZipFile(zip_path).namelist()
assert "MathPhys.Ink.exe" in names                      # 顶层直接见 exe
assert not [n for n in names if n.startswith("包名/")]        # 没有多套一层
```

再逐条核关键文件（主程序 / 操作卡 / 许可署名 / 每个插件 dll / 运行时 / 样例），
以及**不该在包里的东西**（验收用插件 `gfxdemo`、插件目录里重复的契约 dll）。

## 10. 导出试卷（M9）

### 10.1 ★ `RenderTargetBitmap` 是"同步抓帧"：换完 `Image.Source` 必须先 `UpdateLayout()`

M9 S1 唯一一条**生产代码** bug（真机回归 645 PASS / **5 FAIL**，红的全是"某页是白纸"）。

`RenderTargetBitmap.Render(Visual)` **不跑渲染队列** —— 它抓的是该 visual **当前已有的渲染数据**。
所以 `Image.Source = 高清图` 之后只调 `InvalidateVisual()`（意为"排一次重绘"）是**不够的**：
配合同步抓帧 ⇒ 抓到换图**之前**的空内容 ⇒ 7 页里 5 页白纸
（页面白底矩形在、页面位图不在）。

```csharp
var surface = _host.RenderSurface;
if (surface is FrameworkElement element) element.UpdateLayout();   // ★ 少了这句就是白纸
var rtb = new RenderTargetBitmap(w, h, ExportGeometry.BitmapDpi(), ExportGeometry.BitmapDpi(), PixelFormats.Pbgra32);
rtb.Render(surface);
```

推论：**凡"离屏抓帧"都必须先让布局/绘制到位再抓**，别指望 `InvalidateVisual` 帮你。
排查指纹：白纸的典型特征是"白底矩形在、位图内容不在" —— 说明可视树没问题，问题在**抓帧时机**。

### 10.2 ★ `RenderTargetBitmap` 背景是全透明 ⇒ 判"是不是白纸"必须先合成到白底

RTB 没画到的地方是 `alpha=0, RGB=0`。**直接读 RGB 会把透明当纯黑** ⇒
"整页白纸"（全透明）被判成"深色像素占 100%" —— 一条**假通过**，
正好把 §10.1 的真 bug 掩盖过去（第二遍回归才红出来）。

```python
coverage = a / 255.0
lum = raw * coverage + 255.0 * (1.0 - coverage)   # ★ 合成到白底再算亮度
```

同一个前提取两遍：一是"是不是白纸"，二是"平均亮度 / 深色占比"这类判据的基准。
**凡拿 RTB 做图像判定的地方，第一件事就是合成到白底。**

### 10.3 ★ 宿主"永不降级"规则会决定观察点顺序（先低后高，不是先高后低）

`CanvasViewportHost.OnPageRendered` 里有一条：

```csharp
if (e.LevelIndex <= _displayedLevels[i]) return;   // 永不降级
```

⇒ 已经是高清档时再缩放**不会**换回低清档。所以"验证导出与屏幕缩放无关"这条断言，
若观察点写成"先 2.0 倍、后 0.25 倍"，两次渲染拿到的其实是**同一张**屏幕位图，
"两张一模一样"恒成立 —— **空断言**。
必须**先低后高**（低倍时该页档位是 `-1`，会真的重建一档），前提才真的变了。

配套要求：这类断言**必须自带一条"观察点自检"**，把"前提真的变了"
（本次实测：两次之间屏幕位图宽 **198px → 1587px**）也做成一条会红的断言。
否则前提一旦失效，结论就变成白给。

### 10.4 ★ 导出画质不能靠"当前屏幕那张位图"：必须临时换成 200dpi 底图

屏幕上那张位图的分辨率由 `RenderLevels.ForScale(viewport.Scale)` 决定 ⇒
**老师当时缩到 25%，导出来就是一张 198px 宽的糊图**（尺寸对、内容糊，最难发现的那种坏）。

正解：`CanvasViewportHost.OverridePageImage(pageIndex, highRes)` —— 换 `Source`，
**同时把 `_displayedLevels[pageIndex]` 顶到 `RenderLevels.MaxIndex`**
（否则后台迟到的那次低清渲染会把高清图顶掉，导出正好抓到被顶掉的那一帧）。
返回一个 `IDisposable` 令牌，`Dispose` 时还原 `Source` + 档位（借用一律成对、幂等）。
高清图本身走 `IPdfDocumentService.RenderPage(pageIndex, zoom)`，
`zoom = dpi/96`（**这个接口的 zoom=1 表示 96dpi**），同步返回、已 Freeze。

三个数别混：`RenderDpi=200` → 换算 `ZoomForDpi≈2.083`（喂 RenderPage）
→ `BitmapDpi = 96×dpi/72 ≈ 266.67`（喂 RenderTargetBitmap）。详见 `docs/14` §2。

### 10.5 ★ `keybd_event` 是全局注入、**只送给前台窗口**

M9 S1 冒烟第一次跑出 **7 FAIL**，症状是"按了 Ctrl+E，什么都没发生，**日志一行都没有**"。
根因不是功能坏了 —— 是**焦点不在被测窗口上**，键盘事件送给了别人。

`PrintWindow` 截图**不会**把窗口带到前台。M8 S3 之所以没踩到，是它按热键**之前**
先做了一次真实鼠标拖动（`draw_marks`），顺带把窗口激活了。

对策（已写进 `artifacts/smoke_m9s1.py`）：
1. 先点一下窗口（本次点**状态栏中心**）抢回前台焦点；
2. **把它做成一条前置断言** —— `GetForegroundWindow() == hwnd` 不成立就当场红，
   而不是让后面 7 条一起红、把人引到错误方向；
3. **每次**注入热键之前都调一次（第二次导出同样要）。

附带一条通用判据：真机 UI 冒烟里，**"按键毫无反应" 与 "功能坏了" 外观完全一样**。
先验焦点，再验功能。

## 11. 导出整卷 PDF（M9 S2）

### 11.1 ★ PdfSharpCore 的 `XImage.FromStream` 收的是**开流工厂** `Func<Stream>`，不是流

```csharp
// ✗ 编译不过（CS1503：cannot convert from 'MemoryStream' to 'Func<Stream>'）
using var image = XImage.FromStream(new MemoryStream(bytes));

// ✓ 每次要图时由库自己开一条新流
var image = XImage.FromStream(() => new MemoryStream(bytes, writable: false));
```

它要工厂而不要流，是因为**同一张图可能被读多次**（尺寸探测一次、落盘一次），
每次都必须是"从头开始"的一条干净流 —— 拿同一条流读第二遍会读到结尾，图片**静默丢失**
（页数对、尺寸对、文件也不小，就是每页全白）。

推论（内存口径）：**图在 `Save` 之前不能释放**，`XImage` 要攒到 `Save` 之后再统一 `Dispose`。
所以别写"一页一取一放、峰值只多一页"这种注释 —— 那是假的。真实峰值 ≈ 全部页面的编码字节 + PDF 结构
（30 页 A4@200dpi ≈ 60 MB，可接受）。真正的风险不在这些字节，而在**解码后的位图**
（单页 1654×2339 解出来 ≈ 15 MB，30 页就是 450 MB）——
所以**绝不要"提前把所有页都解码出来校验一遍"**，那是把内存翻十倍换一个肉眼就能看出的东西。

### 11.2 ★ PDF 页尺寸必须是 **PDF point**；横向页要**先设 `Orientation`、再设 `Width/Height`**

- **别把像素当 point**：A4 是 `595.28×841.89` **point**。传 `1654×2339` 进去不会报错，
  只是得到一页约 **58×82 厘米**的巨幅页面 —— 打印一页装不下，而页数、体积、能不能打开全都正常。
- **横向页有顺序坑**：PDFsharpCore 的 `PdfPage.Width/Height` 是**按 `Orientation` 解释**的
  （横向时 Width 指长边）。所以要：

```csharp
bool landscape = w > h;
page.Orientation = landscape ? PageOrientation.Landscape : PageOrientation.Portrait;  // ★ 先方向
page.Width  = XUnit.FromPoint(w);                                                     // 再长宽
page.Height = XUnit.FromPoint(h);
```

顺序写反 ⇒ 横向卷子在 PDF 里被转成竖的（内容挤在中间一条），**照样不报错**。
枚举在 `PdfSharpCore.PageOrientation`（**不是** `PdfSharpCore.Pdf`）。

**怎么验**：别信自己数出来的页数。用 **pdfium 把产物读回来**
（`PdfiumDocumentService.Open(导出的pdf)` → `PageCount` / `GetPageSize(i)`），
再 `RenderPage(i, zoom)` 渲一页数深色像素 —— 这才是"页里有东西"的硬证据。
harness 里专门造了一页**横向 A4** 来钉死 11.2（实测回读 `841.89×595.28`）。

### 11.3 ★ PDF 里的非 ASCII 字符串是**十六进制串** —— 别用「原文找字符串」验元数据

写 `document.Info.Title = "某份卷子"` 之后，想验"标题真的进去了"，第一版是
**按 UTF-8 / UTF-16BE / UTF-16LE 三种编码去文件里找那串字符** —— 三种都找不到，报 FAIL。
**但标题其实写进去了**：

```
/Title <FEFF6A2A7AD654044E009875>      # 6A2A=横 7AD6=竖 5404=各 4E00=一 9875=页，FEFF 是 UTF-16 BOM
/Creator <FEFF55106CE27684767D677F>    # 数理墨
```

PdfSharpCore 对非 ASCII 字符串按 PDF 规范写成 **`<hex>` 十六进制串**；
文件里那是一串 ASCII 数字，**按原始编码去找当然一次都找不到**。
所以正确姿势是**按规范解码**，而不是猜库用什么编码：

```csharp
// 找到 /Key 所在那一行里的 <...>，每 4 个十六进制位 = 一个 UTF-16 码元，最后去掉 FEFF BOM
string? ReadPdfString(string file, string key) { /* 见 tools/PdfSmokeTest/Program.cs 的 RunM9S2Checks */ }
```

★ 只在**同一行**内找 `<` `>`：不然会窜到后面某个对象里，把别人的字符串读回来当成标题。
顺带把断言加强成"解码出来**正好等于**我传进去的那个值" —— 只验"文件里有 /Title 这个键"
等于没验（键在、值是空的或写错的常量，一样绿）。

**这是我第五次栽在"猜序列化格式"上**（前四次：中文断言串里的 ASCII 双引号截断、
十六进制颜色大小写、JSON 转义、Base64 换行）。通用规则：
**产物里读回来的东西，一律按它的规范去解，别按"我以为它会怎么写"去搜。**

### 11.4 小坑：内层块的局部变量不能与外层方法体里**声明过的**名字重名（CS0136）

同一方法里先写 `double r1 = DarkRatio(...)`（在 `using` 块内），后面又写 `var r1 = svc.ExportPdfTo(...)`
（在方法体里）⇒ **CS0136**。

反直觉的点：**外层那句写在后面也照样冲突** —— C# 的作用域规则看的是"整个方法体声明了哪些名字"，
不是"执行到哪一行"。长方法里尤其容易撞（`r1` / `i` / `tmp` / `ok` 这些短名字）。
本机的对策：**判据变量一律取有含义的名字**（`darkPortrait` / `darkLandscape`），
别用 `r0` / `r1` 这种 —— 顺带也让断言输出好读。

### 11.5 断言的 detail 文本别写成"失败口径"

```csharp
// ✗ 第三个参数是 detail，**无条件打印**。这句读起来像红的，断言却是绿的
Report("元数据里写了 /Title", ContainsAscii(path, "/Title"), "/Title 未在文件里出现");

// ✓ 中性事实
Report("…", ok, "解码得到 «" + value + "»");
```

现场只有这份输出、没人能重跑时，"绿的看起来像红的"会直接把人带错方向。

## 12. 工程与导出的接缝（M9 S3）

S3 的题目叫"从 `.twb` 内嵌 PDF 导出"，但它真正处理的是**一道接缝**：
M8 打开工程时把内嵌 PDF 落到临时文件，M9 拿这份临时文件去渲染导出。
接缝两边各自都是好的，坏起来也**只有接缝处会坏**。

### 12.1 ★★ 「不可断言的接缝」比一个 bug 更值钱

M8 把"内嵌 PDF → 临时文件"写成了 `MainWindow` 里的私有方法 `WriteEmbeddedPdfToTemp`。
功能是对的，代价是**断言不到**：harness 里造不出这个动作，"从 `.twb` 内嵌 PDF 导出"整条路
就只能靠人去点界面验。S3 把它搬成 `Ink/EmbeddedPdfReleaser`，接缝立刻有了 15 条断言。

判据：**一个动作如果只能在界面里发生、harness 里复制不出来，它迟早会静默坏掉。**
（这次就坏了两处，见 §12.2 与 §12.3 —— 两处都是搬出来之后**当天**就抓到的。）

### 12.2 ★★ 临时文件名绝不能变成成品名

`.twb` 内嵌的试卷被释放到
`%TEMP%\MathPhys.Ink\工程卷面\<工程名>-<8 位随机>.pdf`。
基名只要从**路径**取，老师就会拿到 `静电场复习卷-3f9a1c02-第01页.png`；
更糟的是"关掉工程再打开"会产生**另一个**随机名 ⇒ 同一次会话里两次导出的文件名对不上。

```csharp
// ✓ 工程模式只认工程标题；标题为空就兜底，**永不**去看路径
public static string BaseName(bool hasProject, string? projectTitle, string? pdfPath)
    => hasProject ? Safe(projectTitle) : Safe(ProjectComposer.DefaultTitle(pdfPath));
```

**怎么验出来**（这是本条最值钱的部分）：把"工程标题 / `.twb` 文件名 / 内嵌卷名"三者
**刻意取成互不相同** —— 标题=内嵌工程冒烟卷、工程名=冒烟工程文件、卷名=26西附全真模拟1物理试卷。
这样走错任何一条路都会得到一个**可辨认的错名字**（`冒烟工程文件-xxxx-第01页.png` /
`26西附全真模拟1物理试卷-第01页.png`）；三者相同时，走错路也会得到同一个名字，断言照样绿。
这是"观察点要有区分力"的又一例（同 §10 的"先低档后高档"）。

### 12.3 ★ 释放出来的临时文件必须带随机后缀，且两次释放得到两个路径

固定名（`<工程名>.pdf`）在"关掉工程再打开"时会去写第二份，而第一份**可能仍被 pdfium 打开着**。
运气好是写不进去，运气不好是渲染读到一半被替换的内容 —— 两种都不出声。
所以后缀是 `Guid.NewGuid().ToString("N")[..8]`，并且断言写成
**"两次释放得到两个路径、且两个文件都还在"**，而不是"文件名不同"。

### 12.4 ★ 清理临时文件必须排在"关掉文档"之后（M8 起就没生效过）

```csharp
// ✗ 曾经的样子：_embeddedReleaser.Cleanup() 排在 _viewModel.Dispose() 之前
//   自己还开着这个 PDF 就去删它 ⇒ Windows 直接拒绝
//   「临时试卷文件未能删除：… —— The process cannot access the file because
//     it is being used by another process.」
// ✓ 正确顺序
_viewModel.DocumentChanged -= OnDocumentChanged;
// … 其余解绑 …
_viewModel.Dispose();        // ← pdfium 在这里才松手
_embeddedReleaser.Cleanup(); // ← 现在才删得掉
```

危害是**完全静默**的：界面上毫无痕迹，只在日志里留一行 warn，老师机器上临时目录一份份攒下去。
**这是 S3 新增的那条冒烟断言（"关掉程序后临时试卷必须消失"）当场抓出来的**：
M8 的冒烟只验"打开工程后卷面在不在"，没人验"关掉之后清没清"。

### 12.5 ★ 清理失败时不要把登记清空 —— 登记表是"还没删掉的"

```csharp
// ✗ foreach … finally _released.Clear();
//   顺序万一排错，这一份临时卷面**从此再也没人管**，也丢掉了"还剩几份没清"这个信息
// ✓ 只把真正删掉的摘掉；删不掉的留在表里，下一次调用还能再试
for (int i = _released.Count - 1; i >= 0; i--)   // 倒着走：一边删一边 RemoveAt，正着走会漏
{
    try { if (File.Exists(path)) { File.Delete(path); removed++; } _released.RemoveAt(i); }
    catch (Exception ex) { AppLog.Warn($"临时试卷文件未能删除：{path} —— {ex.Message}"); }
}
```

配套：`Count` / `Paths` 的语义跟着变成"**尚未删掉**的那些"，`Cleanup()` 幂等（全删完再调返回 0）。
harness 里用"`FileShare.None` 占住 + 放开后再调一次"把这条钉死 —— 顺带说明
"删不掉返回 0"是**故意**的（删不掉不该打断退出流程），正因如此**顺序**必须由真机冒烟盯住。

### 12.6 ★ 释放失败要返回 `null` + 日志，由界面给一句人话

临时目录不可写（磁盘满 / `%TEMP%` 指向不存在的盘 / 被安全软件锁住）时：
工程仍然算"打开了"（批注与视图都在），但老师看到的是一片空白画布 ⇒ 只会以为工程文件坏了。
所以 `Release` 返回 `null`（**不抛异常**，那时工程已经装了一半），调用处明确说清
"无法把工程里的试卷释放到临时文件（临时目录不可写或磁盘已满），批注已恢复……"。

harness 稳定复现失败的办法：把目标目录的位置**用一个同名文件占着** ⇒ `CreateDirectory` 必抛。

### 12.7 ★ 文件名清洗只有一处，且要去掉结尾的点与空格

```csharp
string result = …把 Path.GetInvalidFileNameChars() 换成 '_'…;
return result.Trim().TrimEnd('.');   // ← 这一句不能省
```

Windows 的文件名规则里，结尾的点与空格会被**静默丢掉**：工程标题写成"静电场."，
落盘却变成 `静电场.png`，而程序记着的是带点的那份 ⇒ 下次"重新导出"会因为路径不存在
报一个与事实无关的错。**"程序记的名字必须等于盘上的名字"**，与 §11.3 的"按规范解码"
是同一个家族。

### 12.8 兜底名只能有一个值

`PngWriter.FallbackBaseName` 与 `ExportNaming.FallbackBaseName` 必须同值，
harness 直接断言两者相等 —— 不一致时，同一份"没名字的卷子"导 PNG 与导 PDF 会得到两个不同的名字，
而这种不一致只有把两个产物摆在一起才看得出来。

## 13. 打包链路上的两个新坑（M9 S4）

### 13.1 ★ 沙箱会拦「批量删除」（文件数 > 50）⇒ 清目录请用**重命名**，不要删

M9 S4 想先清空旧的 `dist/tablet`（480 个文件）再发布，被安全策略拦下：

```
[safe-delete][SAFE_DELETE_BULK_CONFIRM_REQUIRED] {"count":480,"threshold":50,"scope":"turn",...}
```

表现很迷惑：命令 `Exit Code: 1`、**没有异常栈**，只有上面那行 JSON。
而命令是 `python -c "shutil.rmtree(...)" && dotnet publish ...` ⇒
**`&&` 后面的 publish 根本没跑**，但你看到"清理那步没报错"会以为正在发布。

**做法**：需要"全新目录"时**不要删**，**重命名**旧目录即可 ——
重命名不在批量删除的判定里，而且**不丢数据**，比删安全：

```python
if os.path.isdir('dist/tablet'):
    os.rename('dist/tablet', 'dist/_stale_tablet_m74')   # 不删，只改名
```

（代价是旧目录会一直躺着，需要人工清理；但"多发一份数据"远好过"误删了还得重来"。
真正省事的办法见 §9.7 的思路与 `MEMORY.md`：**publish 直接输出到包目录**，压根不需要清中转目录。）

### 13.2 ★ 要"动桌面会话"的脚本（截图 / 启动 exe）必须用**带 Pillow 的那个 Python**

托管 Python 3.13.12 里**没有 Pillow**：

```
ModuleNotFoundError: No module named 'PIL'
```

而项目历来的冒烟脚本都靠 `PIL.ImageGrab` 截图（M7.2.1 / M7.4S5 / M9 S1~S3 都是）。
可用的是隔离 venv：

```
~/.workbuddy/binaries/python/envs/default/Scripts/python.exe   # Pillow 12.3.0
```

**判据**：脚本里出现 `ImageGrab` / `Pillow` / 要启动 GUI 进程 ⇒ 一律用这个 venv 跑；
纯逻辑 harness（`tools/_run_harness.py`、`PdfSmokeTest`）用托管 Python 即可。
误用托管 Python 的表现是**脚本第一行 import 就死**、什么都没测 ——
比"跑了一半失败"更浪费时间，因为输出里只有一行 ModuleNotFoundError。

## 14. 多形态交付：同一份产物出两个包（M9 S5）

背景：M9 起**固定交付两个**测试包 —— 完整版（含 GeoGebra 演示面板，随包带 WebView2
Fixed Runtime）与轻量版（不含）。两包解压体积差 880 MB。做法沉淀在
`tools/_m9_pack.py --variant lite|full|both`。

### 14.1 过滤，而不是 publish 两次

两个包的 exe / 程序集 / 插件必须**逐字节相同**。若各自 publish 一次，
"轻量版正常、完整版异常"这类差异就无从排查（也无法排除"两次构建产物不同"）。
所以只在**最后一步**分叉：拿同一份发布产物过滤出两个 zip，并抽样比对 SHA-256
（exe、两个插件 dll、样例 `.twb`）确认全等。

### 14.2 不落中转副本：边遍历边写 zip

不必先复制出一个"轻量目录"再压缩。`zipfile` 支持逐条 `write(源文件, 包内名)`，
所以遍历源目录时**跳过要剔除的大件**、直接写进 zip 即可 —— 省掉 180 MB（轻量）
甚至 1 GB（完整）的磁盘副本。附带好处：**不需要删除任何目录**，避开了沙箱的
批量删除拦截（§13.1）。

### 14.3 派生文本：锚点命中数必须断言为 1

轻量版的操作卡与署名文件**由完整版派生**（替换 11 处、删 2 行、整文替换 1 份）。
派生最怕"改了一版、漏了一处"：改完读起来像对的，细看还留着"7 个插件"、`geogebra\`。
约定：每处锚点先 `count(old)`，**必须恰好 1**，否则抛错、**不写 zip**。
这样漏改会立刻失败，而不是悄悄交付一个自相矛盾的包。

### 14.4 校验判据本身也会写错：区分「不该有」与「合法提及」

同一个错误本轮犯了**两次**，症状都是"包明明是对的，校验却报 FAIL"：

| 写错的判据 | 为什么会误报 |
|---|---|
| `"geogebra\\" not in 操作卡` | 轻量版操作卡**合法地**写了一行"本包没有 geogebra\ 与 webview2\ 两个文件夹" |
| `"geogebra" not in 启动日志` | 宿主启动时会**无条件**探测一次 GeoGebra 资源，必然留下一行降级 WARN（§14.5）|

通则：**"不该有"要落到结构上判**（"这条目录行不存在"、"这个插件没被加载"），
不要用"某个字符串不出现"这种全文判据 —— 文本里出现该字符串往往是**在说明它没有**，
恰恰是正确实现的证据。判据过糙会把绿的说成红的，比漏判更伤信任。

### 14.5 待定：宿主启动无条件探测 GeoGebra，轻量版必留一行误导 WARN

`src/MathPhys.Ink/GeoGebra/WebView2PanelBackend.cs` 在**启动早期**（插件扫描之前）
探测 `geogebra/` 离线资源目录，缺失即写 WARN：

```
GeoGebra 演示面板不可用：GeoGebra 资源未部署（缺少 geogebra 目录），请重新解压完整测试包。
```

- 对**完整版**：正常（资源确实该在）。
- 对**轻量版**：**措辞误导** —— 用户本来就不打算用 GeoGebra，却被建议"重新解压完整测试包"。
  功能无影响（没有插件 ⇒ 没有按钮 ⇒ 走不到面板），但测试时翻日志会困惑。

两个候选方案（**待用户点头，本轮未动生产代码**）：

1. **按需探测**：把"探测资源 / 提示降级"的时机从"启动时"挪到"插件请求创建面板时"。
   插件不在 ⇒ 压根不探测、不提示。语义最正，但动的是 M7.5 的初始化时序。
2. **降级措辞分档**：保留启动探测，只把提示改成"未部署 GeoGebra 离线资源
   （本版可能本身就是不含它的轻量版）"。改动最小，只动一句日志文案。

## 15. 交付目录清理与「交付物的源」（M9 收尾）

> 起因：M9 交付后用户要求只保留两个 M9 测试包，`dist/` 从 7.4 GB 清到 1.5 GB。
> 清理本身很顺，但**清的过程中暴露了一个真隐患**，值得单列一节。

### 15.1 ★★ 交付物的「源」不能只活在暂存目录里

包内操作卡 `怎么测试.txt` 在 M9 S4 是**手工写进 `dist/tablet/`** 的 —— 仓库里没有副本。
清空暂存目录后，它的源头就只剩已交付 zip 里那一份。

为什么危险：`tools/_m9_pack.py` 要靠它**派生轻量版操作卡**（锚点替换），
而它的 `--variant full` 分支**根本不读这份文本** ⇒ 源目录缺了操作卡时，
完整版会**安安静静打出一个没有操作卡的包**，直到 `verify()` 才报 FAIL（那时 zip 已落盘、
并且看起来「打成功了」）。

处置（三件一起做才算修好）：

1. **提回仓库**：从交付 zip 里取出，落到 `src/MathPhys.Ink/Assets/怎么测试.txt`；
2. **接进 publish**：csproj 加 `None` 条目 + 显式 `TargetPath`（同署名文件那样），
   publish 自动放到包顶 —— 改内容只改这一个文件，两个包自动同步；
3. **前置校验**：`_m9_pack.py` 的 `build_zip()` 在**写 zip 之前**就查
   `怎么测试.txt` / `第三方许可与署名.txt` 在不在，缺了立刻抛错。

通则：**凡是「随包交付但不是构建产物」的文件（操作卡、署名、样例、离线资源），
都必须在仓库里有唯一权威副本，并挂在 publish 或打包脚本上。**
「手工往暂存目录里摆一份」等于把交付物的源头放在一个迟早会被清理的地方。

### 15.2 不可再生的随包资产要单独记账

`webview2/`（WebView2 Fixed Runtime，860 MB / 917 文件）既不在 publish 输出里，
也不在 `Assets/` 里 —— 它只存在于**已交付的完整版 zip 内**。这次清理差点连
「M8 包目录」（当时的取用来源）一起删掉。

现在唯一留存处 = `dist/白板M9-导出测试包.zip`；取回方式固化进
`tools/_m9_rebuild_stage.py` 第 3 步。**清目录前先自问：哪些资产是「只在磁盘上」的？**

### 15.3 重建打包暂存目录（四步，顺序不能换）

```bash
python tools/_m9_rebuild_stage.py            # publish -> 铺插件 -> 取 webview2 -> 造样例
python tools/_m9_pack.py --variant both      # 再打两个包
```

1. `dotnet publish … -o dist/tablet`（★ publish **只增不删**：目标非空必须先挪走，
   否则陈旧文件留在暂存目录里、进而混进包内，包内文件集就不再等于源文件集）；
2. `tools/_stage_plugins.py --out dist/tablet --config Release`（★ publish 不刷 `plugins\`，§8.15）；
3. 从**已交付的完整版 zip** 取回 `webview2/`；
4. `tools/_m9s4_make_samples.py`（样例必须现造：`.twb` 里存着小试卷指纹，见 §14）。

### 15.4 ★ 试跑模式必须没有副作用

`_m9_rebuild_stage.py --probe N` 用来在**不落 860 MB** 的前提下验证 webview2 的
筛选与解包逻辑。第一版把试跑判断写在 publish **之后**，结果「试跑一下」
凭空 publish 出一个 201 MB 的暂存目录 —— 与「只留交付包」的清理目的正相反。

通则：**「只验证不产出」的开关要放在会产生副作用的那一步之前**，
否则它会变成「顺手干了一半真活」的按钮。

### 15.5 清理脚本要自带护栏与收尾断言

`tools/_m9_cleanup_dist.py` 的做法可复用：

- **白名单式**：只列待删项，不遍历删除；每项先按**绝对路径**校验确实在 `dist/` 之下；
- 待删名单与保留名单**冲突即抛错**；每删一项后**实时复检保留项还在**（防误伤）；
- 收尾打印 `dist/` 现状并断言「白名单外零残留」；
- 配 `--dry-run`：先出清单与体积，人点头再 `--go`。

★ 批量删除（>50 文件）仍会撞沙箱拦截（§13.1）：这次实删是以
「越权执行（已获批准）」方式跑的 —— 也就是**每次都要过一次确认**，
别把「上次能删」当成「以后都能默默删」。

## 16. 界面设计系统（M10）

### 16.1 ★★ 锁屏桌面下「系统截图」会骗人：ImageGrab 抓到锁屏、PrintWindow 拿到旧帧

M10 真机冒烟第一次跑出来 5 个 FAIL，截图里工具栏**少了「墨色」标签与 5 个色块**。
顺着截图去查，结论会是"新设计系统把一组控件弄没了"—— 而产品完全正常。

真相（要在**同一次运行内交叉验证**才看得出来）：

- 会话**锁屏**时 `ImageGrab.grab()` 抓到的是**锁屏界面本身**（壁纸、时钟），不是程序窗口；
- `PrintWindow(hwnd, dc, PW_RENDERFULLCONTENT)` 从 DWM 拿到的**不是当前视觉树**：
  它给出的那一帧里工具按钮的宽高是真实值的 **1.5 倍**（另一个 DPI 缩放状态），
  行高、换行位置全都不同 —— 于是"少了一组控件"只是那一帧的排版结果。

当时用来定案的四层证据（逐层排除，缺一层都不够）：

1. **XAML 结构解析**：`墨色` 与 `ColorButton0..4` 确实是工具栏 WrapPanel 的孩子；
2. **产物核对**：`bin\...\MathPhys.Ink.dll` 的 BAML 里**有** `墨色`，
   且构建时间晚于源文件（排除"改了没编译"）；
3. **运行时读视觉树**（临时插一段诊断）：25 个孩子全部 `Visible / IsVisible=True`，
   `ColorButton0..4` 各 40×40，`Background` 就是 `#FFFF0000 / #FF1A1A1A / …`；
4. **WPF 自己渲染一张图**：色块清清楚楚在工具栏上。

★ 通则：**凡是"从外部取帧"的取证手段，都要先证明这一帧可信，再拿它谈判据。**
否则一次"取帧失败"会被当成产品缺陷，而且**证据看起来非常确凿**（有图、有像素统计）。

### 16.2 ★★ 让产物自己报真值 —— 判据里不许再手抄一份期望值

修法：新增 `Design/UiShotHook.cs`，环境变量 `M10_UI_SHOT=<目录>` 门控
（不设则一行代码都不执行）。

- 窗口构造完成后（`DispatcherPriority.ApplicationIdle`：布局与首帧都已就绪）
  用 `RenderTargetBitmap` 把主窗口渲染成 `ui-a.png`；
  再 `ThemeService.Toggle()` + `UpdateLayout()` 渲染 `ui-b.png`；
- 同时写出 `ui-shot.txt`：每张图的主题名、`Ui.ChromeBackground` 的 `#AARRGGBB`、
  以及 `InkPalette.Colors` 的 5 个墨色真值；
- 然后 `Application.Current.Shutdown()`（自动化跑完即退，不留进程）。

冒烟脚本 `artifacts/smoke_m10.py` 读 `ui-shot.txt` 拿期望值，再去数两张图的像素 ——
**脚本里没有一个手抄的颜色**。

★ 与 `M75_GGB_SELFTEST` 同属"环境变量门控的自测钩子"这一套做法：
**程序能自己说清的事，不要靠外部猜。** 附带好处：一体机上验收也不用再截图。

### 16.3 ★ 工具栏换行：一个 ItemsControl 是不可拆分的，别指望它自己排好

工具按钮由一个 `ItemsControl` 生成，它在 `WrapPanel` 里是**一个**孩子 ⇒ **不能跨行拆分**。
于是"视口那一小段 + 1371px 的工具块"放不进一行时，整块工具被推到下一行，
**上一行右侧会空出一大截**。看起来像排版溢出，其实是 WrapPanel 的正常行为。

结论：

- **按语义分行**（M10 用两个 WrapPanel：文档/工程一行，视口/工具/笔一行），
  不要让一个巨大的 WrapPanel 自己换行；
- **常驻操作钉住**：主题按钮与窗口模式按钮放进第一行的 `DockPanel.Dock="Right"`，
  这样工具栏怎么换行都挤不掉它们（一体机上这两颗是"出得来、回得去"的保险）。

### 16.4 ★ 换肤 = 原地替换「界面板」那一本字典

`ThemeService.Apply` 按 `Source` 认出界面板字典并**原地替换**，其余字典不动。

- 三套板：`Ui.*`（随主题翻转）｜`Ink.*`（墨迹，**唯一来源** `InkPalette.cs`）｜
  `Canvas.*`（纸白 / 图形默认色 / 选中框 —— **会被导出**，永不翻转）；
- 铁律：**会随主题变的引用必须 `DynamicResource`**。`StaticResource` 在加载时解析、
  换肤不会刷新它（最外层 `Window.Background` 写成静态就会留一圈旧底色）；
- 令牌都 `po:Freeze="True"`，否则跨窗口可能串色。

### 16.5 ★ harness 里的控件也需要「资源底子」

M10 之后控件构造要解析 `{StaticResource Canvas.PageWhite}` 这类令牌，
而独立跑 harness（没有 `Application`）时资源字典是空的 ⇒
构造函数抛 `XamlParseException: 找不到资源 Canvas.PageWhite`。

做法：harness 启动时调 `InitializeDesignResources()`，**只在没有 `Application` 时**
自己造一套离线资源；C# 侧一律走 `Design/Tokens.cs`，查找顺序 =
注入字典 → `Application.Current.Resources` → 离线自建。

★ 通则：**测试环境的资源底子必须和真机一致**，否则测试要么起不来、
要么测的不是真东西。

### 16.6 ★ 扫「裸色值」要给词边界：`InkPalette.Colors.Count` 里的 `Colors.` 不是色值

正则扫 `Colors.` / `Brushes.` / `Color.From*` 时，`InkPalette.Colors.Count`
这类**成员访问**会被误判 ⇒ 假 FAIL。

做法：加否定后视，前面是 `.` 或标识符字符就不算：

```
(?<![\w.])Colors\.     (?<![\w.])Brushes\.     (?<![\w.])Color\.From(?:Argb|Rgb|ScRgb)
```

（`Colors.Transparent` / `Brushes.Transparent` 是合法例外，用 `(?!Transparent\b)` 放行。）

### 16.7 ★ 改了包内操作卡，打包脚本的锚点必须同步改 —— 而且要在**写 zip 之前**炸

`tools/_m9_pack.py` 由完整版操作卡**派生**轻量版（局部替换 + 整行删除），
每条锚点都断言**命中数恰好为 1**，对不上直接抛错、**不写 zip**。
M10 换标题（`M9 测试包（导出` → `M10 测试包（界面`）时这条断言立刻生效，
逼着两边一起改 —— 这正是它该有的样子（§14.3、§15.1）。

包名跟随里程碑：`白板M10-界面测试包.zip` / `白板M10-界面测试包-轻量版.zip`。
（脚本文件名仍叫 `_m9_pack.py`：它诞生于 M9，从 M9 起就是本项目的通用打包脚本。）

### 16.8 交付前的「插件 Release 体检」仍不可省

这次 `dotnet build MathPhys.Ink.sln -c Release` 又一次把
**`VectorArrow` 与 `PdfSmokeTest.Plugin` 编到了 `bin\Debug\`**
（sln 里这两个工程的**配置映射缺 Release** —— §9.7 的根因）。

## 16. M12 —— 个人教学工作流（2026-09-23）

### 16.1 ★ 宏热键会被 Ctrl switch 吃掉：带 when 的 case 必须排前面（老规矩再踩一次）

`OnPreviewKeyDown` 里宏热键块（Ctrl+Shift+D1~D9）**必须排在** `switch (e.Key)` 的
`case Key.D1`（无 when，"原始大小"）**之前** —— switch 按顺序匹配，排在后面永远轮不到。
这和 Ctrl+Shift+S / Ctrl+Shift+E 是同一条纪律，第三次出现。

### 16.2 ★ `Point.ToString(string)` 不存在

`Point` 只有 `ToString()` 与 `ToString(IFormatProvider)` —— `$"{p.Value.ToString("F1")}"` 直接
CS1503。要格式化就写 `$"{p.Value.X:F1},{p.Value.Y:F1}"`。

### 16.3 ★ harness 里摸不到宿主 internal 类型：把「内部状态」换成「可观察行为」断言

`GfxObject.ContentVersion` 是 internal（harness 无 IVT），不能 `is GfxObject` 读版本号。
换成更强的可观察断言：真 `GfxObjectLayer` + rebase 前后各取一次 `VisualFor(id)`，
`!ReferenceEquals(before, after)` —— 版本号存在的目的就是换视觉实例，断行为不断状态。

### 16.4 ★★ store 的「拖动改参数」只对**绑定坐标系**的曲线生效

`GfxObjectStore.UpdatePose` 的 rebase 分支在 `FindBindTarget(obj)` 成立时才走
（自由曲线拖位姿本就是正确设计）。给 harness 造 rebase 测试对象时：
- 必须带 `bindTo`（+ bindRelX/Y/Rot = 0 + unitWorld）；
- **绑定归位后锚点 = 坐标系中心**（不是 draft 里的 Center —— 写错位置，两帧增量全是错的）；
- `IsPureTranslation` 要求 rotation/scale 与对象当前值逐位相等（scale 要传 obj.Scale 本尊）。

### 16.5 ★ 吸附端到端的查询点要「故意离轴远」：多目标竞争按最近者赢

坐标系同时提供网格交点与两条轴线。查询点离轴近时，轴线最近点天然比网格交点更近，
吸到轴不是 bug。断言网格吸附时把查询点放到离轴远的位置，别让两类目标打架。

### 16.6 ★ 契约纪律的又一次兑现：M12 没动任何既有接口

新增能力全部走「新可选接口 + `is` 探测」：`ISnapTargetProvider`（渲染器实现、宿主探测）、
`IGfxPoseRebaser`（M12 未发货，接口可自由调整）。宿主内部机制（ContentVersion、
锚点增量）不进契约。插件零改动兼容。

### 16.7 ★ 像素探针设计：用「结构性位置」当判据，别用具体颜色

翻转探针数「中线上/下方的彩色像素」而不是「蓝色像素」——渲染器对 draft 色的处理
（调色板指派、覆盖）不是被测对象，判据越中性越不假红。x^2+3 的顶点在数学 (0,3)，
翻转修复后**整条**曲线在中线上方 ⇒ `above > 100 && below == 0`，修前整条在下方，
判据对翻转方向敏感（旧 e2e 的盲区正在于此）。

### 16.8 悬浮球策略必须有自己的 UI 入口

`ball.mode.off` 只登记在总线、没有菜单项 ⇒ 用户关掉球之后没有回头路（球都没了，
哪来的球菜单）。补进球菜单固定区。教训：**给"开关 X"建命令时，检查"关掉 X 后
还有没有路把 X 打开"**。

## 18. M14 —— 公式（LaTeX）与电路元件

### 18.1 ★ WPF-Math 2.x 的 API 与 0.x 完全不同（S0 spike 必须先行）

`TexFormulaParser` 要构造参数（用 `WpfMath.Parsers.WpfTeXFormulaParser.Instance`）、
`formula.Extent` 不存在（用 `RenderToGeometry` 的 `Geometry.Bounds`）、
`RenderToBitmap` 第二参是 `TexEnvironment` 不是 scale。
**矢量渲染走 `RenderToGeometry` 出 `GeometryGroup`，几何与笔刷分离 ——
外部 DrawGeometry 指定墨色刷即可染色**，不需要 SetForeground。
中文必然失败（数学字体无 CJK 字形与度量）—— 面板里要把这条边界写明白。

### 18.2 ★ harness 源级断言必须 StripComments（再踩一次）

CircuitTool 的 XML 注释里写了"刻意不实现 IGfxTool"，裸 `Contains("IGfxTool")`
直接假 FAIL。凡是对"代码里有没有某个标识符"的断言，先去注释再查 ——
M13 光标断言、M14 工具形态断言，两次同一类坑。

### 18.3 ★ bash heredoc 里的中文锚点会转码损坏

往脚本里打带全角字符的补丁，heredoc 偶发 `·`/`（` 损坏导致锚点断言失败。
对策：① 锚点用 `\u` 转义构造；② 长中文块（如 TESTCARD_EDITS）用 Write 工具
写成模板文件，Python 读文件再替换 —— 不要把大段中文塞进 heredoc。

### 18.4 导线方向：`Math.Atan2(dy, dx)` 与宿主 `Matrix.Rotate` 同向，无需换号

WPF 的 Matrix 在 y 向下坐标系里正角 = 屏幕顺时针；拖线方向角直接 atan2 得到。
前提是渲染器**不自己画旋转**（位姿由宿主施加，渲染器契约第一条）。

### 18.5 插件 UI 的"连续落"与"落一个就走"

创建型工具是否弹回选择，看的是**动线**不是姿势：
公式（通常落一两个）→ IGfxTool 弹回；电路元件（连放十几个）→ 普通指针工具不弹回。
面板/调色板一律无模式 Window（画布必须保持可点），Deactivate 时收起。

## 19. M15 —— 公式缺件热修 + 电路自动连线

### 19.1 ★ 类库插件的 NuGet 依赖不复制到 bin —— 打包 must-have 必须覆盖依赖 dll

`EnableDynamicLoading` 没加时，纯类库项目默认 `CopyLocalLockFileAssemblies=false`：
restore 成功、deps.json 记账，但 **WpfMath.dll / XamlMath.Shared.dll 不落 bin** ⇒
stage 如实照抄 ⇒ 包里只有插件主 dll ⇒ 启动日志一切正常（类型加载是懒的），
一用就"解析失败"。且**完整版与轻量版一起缺**（逐字节一致），别信"完整版没报就是好的"。
修复 = csproj 加 `<EnableDynamicLoading>true</EnableDynamicLoading>` +
打包 must-have 把依赖 dll 列全（缺了当场 FAIL）。**deps.json 不要进包**
（记的是开发机 NuGet 缓存路径，resolver 拿到死路径会跳过本地回落）。

### 19.2 ★ 插件内自算世界坐标：缩放旋转之外，平移最容易漏

插件里自己拼位姿矩阵（契约不给宿主内部类型）时，`Scale×Rotate` 顺手就写了，
**`+ Center` 最容易漏** —— 因为平时位姿由宿主施加，插件很少做完整仿射。
表现是所有引脚世界坐标整体偏一份 Center，回归一跑就红。
**断言用例必须含"旋转+缩放+平移"组合**，只测原点元件抓不住这个错。

### 19.3 角度断言按模 360，端点断言用容差

宿主 `ApplyPose` 把旋转归一化到 [0,360)：解算给的 -20.2° 存成 339.8°，
裸角度精确比较必红；端点经过 度→弧度 往返，精确相等被舍入坑掉。
harness 用 `AngleClose`（模 360）与 `CloseTo`（1e-6 容差）。

### 19.4 "复用现成接口"的每一步都要核对返回值真的够用

计划时以为"SnapToGfx + ISnapTargetProvider 就能做引脚吸附"，勘察发现
`SnapToGfx` 只返回坐标不返回身份 —— 而跟随恰恰需要"{对象Id}:{引脚号}"。
幸而 `IGfxObjectHost.Objects` 早已存在，插件内枚举自算（CircuitSnap 纯函数）
反而更简单、真·零宿主改动。教训：**方案里每个"复用"都要把签名读一遍再落笔**。

### 19.5 跟随解算（IGfxAttachmentSolver）三条纪律

宿主在 RaiseChanged 的重算窗口里调渲染器解算：① 只改字段不抛事件（否则递归）；
② 写回前逐项比对，无变化不动 LocalSize；③ 真变了必须重算 LocalSize ——
导线长度在 Numbers 里，只改位姿不改尺寸视觉层根本不会重建（RefreshSumObjects 同款坑）。

### 19.6 ★★ collectible ALC 必须被宿主永久攥住（keep-alive）—— 真机 0x80131509

现象：真机上"插入 latex 公式"间歇性炸
`InvalidOperationException: AssemblyLoadContext is unloading or was already unloaded`（0x80131509），
稳定包本机 7 轮自动化复现不出，用户两个会话分别在启动后 49 秒 / 7 分半中招。

根因链：`PluginLoader.LoadOne` 里 `PluginLoadContext` 是**局部变量**，扫描完无人引用；
collectible ALC 没有引用就会被 GC 回收（.NET 7 起官方文档明说：
"keep a reference to that AssemblyLoadContext forever"）。上下文一死，
公式插件**首次调用 Build 时 JIT 绑 XamlMath** 走进已死上下文 → 炸。
两个放大因素：① 异常在 JIT 阶段抛出，Build 自己的 catch 接不住（还没进 try）；
② 公式是唯一"首用时才 JIT 绑依赖"的插件，其余插件扫描时就把依赖绑完了所以不炸。

诊断教训：
- **控制台最小复现证伪不了真机问题**：变体 A/B/C（不攥 ALC / 延迟首绑 / 只攥实例）全不复现
  —— 控制台 GC 压力与 WPF 真机不同，`asm` 局部变量活着就能保活。
  最终靠微软 .NET 7 兼容性文档的处方定案：**把 ALC 引用永久攥住**。
- **pywinauto 真机驱动 7 轮也不复现**（等 45-50s / 深浅主题 / 电路前置都试了）
  —— 间歇性 GC 时机问题，别指望稳定复现，机制+权威文档+修法闭环就该动手。

修法（三件套，harness 第 7 条源级护栏钉死防回退）：
1. `PluginLoader` 加 `static readonly List<(PluginLoadContext, Assembly)> KeepAlive`，
   LoadOne 里 `KeepAlive.Add((loadContext, assembly))` —— 顺手连 Assembly 一起攥（双保险）；
2. `PluginLoadContext` 构造里订阅 `Unloading` 事件打 WARN 堆栈（绊线/尸检报告）；
3. RunM15Checks 源级断言：KeepAlive 列表声明 + Add 调用 + Unloading 订阅三样都在。

另：早间 8:36 会话跑的是**陈旧的 `dist\tablet`**（M14 产物缺公式依赖 dll）——
"报错找不到 XamlMath" 与 "ALC 已死" 是两个会话两种错，别混为一谈；
打包完随手跑 `_m9_cleanup_dist.py --go` 清暂存，能防"拿旧目录当新包验"这种混淆。

### 20.1 ★ 抬笔路径「先 Reset 后用字段」—— 起点被归零，落墨画到 (0,0)

`EndLine` 里先 `Reset()`（清 `_start`）再 `MakeLine(_start, end)` ⇒ 落墨起点恒为原点。
harness 当场抓住（预览 True、落墨 False，一处改两处错）。修法照 `TriangleTool.Commit`
的先例：**Reset 前先把字段读成局部变量**。对照：`RulerTool.Reset` 不清 `_start`
所以同样的顺序它没事 —— 「同款顺序在别处没炸」不代表安全，字段生命周期要看每个 Reset。

### 20.2 ★ 自证恒真/恒假的位移判定表达式

第一版拖板撤销步判定写 `(world - (center + grabOffset)).Length < 阈值`，而
`center = world - grabOffset` ⇒ 表达式恒 0 < 阈值 ⇒ **永远记不上撤销步**。
修法：判定要跟「基准」比（按下的板心 `_downCenter`）。教训：凡是
「A - (B - C)」这类互相抵消的表达式，落笔前先代入问一句「它恒等于什么」。

### 20.3 harness 里 `GfxObjectStore` 不实现 `IGfxObjectHost`

直接把 store 塞给 `FakeToolContext.GfxOverride` 编译失败 —— 要包真宿主通道
`HostGfxObjectHost(store, GfxHistory, BoardHistory)`（`BeginStep` 的撤销历史在里面）。
M15 能直接用 store 是因为吸附纯函数只吃 `Objects` 只读视图。工具的状态机断言
（尤其带 BeginStep/UpdatePose 的）必须走带历史的真通道。

### 20.4 交互容差的「屏幕像素定手感、世界单位做几何」

边吸附容差 = `20 屏幕像素 / Scale`（世界单位），与缩放无关的手感；
顶点吸附容差 = 24 世界单位（与三角板顶点吸附同一条，世界固定）。
两类容差语义不同，别统一成一个常量。

### 20.5 测试点选择：板内拖动的按下点必须离三边都 > 容差

45° 板 leg=110 的内切圆半径 ≈32.2，容差 20 ⇒ 按下点取 (132,68)（离最近边 ≈32）。

## 22. 工具栏拖动仍卡（M18 后 bug 修复，2026-09-24）

M16 已把 `FloatingDrag` 从「每帧改 Margin」改成「拖动只走 `TranslateTransform`（零布局）」，
悬浮球（M18）同理后不卡了；但工具栏仍然卡。根因**不是布局**：

- `RenderTransform` 平移大 Visual 时，WPF 在每一帧仍要重绘该元素的**矢量内容**
  （40 来个按钮 + 多行文字 + 图标），213Hz 触摸率下这块脏矩形合成在一体机集显 / 软件回退时是瓶颈。
- 悬浮球小、内容少，所以同机制不卡；工具栏大，所以卡——二者机制一致，差异只在体量。

修法（改 `FloatingDrag.cs`，工具栏 / 计算器面板共用，一处受益）：
- 拖动开始 `BeginDragVisual()`：先 `EnsureTranslate()` 挂平移变换，再给目标设
  `CacheMode = new BitmapCache { RenderAtScale = max(DpiScaleX,1) }` ——
  把整块预光栅化成位图，平移只移动这张位图（GPU 合成），UI 线程零矢量重绘。
- 松手 / 捕获中断 `EndDragVisual()`：清平移变换 + `CacheMode = null`，恢复矢量清晰渲染
  （静止时不需要缓存，也避免长期占显存 / 高 DPI 长期模糊）。
- `RenderAtScale` 按 `VisualTreeHelper.GetDpi` 取实际 DPI，100% 屏不糊、高分屏也不糊。

护栏：`RunM16Checks` 的 `FloatingDrag` 源级断言（含 `TranslateTransform` / `_translate.X = ..._startMargin.X`
/ `_target.Margin = ...`）全部保留、未触碰，仍 PASS。改动只加 `CacheMode`，不动任何布局写入。
回归：构建 0 警告 0 错误（本机 `dotnet build -c Release`）；流畅度须真机上机确认（本机无法测触摸手感）。

## 23. M18 之后的代码体检（2026-09-25）：三处「静默失效」类缺陷

这三处都不是崩溃，而是**功能看起来在、用起来没反应**——正是最该被断言钉住的形态。
共同教训：**"引用了某个东西"不等于"那个东西存在"**，凡是靠字符串 / 手写清单串起来的地方，

### 23.1 ★ 球菜单的 `calc.open` 从未登记（真机可见的功能缺失）

`MainWindow.BuildBallMenu` 第 6 项写着 `_commands.Execute("calc.open")`，
而 `RegisterCommands()` 里**没有 `calc.open`** —— 于是"悬浮球 → 计算器"点了毫无反应：
`Execute` 对认不出的 Id 只返回 `false`，而这里没看返回值。
docs/18 §S5 写得很清楚："入口 = 总线 `calc.open` + 工具栏按钮 + 球菜单第 6 项"，
**后两者都落地了，总线这一条漏了**，而 M13 的源级断言只要"源码里出现过 `calc.open`"就 PASS
（菜单里出现过也算）⇒ 一路绿灯。

- 修法：① 宿主补 `ShowCalculator()` / `HideCalculator()`（`open` 必须**幂等**，
  "打开"却把开着的关掉是最难查的毛病），总线上登记 `calc.open` / `calc.close` / `calc.toggle`；
  ② 球菜单 7 项提成数据表 `BallMenuItems`（标签 + 命令 Id 各写一遍），装配与自检共用同一张表；
  ③ 执行统一走 `RunBallCommand`：认不出的 Id **同时进日志与状态栏**，不再静默；
  ④ 启动后 `AuditCommandIds()` 拿 `CommandBus.Missing()` 问一次总线（球菜单 + 内置模式的全部 Id），
  缺谁就 `Error` 进日志 + 状态栏提示。
- 断言升级：球菜单那组从"字符串在不在"改成三层——表里有直尺/计算器、**每个 Id 都有对应
  `_commands.Register`**、装配确实走总线；另加 `CommandBus.Missing` 的行为断言与
  `ShowCalculator` 幂等行为的真控件树断言。

### 23.2 ★ 两个工具抢同一个快捷键（9），谁先注册谁赢

坐标系（M7.4，docs/11）与「三角板·沿边画线」（M17，docs/22 + 操作卡）**都声明 `Key.D9`**，
两份文档各说各话（操作卡告诉老师"按 9 沿边画线"）。`ToolRegistry.FindByShortcut` 只返回
**第一个**命中者，插件按目录名排序加载 ⇒ `CoordSystem` 排在 `Triangle` 前面 ⇒ **坐标系赢，
沿边画线的 9 是死的**，而它的 tooltip 照样写着"快捷键 9"。表现是"按了键却选中别的工具"。
单插件的断言（箭头那组各自比"不与彼此撞车"）永远看不到跨插件撞车。

- 修法：以**较新的文档口径**为准（M17 + 操作卡：9 = 沿边画线），坐标系让位到 **C**，
  tooltip 与 docs/11 一并改；`ToolRegistry.Add` 增加"快捷键重复"告警（**只告警不拒绝**——
  为一次键位冲突把整个工具丢掉更糟，按钮入口还在）。
- 断言升级：新增 `RunShortcutChecks`——把**全部 9 个真实插件装进同一个真宿主注册表**
  （20 个工具），断言 ① 快捷键两两不撞车；② 操作卡承诺的键位逐个能查到对应工具
  （1/2/3 笔橡皮手、4/5 直尺、6 量角器、7/8 三角板、**9 沿边画线**、0 函数、C 坐标系、V 选择、N 箭头）；
  ③ 小键盘 9 归一到大键盘。

### 23.3 FitToWidth 用"没钳过的缩放"算偏移（窄窗口下页面偏出视口）

`CanvasViewport.FitToWidth` 先算 `scale = available / bounds.Width`，再把 `scale` 交给 `SetView`
（内部会钳到 `[MinScale, MaxScale]`），**但水平/竖直偏移是按钳之前的 `scale` 算的**。
两者不一致时页面会整体偏出视口，而且完全是静默的（只在窗口极窄或世界特别宽时出现）。
修法：算偏移前先 `Math.Clamp` 到合法区间，让"实际缩放"与"偏移推导"用同一个值。
断言：新增"极窄视口（宽 60）⇒ 缩放钳到下限、左侧留白仍等于 padding"一条。

### 23.4 ★ 打包冒烟脚本自己写错：`check()` 参数顺序反了 ⇒ 13 条断言恒真

M18.1 的包本体冒烟（`artifacts/smoke_m181_pkg.py`）第一版把
`def check(name, ok, detail)` 写成了 `def check(ok, name, detail)`，而调用处一律按
`check(名字, 条件, 细节)` 传 —— 于是 `ok` 收到的是**非空字符串**（恒真），
`name` 收到的是 `True`/`False`。跑出来是：

```
[PASS] True
[PASS] True  —— 数理墨
...
[PASS] False  —— 清实时湿墨失败（已兜住）...
结果：PASS（FAIL=0）
```

**13 条"通过"里有一条明明是失败（那行把 `False` 当成了名字印出来）**。
教训有两条，都很便宜：

1. **断言函数本身要先自证**：打印出来的必须是"人名 + 判据"，
   一旦出现 `[PASS] True` 这种"判据当名字"的形状，立刻停下来看参数顺序；
2. **别在结论里只看 `FAIL=0`**：它只说明"我没发现失败"，不说明"我查过了"。
   这也是 §12.1「不可断言的接缝比一个 bug 更值钱」的反面教材 ——
   假 PASS 比没有断言更坏，因为它会让人停止怀疑。

### 23.5 无活动指针时 `DynamicRenderer.Reset` 必然抛异常 ⇒ 该省的调用要省掉

M18 的"清湿墨"兜底（`InkSurfaceCanvas.ResetDynamicRenderer`）在**没有按下的笔/鼠标**时
调用 `Reset(device, empty)` 必然抛 `ArgumentException`（"调用重置时触笔或鼠标必须…"）：
它被 `try/catch` 兜住了，看起来"不会崩、无所谓"，但只要<b>切一次工具</b>就往老师的日志里刷一行
ERROR 样式的告警 —— 而日志是这台机器上唯一的证据，噪声等于把真故障埋掉。

→ 修法：`Stylus.CurrentStylusDevice` 为 `null` 时**直接 return**（没有按下的笔，本就没有
"半截湿墨"要清），真有指针却失败时才记 Warn。harness 的接线护栏同步加了一条源级断言钉住它。

### 24.1 `using System.Windows.Shapes;` 会和 `System.IO.Path` 撞名

harness 的 `Program.cs` 里有 `using System.IO;`，再引 `System.Windows.Shapes` ⇒

### 24.2 断言组里的 `ReadSource` 是**局部函数**，不是类方法

`static string ReadSource(string root, params string[] parts)` 定义在**每个** `Run*Checks` 方法体内部。
新写一个断言组时想读源码做护栏，必须在自己的方法体里再写一遍（编译器报 `CS0103` 就是漏了它）。

> **再踩一次（2026-09-26，M20 S4）**：S4 的 5 条新断言插在 `RunM10Checks` 尾部，
> 而那个方法体里**有 `root`、有 `srcRoot`，却没有 `ReadSource`**（helper 在别的方法里）。
> 修法是在插入块内自带一个 `ReadSrc` 局部函数（`Path.Combine(repoRoot, Path.Combine(full))`
> 拼绝对路径，`Array.Copy` 把 `"src"` 前置到 parts 前面），免得依赖不存在的成员。
> ★ 教训升级：**别因为"项目里到处在用 X"就以为 X 在类作用域**。局部函数长得跟类方法一模一样，
> 只有编译器能证伪 —— 而这类错误编译器**一定会**报，代价只是多一次编译。
> 真正要防的是"以为它在、懒得看一眼"。

### 24.3 断言自己写错：`TryCancel` **之前**就把手柄列表抓下来了

`VisibleThumbs(...)` 写在 `tool.TryCancel()` 前面 ⇒ 抓到的是「放置中」那一瞬的**空列表**
（手柄都收着），断言必然 FAIL。同一家族还有 §23.4 的 `check()` 参数顺序 ——
**断言失败先怀疑断言**（「改成功」不算证据，PASS 也不等于查过了）。

### 24.4 `Geometry.GetFlattenedPathGeometry` 在 harness 里给不出可用折线

拿它拍平 `StreamGeometry` 再逐段算距离，实测循环走不出任何距离（结果恒为 `double.MaxValue`，

好处有三：与真机上点弧线选对象同一套判定；不必自己拍平；**弧画反了照样过两个端点**，

### 24.5 真 bug：`CancelPlacing` 没把「对象位姿」读回来

圆规的 `StartPlacing` 会把 `_center` / `_radius` 覆写成**新预览**的值，而

## 25. M19 后 bug 修复：浮动面板拖动闪烁 = 坐标基准成环（2026-09-26）

反馈：**拖浮动工具栏（M16 的方阵面板）时面板剧烈闪烁、不跟手，松手位置有时不对**。
M16（改渲染变换）与 M18（再加 `BitmapCache`）两次修「卡」都没治到它 —— 根因不在性能。

### 25.1 根因：量距基准选在了「会被自己改变」的坐标系里

`GetPosition` / `GetTouchPoint` 的量距是在<b>指定元素的本地坐标系</b>里做的，而这个坐标系
**包含该元素及其祖先的 `RenderTransform`**。`FloatingDrag` 原先以 `_handle`（把手）为基准，
而把手正是被拖动目标 `TopChrome` 的**子元素** —— 拖动中刚给目标挂上的
`TranslateTransform` 会把读数抵消掉一部分：

```
读数 = 真位移 − 当前位移      ⇒      下一帧位移 = 读数 = 真位移 − 当前位移
```

这是「位置 → 读数 → 位置」的**正反馈环** `T′ = D − T`。真位移恒定时它的解不是收敛，而是
**两点之间来回翻**（`D 0 D 0 …`）：每帧在起点与终点之间跳一次 = 闪烁；净位移被砍半 = 不跟手；
松手落下的 `Margin` 取的是最后一帧的值，奇偶一颠倒就落回起点 = 松手位置有时不对。

### 25.2 证据（本机真窗口实测，不是推理）

- **坐标基准探针** `artifacts/_probe_dragcoord`（真窗口 + 真光标）：光标**不动**时给目标挂
  `TranslateTransform(60,30)`，`GetPosition(把手)` 由 `(120,90)` 变成 `(60,60.7)`（≈ 减 60/30），
  而 `GetPosition(容器)` 纹丝不动（`(180,150)` → `(180,150.7)`）。算法复算出的位移与真值恰好差
  `−(60,30)`；迭代 6 帧得 `140 0 140 0 140 0`。
- **现场拖动探针** `artifacts/_probe_draglive`（真窗口 + 真鼠标注入 `mouse_event`，
  **直接挂生产代码的 `FloatingDrag`**，24 帧连续拖动、逐帧比对）：
  修复前位移序列 `0,0,12,6,18,24,12,30,18,24,36,42,30,48,36,…` —— 非单调、来回跳，
  最大偏差 **72.0 DIP**、松手 `Margin` 误差 **78.0 DIP**；
  修复后 `0,6,12,…,138` 严格单调、最大偏差 **0.0 DIP**、松手误差 **0.0 DIP**。

### 25.3 修法（`Views/Controls/FloatingDrag.cs`：一行语义 + 四处读数）

```csharp
public static FrameworkElement ResolveReference(FrameworkElement target, FrameworkElement container)
    => target.Parent as FrameworkElement ?? container;   // 目标父级 = Margin 的坐标系
```

- `OnPress` 里按下时**定下**基准，整段手势不换（中途换父级也不会串坐标系）；
- `OnPress` / `OnMove` 的 `GetPosition` / `GetTouchPoint` 全部改用基准元素（把手不再参与量距）。

为什么「父级」是对的：① 它**不在这次拖动的影响范围内**（变换挂在目标身上，不在父级上）；
② `Margin` 本来就相对父级解释，「量距坐标系 = 落位坐标系」两处口径天然一致；
③ 悬浮球（`FloatingBall`）从一开始就以宿主 Grid 为基准，所以**它没有这个毛病** ——
这也正是 M16/M18 里「球不卡、只有工具栏卡」的真解释（当时归因为「工具栏大、重绘慢」）。

### 25.4 护栏（`RunDragCoordChecks`，3 条）

1. **真控件树**：`ResolveReference(target, container)` 返回容器，且**不是目标自身、也不是目标的
   子孙**（反向自证：把手确实落在目标的坐标系里）；
2. **源级**：`FloatingDrag` 去注释后含 `GetPosition(_reference)` / `GetTouchPoint(_reference)`，
   且**不含** `GetPosition(_handle)` / `GetTouchPoint(_handle)`；
3. **反馈环数学**：同一段真位移，以自身为基准的序列 `140 0 140 0` 翻跳、以父级为基准 `140×4` 稳定。

负向自证（必做）：把 `ResolveReference` 改回 `target`、读数改回 `_handle` ⇒ 第 1、2 条当场红
（第 3 条是纯数学，本来就与源码无关）；改回来 ⇒ **854/0**。

### 25.5 教训

1. **「给渲染换了更便宜的路径」不等于「那条路径是对的」** —— 两次性能补丁（RenderTransform、
   BitmapCache）都绕过了根因，而根因只有一行：量距基准自指。
2. 写拖动时先问一句：**这个坐标系会不会被我自己改变？** 会，就换一个不会的（父级 / 容器）。
3. 反馈环的**观感**（闪烁）与**根因**（坐标自指）在代码里只差一行，肉眼读代码看不出来 ——
   把「每帧的位移序列」打出来就一眼可见：这正是探针比阅读更值钱的地方。
4. 遗留（注意区分）：M16 加的 `CacheMode = BitmapCache` 仍在拖动起手 / 收手各光栅化一次；
   真机上若还看到「文字起手发糊一下」，那是缓存光栅化（ClearType → 灰度 AA），
   **不是**本条的成环问题，别把两件事混成一件。

## 27. M20 S4 —— 工具栏四组 + 二级 Popup（2026-09-26）

需求侧一句话：把一堵 64 个目标的「按钮平墙」拆成 **笔类｜图形｜文档｜系统** 四组，组间加横线，
同一工具的多个变体折进二级菜单。设计稿见 `docs/15` §16。

实测：工具栏 **492×624 / 64 目标 / 13 行** → **500×649 / 57 目标 / 22 工具**（15 瓦片 + 7 折进族）。
一体机可用高 688（状态栏 690），底部余量 27px。回归 863 → **868/0**。

### 27.1 ★★ WrapPanel 量「嵌套容器」用的是**整行宽度**，不是本行剩余宽度

这是整个 S4 返工一次的根因，值得单开一条。

`WrapPanel` 在量一个子元素时，给的 `availableSize.Width` = **整行的宽度**（本项目铬宽上限
`Chrome.MaxWidth = 500`，去掉内边距约 492），**而不是"本行已放了 X 之后剩下的 492−X"**。
于是：

- 把「组标题」和「该组所有瓦片」分别做成两个容器（`Border` / `WrapPanel`）塞进外层 `WrapPanel`，
  每个内层容器都以为自己**独占一整行**（按 492 算），于是每个组至少占两行：
  第一行只有组标题（44px），第二行才是瓦片。
- 5 个组就白花 5×44 = 220px 高。表现是「工具栏莫名高了 77px」，而**源码上完全看不出来** ——
  没有哪个属性写着"占一整行"。

**修法（唯一）**：组里**每一个瓦片都必须是组 `WrapPanel` 的直接子元素**；组标题做成
**行内的一个 `Border` chip**（`Style.GroupHeaderChip`，44×44），跟瓦片一起参与换行。
这样外层只量一次，标题与瓦片自然排在同一个流里。

> ★ 反推护栏：harness 的 M16 第 4 条据此改成「`x:Name="ToolButtons"` 这个名字就落在
> `WrapPanel` 上」，并**明文禁止改回 `ItemsControl`**（`!mainCsS4.Contains("ToolButtons.ItemsSource")`）：
> `ItemsControl` 的 `ItemsPanel` 天然就是嵌套容器，踩这个坑，而它在源码上一点看不出来。

### 27.2 ★ 高度预算：`Padding` 的垂直分量 × 行数 = 灾难

初版分组后实测 **500×701**（基线 624；一体机可用高 688 ⇒ 会被状态栏切掉）。
逐项量出来是这么吃掉的：`Tile.Pad` 垂直 3px + 文字 `Margin` 垂直 2px ≈ 5~7px / 行 × 11 行。

| 步骤 | 高度 |
|---|---|
| 基线（改造前 13 行） | 624 |
| 初版分组（组标题各自占行） | 701 |
| `Tile.Pad` `2,3`→`2,0` + 文字间距抽成 `Tile.TextGap`(0,1) | 661 |
| `Gap.GroupDivider` `0,6`→`0,4` | **649** |

> ★ 教训：**瓦片高度要落在 `Tile.MinHeight`（44），别靠 Padding 把行撑高**。
> 垂直 padding 在"一行"上看不出问题，乘以十几行就顶到状态栏。
> 又想加内边距又想不超高，只能往**水平**方向加（`Tile.Pad` 保留左右的 2）。

### 27.3 ★ 正则「从某处往后切 N 个字符」会越界读到**下一个类**

S4 的目录表对账断言要从源码里抽「声明了哪些工具 Id」。初版写法是：

```csharp
int end = Math.Min(source.Length, cls.Index + 900);
string window = source[cls.Index..end];   // ← 切窗
```

结果把 `ArrowTool` 类里的 `UnitWorldKey = "unitWorld"` 也当成了工具 Id，
报出「声明了 23 个工具 / 目录表 22 个；★ 未登记：unitWorld」—— 一条**假 FAIL**。

原因：`ArrowToolIds` 是个只有一行的类，紧跟其后的 `ArrowTool` 类里常量一大片，
900 字符的窗口稳稳跨过去。**100% 命中，不是偶发。**

**修法**：**按大括号配平取类体**（`{` 深度 +1、`}` 深度 −1，回到 0 即类尾），只在类体内抽常量。
配平后抽出来正好是 22 个工具 Id，假 FAIL 消失。

> ★ 通用纪律：任何"从锚点往后切固定长度"的源级抽取都是**定时炸弹** ——
> 锚点附近的代码一改，窗口就开始咬到不该咬的东西。要么配平、要么用更精确的结构特征。

### 27.4 宿主侧「工具目录表」，而不是给契约加成员

分组信息（属于哪组、图标键、瓦片短名、是不是某个工具族的变体）本是**表现层**信息，
不该进插件契约：`ITool` 加成员会让**旧插件加载时 `TypeLoadException`**（§7 铁律）。

做法：宿主侧新增 `Tools/ToolCatalog.cs`（纯数据表），按 Id 关联；
**没登记的 Id 落到兜底组「其他」**（`GroupPanelOther`，空组不渲染），并在日志里 WARN。
好处是新插件没来得及登记时**功能不消失**（掉进"其他"），只是分组不理想 —— 优雅降级。

### 27.5 ★ 工具族的折叠纪律

- 变体行**必须紧跟**在其族代表之后声明（折叠就是"把连续几项收起来"，靠的正是连续性）；
- **只有一层**（变体不能再挂变体）；
- 族代表**自身不被折叠**，只有成员进二级菜单 ⇒ 「tiles + folded = 工具总数」必须成立：
  实测 `15 + 7 = 22` ✓（`folded` 不含 4 个族代表）。

harness 第 19 条把这些全钉住（组顺序 == 枚举顺序、图标键可解析、瓦片短名 ≤8 字、
族只有一层且成员紧跟在代表之后）。

### 27.6 XML 注释里不能出现 `--`（MC3000）

脚本化重排 XAML 时为了可读性插了几条 `<!-- ---- 墨色 ---- -->` 风格的分隔注释，
编译直接 `MC3000: An XML comment cannot contain '--'`。XAML 注释体里 `--` 是**语法级禁止**
（与 XML 规范一致），`-{2,}` 一律换成 `====` 之类。

> 这条踩过不止一次：`tools/fetch_lucide_icons.py` 已经在 `Icons.xaml` 上自带自检，
> 但**只查那一本**。凡是脚本生成/重排 XAML 的地方，都该在自己的产物上查一遍 `-{2,}`。


## 28. M20 步 2b —— 宿主自建面板接入设计系统（2026-09-26）

背景：M10 立了设计系统，但「纯代码建界面」的 5 个宿主面板（图层 / 计算器 / 参数 / 回放 / 悬浮球菜单）
一直是**手抄色值 + 裸按钮**。摸查实数：**10 个裸 `new Button`、31 处 `Tokens.Brush(...)` 静态快照、
0 处 `SetResourceReference`**。回归 868 → **872/0**。

### 28.1 ★★ `Tokens.Brush(key)` 是**快照**，不是绑定 —— 「不写色值」≠「不会留旧色」

`GfxParameterPanelView` 的类注释里 M10 时写过一句：

> 「M10 起本类一个色值都不写，全部走 Tokens（设计令牌）… 但反过来，它也因此**绝不会**在换肤后留下旧色。」

**后半句是错的**，而且错得很隐蔽：`Tokens.Brush(key)` 当场把画刷**取出来交出去**，
元素拿到之后就跟资源字典脱钩了。`ThemeService` 换掉界面板那一本时它**收不到通知** ——
屏幕上表现为「漏了一块」；而 XAML 里写 `DynamicResource` 的兄弟元素都跟着变了。

**判据**：换肤要生效，属性必须由**资源引用表达式**驱动，而不是一个本地值。
代码侧的等价物是 `FrameworkElement.SetResourceReference(dp, key)`。本步把它包成
`Tokens.FollowTheme<T>(this T, DependencyProperty, string key)`（可链在对象初始化式后面）。

### 28.2 ★ FollowTheme 的环境判据不能是 `Application.Current is null`

第一版写的就是它，**错**：验收 harness 自己会造一个 `Application`
（`PdfSmokeTest.InitializeDesignResources`）并合并同一批设计字典 —— 判 null 会把它误判成离线。

正确判据是「**当前确实有一本 Application 资源字典能解析出这个键**」——
这正是 WPF 解析 `DynamicResource` 的条件：

```csharp
if (Application.Current is { } app && app.Resources.Contains(key))
    element.SetResourceReference(property, key);
else if (TryGet(key, out var value))
    element.SetValue(property, value);   // 离线回退，见下
```

★ 为什么必须留 `else` 这一支：资源引用**解析不到**时不是「保持原值」，而是把属性
打回该依赖属性的默认值（通常是 `null`）—— 颜色会**凭空消失**。
而没有资源环境的场景里根本不存在换肤，取一次快照不会残留旧色。

### 28.3 ★★ `TextElement.Foreground` 跟随的是 **Windows** 的主题，不是本程序的主题

这是本步顺手挖出来的**真缺陷**，值得单列。

界面里不写 `Foreground` 的 `TextBlock`，其 `TextElement.Foreground` 取
`SystemColors.ControlTextBrush` —— 一个**动态系统画刷**。于是三条事实叠起来：

- 本项目**没有**隐式的 `TextBlock` 样式（`App.xaml` 里没有）；
- `MainWindow` 只设了 `FontFamily` / `FontSize`，**没设 `Foreground`**；
- ⇒ 那些 `TextBlock` 的文字色跟着**操作系统**走。教室一体机通常是浅色系统 ⇒ **黑字**；
  而我们的面板是**深色浮层** ⇒ **黑字压黑底**。

实测中招 4 处：图层面板的「图层」「批注层 / 草稿层」、计算器的「计算器」、回放条的「回放 0/0」。

**修法**：套文字层级样式（`Style.TextTitle` / `TextBody` / `TextLabel` / `TextCaption`），
它们带 `{DynamicResource Ui.TextPrimary/Secondary/Muted}`。
★ 判据写成源级护栏：**每个 `new TextBlock` 之后必须有 `Foreground` 或 `Style`**。

> ★★ 普遍教训：**「默认值」不等于「安全值」**。凡是不显式着色的文字/背景，
> 都要问一句「它的默认值跟着谁走」。

### 28.4 裸 `new Button` 会悬停闪系统浅蓝

不套样式的 `Button` 走 WPF 默认模板，其 `IsMouseOver` 触发器把背景换成
Aero2 的 `ButtonMouseOverBackground`（系统浅蓝）—— 与深色主题正面冲突。
**判据**：每处 `new Button` 之后、**下一个 `new Button` 之前**必须出现 `Style = `。

> ★ 为什么卡在「下一个 `new Button` 之前」而不是「往后看 500 字符」：
> 后者会被下一个按钮的 `Style = ` 蒙混过关 ⇒ 断言**恒真**（同类坑见 §23.4）。

### 28.5 面板里三个既有的设计系统样式，之前根本没被用上

| 样式 | 本来是给谁的 | 现状 |
|---|---|---|
| `Style.PanelCloseButton` | 面板的 ✕ | 3 处**手抄了它的 8 个属性** |
| `Style.PanelStepButton` | 面板的 −/＋ | 参数面板**手抄了它的 7 个属性** |
| `Style.FieldBox` | 面板的输入框 | 参数面板的值框**手抄了它的 9 个属性** |

M10 就定义了，一直**没有调用方** —— 于是「令牌改了、面板没变」的老毛病有了温床。
本步一并接上（`Style.FieldBox` 那处少写 9 行）。

> ★ 教训：设计系统里「定义了但没人用」的样式，等于没有 —— 它会静静地腐坏。
> 收口时应该反过来查一遍：**每个样式键有没有调用方**。

### 28.6 顺手把两句错注释改对了

- `GfxParameterPanelView` 类注释：「因此**绝不会**在换肤后留下旧色」→ 改为如实描述（§28.1）。
- `GfxParameterPanelView.StepButtonSize` 注释：「harness 会把两个值放在一起断言」→
  实际 harness 里**没有**这条断言，已把话说准（真正的护栏是 `Style.PanelStepButton` 的 `Touch.Min`）。

> ★ 注释里的「保证」如果没人断言，就会变成下一个人敢踩的坑。

## 29. M20 收口与交付（2026-09-26）

### 29.1 不在 sln 里的工程，`dotnet build sln -c Release` 不会给你 Release 产物

`MathPhys.Ink.sln` 只有 **13** 个工程；`Plugin.VectorArrow` 与
`PdfSmokeTest.Plugin` **不在其中**，它们只被 `tools/PdfSmokeTest/PdfSmokeTest.csproj`
用 `ProjectReference` 带出来。后果实测（2026-09-26 M20 收尾）：

```
MathPhys.Ink.Plugin.Ruler      -> ...\bin\Release\net8.0-windows\...dll    ← 在 sln 里，正常
PdfSmokeTest.Plugin                 -> ...\bin\Debug\net8.0-windows\...dll      ← 不在 sln 里
MathPhys.Ink.Plugin.VectorArrow-> ...\bin\Debug\net8.0-windows\vectorarrow.dll
```

机制：`Configuration` 没沿这条 P2P 链传下去，SDK 回落到默认值 **Debug**
（`<Configuration Condition="'$(Configuration)'==''">Debug</Configuration>`），
产物落进 `bin\Debug\`；而 `bin\Release\` 里那个 dll 是**上一轮**留下的，原地不动。

为什么危险：这是「静默」的 ——

* MSBuild 的输出行**照样**打印 `... -> ...\bin\Release\...dll`
  （增量判定为「已是最新」时也会打印目标路径），日志里看不出任何异常；
* `_stage_plugins.py` 原本只校验「目标目录里有那个 dll 且字节数与源一致」，
  **源本身是旧的它看不出来**；
* 表现要到一体机上才暴露：「明明改了插件，装上还是旧行为」。

处置（已落地）：`_stage_plugins.py` 新增 `newest_source_mtime(project_rel)`，
逐个插件比较 dll mtime 与「该工程最新源文件 mtime（排除 bin/obj）」，
落后就 FAIL 并打印逐个工程的修法：

```
dotnet build src\MathPhys.Ink.Plugin.VectorArrow\MathPhys.Ink.Plugin.VectorArrow.csproj -c Release
```

**改成哪个插件源码，就顺手核一遍这条**；`新鲜度=OK` 才是可以铺装的凭据。

### 29.2 轻量版操作卡里凡是「数」都要按变体复算

轻量版操作卡是从完整版卡**锚点替换**派生出来的（`_m9_pack.py` 的 `TESTCARD_EDITS`）。
文字措辞漏改还好，**数字漏改会直接引来误报**：

| 说法 | 完整版 | 轻量版 |
| --- | --- | --- |
| 插件个数 | 10 | 9 |
| 瓦片（工具）总数 | 22 | **21**（少一颗 GeoGebra） |
| 折叠（折进小箭头） | 7 | 7 |
| 工具栏可点目标 | 57 | **56** |

M20 收尾时卡上写的是「瓦片一共 22 颗」，老师照着数只有 21 颗 ——
会当成「少了一颗按钮」报回来。现已补两条锚点：

* `（瓦片）一共 22 颗` → `21 颗（轻量版少了 GeoGebra 那一颗）`；
* `瓦片从 29 颗减到 22 颗` → `…（轻量版 21 颗）`。

**规矩**：以后每加一条带数字的说法，都要问一句「这个数在轻量版里一样吗」，
并在 `smoke_*_anchors.py` 之外，用包本体冒烟**实测**那三个数（见 §29.3）。

### 29.3 包本体冒烟要断言「账目自洽」，不能只钉死数字

`artifacts/smoke_m20_pkg.py` 用 `M10_UI_SHOT` 让包里的 exe 自己出图并退出，
再从 `ui-shot.txt` 读工具栏账目。这里有两层断言，缺一不可：

* **按变体的期望值**（22/15/57 与 21/14/56）—— 钉住回归；
* **账目自洽** `tiles + folded + other == tools` —— 这才是「没弄丢工具」的不变量。

只钉死数字的话，将来加一个工具就要改三处；只查自洽的话，「全组折叠没了」也能自洽通过。

同一份 `ui-shot.txt` 还自带三条不用写代码的真值，直接断言即可：

* 两张图主题一深一浅（`[a] 深色` / `[b] 浅色`）；
* `ui.chrome` 随主题变、`ink.红` **不**随主题变（两套色板分开管的证据）；
* 工具栏区域的像素平均亮度差（深色 100.1 ↔ 浅色 217.5，Δ=117.4）——
  这条是**像素级**复核，防「字典换了但界面没重绘」。

### 29.4 改了 `Assets\` 里的随包文本，暂存目录里的副本必须同步

`怎么测试.txt` / `第三方许可与署名.txt` 由 publish 拷到包根。若在 publish **之后**
才改源文件，`dist/tablet/` 里还是旧副本，打出来的包就是旧卡。
两种处置：重跑 publish，或直接把源文件 `shutil.copy2` 覆盖到暂存目录，
然后**比对 SHA-256 确认字节一致**再打包。（本轮在 publish 之前就改好了卡，
同步前后 SHA 相同 —— 顺带验证了这条。）

## 30. M21 —— 默认值调整踩到的七件事（2026-09-26）

### 30.1 断言里写死"当时的伴随事实"，一改设计就撞

M4 那条原文：`Math.Abs(attributes.Width - 1.5) < 1e-9 && attributes.Color == Colors.Red`。
它的**本意**是"出厂默认笔 == 调色板里的默认档"，而 `1.5` / `Colors.Red` 只是当时的伴随事实 ——
默认笔宽一改成 0.8 它就 FAIL，而 FAIL 的原因与"坐标 / 单位"这件事毫无关系。
改成 `paletteDefaultWidth.WorldWidth` / `paletteDefaultColor.Color` 之后，它才真的能抓到"两处各说各话"。

**判据**：断言里出现字面量数值时，先问一句"这是在验恒定事实，还是在替某个可改的配置背书"。

### 30.2 像素数阈值会随默认笔宽漂移

`stats.InkPixels > 20`（端到端光栅的前置）在 1.5 时余量就不大，0.8 时直接掉到 4。
这类"像素计数下限"本质上是在替**笔宽**背书。修法是给被测段**显式设笔宽**，
而不是把阈值一路往下调（调到 3 就等于没验了）。

### 30.3 操作卡锚点会被**标点**改动打破

轻量版派生锚点原本挂在 `"请双击文件或用「打开工程」。"`（句号收尾）上。
本次在它后面追加两条"已知小事"，把那句的收尾从 `。` 改成 `；` ⇒ 锚点命中 0 次、`build_lite_testcard` 抛错。
教训：**改操作卡里任何一句话，都要紧接着跑一次锚点冒烟**，而不是等打包到一半才发现。

### 30.4 墨色块是 XAML 手摆的，加一档要改三处

`_colorButtons = new[] { ColorButton0, ... }` 是**手写**数组，`BuildInkButtons` 只填
`i < _colorButtons.Length` 的前几档。往 `InkPalette.Colors` 加一档白墨，界面**不会自动多一颗按钮** ——
必须同时改：① `InkPalette.Colors`；② `MainWindow.xaml` 的 `ColorButton5`；③ code-behind 的数组。
漏掉②③的表现是"白墨在调色板里、但老师点不到"，而且**没有任何 assert 会报**。

### 30.5 `targets` 探针数的是 ButtonBase，加色块就 +1

`UiShotHook.CountTargets` 数的是可视子树里的 `ButtonBase`。墨色 5 → 6 颗 ⇒ `targets` 57 → **58**，
包本体冒烟的 `EXP_TARGETS` 必须跟着改。

## 32. M22 S3 —— 原生运动学仿真踩到的七件事（2026-09-26）

### 32.1 ★★ 「参数」与「状态」是两套字段时，切模型必须**显式**初始化状态

`PendulumModel.Angle` / `SpringModel.Displacement` 的初值都是 0（静止在平衡位置），
而"初始状态"是**另一组字段**（`StartAngleDegrees = 20` / `StartDisplacement = 0.25`）。
`SimWindow.SwitchKind` 原先只换 `_kind` ⇒ **打开仿真窗，摆和弹簧一动不动地钉在最低点**，
而右侧滑杆上的数字（20°、0.25 m）看着全对。

这是最难查的一类故障：界面呈现的是一个**合法的静止**，不报错、不空白、控件都在，
于是只能被当成「坏了 / 点了没反应 / 电脑卡了」。修法是抽 `ResetCurrent()`，
让"切模型"和"按重置"走同一条路。

**通用口径**：任何"模型 + 视图"的组合里，只要"目标值"与"当前值"是两个字段，
切换目标就必须显式同步当前值 —— 不能指望它们碰巧相等。

### 32.2 界面上的"能不能用"必须抽成 **public 纯函数**，否则只有真机能验

`SimWindow` 是 `internal` 的 WPF 窗口 ⇒ harness 够不着 ⇒
「轻量版里那两颗『网页仿真』按钮该灰」这条只能靠真机肉眼。
抽出 `WebSimAvailability.IsUsable / Reason` 之后，harness 用真 `WebPanelController`
把「有通道 / 通道自报不可用 / 通道没给原因 / 没有通道」四种各断言一次。

**配套的界面纪律**：灰按钮必须说得出**是哪一种**不可用（本版本没带 Web 模块 /
没装 WebView2 运行时 / 宿主较旧没给通道）。只说「不可用」等于没说。

### 32.3 `*ToolIds` 类里**只许放工具 Id 这一个常量**；连注释都要躲开那四个连写字

工具 Id 是 harness 按正则抓的：先找 `static class \w*ToolIds` 取类体（大括号配平），
再抽其中所有 `const string`。于是：

- 往 `NativeSimToolIds` 里多放一个常量 ⇒ 被当成"这个插件又声明了一个工具"，
  而它没登记在目录表里 ⇒ 直接 FAIL；
- 在 `ToolCatalog.cs` 的注释里写下 `*ToolIds` 这四个**连写**字 ⇒ 正则把注释当成一个类，
  从注释往后"配平大括号"抓出半个文件。

⇒ 注释里要提它，就拆开写、或者换个说法。

### 32.4 ★ 含 ASCII 双引号的 C# 行，绝不能塞进 Python **双引号**串（我又踩了一次）

`tools/_m22_s3_patch2.py` 里：

```python
"        var export = MakeAction("导出到白板", "……", OnExport);"
```

中文段在第一个 ASCII 引号处被**提前截断** ⇒ `SyntaxError`（报的还是"非法字符 `（`"，
看着像编码问题，其实是引号配对问题）。而 §31.4 早就写了这条。

**两条修法，按可靠性排序**：
1. 走 §31.4 的模式：C# 整块写进 `.cs.txt`，脚本只读文件 + 校验命中计数 + 写入（**首选**）；
2. 确实要内联时：含 ASCII 双引号的行一律用 Python **单引号**串；
   整块代码用 `r"""..."""`，并确认正文里没有连续三个双引号、也不以双引号结尾。

### 32.5 断言的门槛必须**比被测物理量本身小**

单摆「Reset 之后真的开始演了」那条，我拿 `0.1 rad`（≈5.7°）当门槛，
而 20° 起摆 0.5 s 后**只回到 0.4°**（`cos(ωt)` 已经过了一个谷底）⇒ 断言恒假。

**口径**：断言里出现的每个物理量，都要先想一遍"它这一刻大概是多少"。
写不出这个数，就说明该断言的是**趋势**（变大/变小/离开 0）而不是**幅度**。

### 32.6 ★★ 测试参数必须落在模型的**量程**内，否则断言会安静地报假失败

弹簧阻尼四态（无 / 欠 / 临界 / 过）那条：我用 m=1、k=20 ⇒ `b_c = 2√(km) = 8.94`，
而 `Damping` 的量程上限是 **3** ⇒ setter 把 8.94 夹到 3 ⇒
「临界阻尼」「过阻尼」这两态**永远测不出来**。断言没有报错、没有异常，
只是一个安静的 `FAIL`。

**口径**：给"参数化的模型"写断言前，先把**每个要设的值**跟它 setter 的夹紧区间对一遍。
这次的信号很明确 —— FAIL 的详情行里出现了两个一模一样的「欠阻尼」，
而标题写着"四态"。**详情行要写得能一眼看出这种事**（把四态各自的原话都打出来）。

### 32.7 浮点相等：`Advance(dt)` 是**拆步累加**，`Time` 不可能 `== dt`

`Advance(0.5)` 内部拆成 500 步、每步 `Time += 0.001` ⇒ 结果是 `0.5000000000000003`。
`born.Time == 0.5` 这种断言必假。同一件事在本项目还有：`Travel`、`Angle` 这类
"积分出来的量"一律**只做容差比较**。

### 32.8 ★★ 补丁脚本的行尾翻倍（`\r\r\n`，一次 236 处）

S5 的 harness 补丁脚本里，新文本先整体 `replace('\n', CRLF)` 预转了一遍，进统一的
`sub()` 后又被 `replace('\n', CRLF)` 一次 —— 已含 `\r\n` 的文本被翻成 `\r\r\n`，
全文件 236 处变成"每行后面跟一个空行"。**编译器不在乎**（C# 当它空行，构建照绿），
但源级断言在乎（按单行写的锚点全部失配），而且视觉 diff 满屏都是假改动。
**防法**：行尾归一只在写盘前做一次；补丁跑完回读 `\r\r\n` 计数（必须为 0）。

### 32.9 ★ bash `-c` 会吃掉一层 `\"`，带转义序列的补丁必须落盘成文件

`python -c "... \"ready\" ..."` 里，bash 双引号把 `\"` 变成 `"`，Python 收到的锚点
已经和文件里的不一样了 —— 表现是「锚点命中 0」或改错位置。和 §32.4 同源：
**多层转义叠加必出错**。防法：凡锚点里含反斜杠或双引号的补丁，一律先写 `.py` 文件
（`Write` 工具原样落盘），再执行；不在 `-c` 里现写。

### 32.10 ★ C# 字符串里的 Windows 路径反斜杠要翻倍

`csproj.Contains("Assets\websim\**\*")` 里的 `\w`、`\*` 是非法转义（CS1009）。
C# 源码里要写 `"Assets\\websim\\**\\*"`；经补丁脚本写入时 Python 侧给四层
（Python `\\\\\\\\` → 文件 `\\` → C# 值单反斜杠），或干脆用 `chr(92)` 拼接避免数层数。

### 32.11 ★★ 打包链里的「版本常量」每次发包都要全数过一遍

M22 S7 轻量包冒烟连吃两次 FAIL，根源都是 M21 字面量没换：`_m9_pack.py` 的残留探针
写死 `"  10 个插件（"`、轻量版标题检查写死 `M21 测试包 · 轻量版`。探针和标题检查
本来是防呆的，结果自己成了呆点 —— **版本字面量比想象的分散**。

**发包 checklist（已固化）**：
① `_m9_pack.py` 的 VARIANTS 换新版名；② TESTCARD_EDITS 整表核对 +
`ast.literal_eval` 锚点预检（全部命中才开压）；③ 残留探针（「N 个插件（」）按新版
插件数改；④ 轻量版标题检查换新版名；⑤ `smoke_pkg.py` 的 EXP_TOOLS/EXP_TILES/
EXP_TARGETS + expect-plugins（全量/轻量两套）；⑥ 操作卡里的每个数按变体复算
（**在 publish 之前**改源卡）；⑦ `_m9_rebuild_stage.py` 的 DEFAULT_WEBVIEW2_FROM

### 33.7 ★★ 「启动即崩 + 天书报错」= 解压不完整 —— 启动自检要放在**静态**构造函数里

wpfgfx_cor3.dll`，0x8007007E），7 秒后再双击又好了。zip 里明明有这个 dll（逐包校验过）。
根因是**解压还没完成（或在压缩包里直接双击）就启动**：自包含布局的原生库
（wpfgfx_cor3.dll / PresentationNative_cor3.dll）尚未落盘或正被实时扫描锁住。

**修法**：启动自检 —— exe 旁有 `hostfxr.dll`（自包含布局的标记）才检查那两个原生库；
缺了就弹中文指引（「完整解压后再运行」）并落日志后退出。**框架依赖布局（dotnet run）
旁没有 hostfxr ⇒ 跳过检查**，不误伤开发机。配套：操作卡加一条、harness 加源级断言。

### 33.8 ★★ Application 基类构造函数会把整个启动流程**排队** —— 实例构造函数里弹模态框会重入

自检第一版放在 `App` 实例构造函数里，探针实测抓到诡异现象：弹窗后 41ms 就出现了
`ThemeService.Initialize` 的日志（而「弹窗后」一行永远没打出来）——**启动流程在模态框
底下继续跑了**。原因：`Application` 基类构造函数把 `DoStartup → OnStartup → 加载
App.xaml 资源` **排队成 Dispatcher 操作**（原始崩溃堆栈里的
`Application.<.ctor>b__1_0` 就是它），`MessageBox.Show` 的模态泵把这条排队的启动流程
**一并泵了进来** —— 重入，进程挂在半启动态。

**口径**：任何「要在 WPF 启动之前做事」的检查，放进 **`static App()`** ——
它跑在 Application 基类构造**之前**，此刻 Dispatcher 队列是空的，模态框才是纯模态框，
点确定后 `Environment.Exit` 干净退出。实例构造函数在基类构造**之后**跑，
那时启动流程已经排上队了。

## 34. M24 热修① —— 异常长线第二刀：包内逐点过滤（2026-09-27）

### 34.1 ★★ M18 断点检测的三个残留缺口（为什么修过仍有线）

现场反馈书写偶发横贯直线，M18 的 `JumpDetector` 修过未根治。勘察定位到三个缺口，
全部在 `InkSamplerPlugIn` 一处：

1. **包内点零检查**：M18 只查「包边界」（上一包末点 vs 本包首点）；`OnStylusMove`
   对包内点无条件采集 + 整包写回。UI 繁忙时 RTI 把多个采样合进一个包，
   手掌并入若发生在包中间 ⇒ 检测不到，直线照画照提交。
2. **写回不截断**：即便包边界跳变命中，`OnBreakDetected` 只是异步投 `Reset` 清湿墨 ——
   `Reset` 慢一两帧的间隙里，DynamicRenderer 拿着原始点照样把直线画上屏。
   「看得见的直线」的直接闸门应是**写回点集本身**，不是事后清理。
3. **坏点不过滤**：`JumpDetector` 遇 NaN 直接放过（return false）；NaN/∞/(0,0)
   会进几何、污染平滑与笔锋。精确 (0,0) 是红外框漏检/故障的典型输出。

### 34.2 修法：判定逐点化 + 写回截断（`PacketPointFilter` 纯函数 + `ScanPoints`）

- **纯函数层**（`InkPointFilters.cs`）：`PacketPointFilter.Classify(hasAnchor, ax, ay, aTs, x, y, ts)`
  逐点返回 Good / BadPoint / Jump。跳变判定**完全复用** `JumpDetector.IsJump`（阈值同源）：
  同包内所有点共享 `RawStylusInput.Timestamp` ⇒ 包内 dt=0，`IsJump` 自动退化为
  「距离 > 80 world」单条件 —— 真机 213~281 Hz 下相邻点正常位移 < 5 world，不引入新旋钮。
  坏点 = NaN / ±∞ / 精确 (0,0)，**丢弃而不判跳变**（一个毛刺不该牺牲整笔）。
- **插件层**（`InkSamplerPlugIn`）：`ScanPoints` 逐点分级，完好点的原始锚**逐点**推进
  （包边界判定被天然覆盖，不是并列两套逻辑）；跳变 ⇒ 写回截断到完好前缀 + 走既有
  `OnBreakDetected`（整笔 UI 层作废口径不变）；坏点 ⇒ `BuildKept` 重组点集参与
  平滑/采集/写回。**Down 起点也过滤**：坏点不作起点（否则湿墨从 (0,0) 起笔连斜线）。
- **写回纪律**：`WriteBackSet` 空集也照写（湿墨整段没原料可画）；失败只记日志退化为
  M18 行为（Reset 兜底），绝不影响落墨。

### 34.3 ★ 断言口径跟着升级（旧锚点会假 PASS/假 FAIL）

M18 接线护栏断言钉的是 `JumpDetector.IsJump` 出现在插件源里 —— 判定逐点化后插件里
**不再直接出现**这个调用（进了 `Classify`），断言必须跟着改成
`PacketPointFilter.Classify` / `ScanPoints(` / `BuildKept(` / `WriteBackSet(`。
教训：**源级护栏钉的是「实现形态」，实现重构时护栏必须同步重审**，否则要么假 FAIL、
要么守着一段已经不存在的现实。新增纯函数断言 10 条（harness M18 组 1b），
回归基线 1002 → **1003/0**。

### 34.4 ★★ SetStylusPoints 不收空集 —— 「写回空集让湿墨不画」是空想

官方源码实锤：`RawStylusInput.SetStylusPoints` 对空点集**直接抛 ArgumentException**
（`Stylus_StylusPointsCantBeEmpty`）。凡「想让湿墨无处可画」都要改用**钉点**：
写回一个单点。钉在湿墨当前位置 ⇒ 增量段零长度（画不出新东西）；钉在主触点笔尖
⇒ 与真笔迹重叠（肉眼不可见）。`DynamicRenderer.Reset` 仍保留：它是「清掉已画半截、
让后续增量从新位置重新起笔」的唯一手段（M18 语义不变）。

另：`RawStylusInput` 上**没有** `StylusDevice` 对象，笔线程区分触点用
**`StylusDeviceId`**（public int，plain 字段无线程亲和）—— 官方 GestureRecognizerPlugin
的多触点示例正是这么写的。

## 35. M24 热修④⑤ —— 异常长线第三刀：落笔锚点 · PinWet 描述 · 丢笔幽灵（2026-09-28）

现场第二轮反馈：刀①②③ 上线后**仍**偶发横贯直线。本轮换一种查法 —— 不追实现，而是
对着「要判什么、判据依赖什么状态」逐个字段自查（读源码 + 仓库外探针
`%TEMP%\twb_probe_da2f` 实证）。查到 **3 个会让检测整个失效的缺口 + 1 个假闸门 + 1 处死区**。

### 35.1 ★★ 落笔点从未登记成「原始锚」—— 检测里唯一没人查的那一跳

M18/M24① 的跳变判定全都依赖「上一个完好点的原始锚」`_rawLast*`，而 `_rawLast*` **只在
`ScanPoints` 里推进**。于是本笔的第一个 Move 包首点以 `_hasRawLast == false`（**无锚**）
的身份过检 —— `PacketPointFilter.Classify` 对无锚点直接判 Good。而「落笔之后马上搭上手掌」
恰恰是最常见的并入时机：那一下瞬移成了唯一没人查的跳变 —— 湿墨从落笔点连到手掌、
长线画出来、断笔旗标却还是 false，**整笔照旧提交**。这就是「修过仍有线」的残留口子。

修法（`InkSamplerPlugIn.OnStylusDown`）：`_buffer.Begin(first)` 之后补
`_rawLastX/Y = first.X/Y`、`_rawLastTimestamp = rawStylusInput.Timestamp`、`_hasRawLast = true`；
落笔包内部也逐点扫一遍（同包共享时间戳 ⇒ 判定退化为距离单条件），命中则
`downJumped = true` ⇒ `OnBreakDetected`，写回截断到跳变前的完好前缀。

### 35.2 ★★ `PinWet` 造点用了默认描述 ⇒ `Add` 必抛，被 `Fail` 静默吞掉

`PinWet`（M24② 的「钉点抑制湿墨」闸门）原写法：
`new StylusPointCollection(template.Description)` 之后 `pin.Add(new StylusPoint(x, y))`。
`new StylusPoint(x,y)` 的描述只有 X/Y/PressureFactor，而 `template`（本包的
`GetStylusPoints()`）的模板含 Width/Height 等属性 ⇒ **描述不兼容，`Add` 抛
ArgumentException**。异常被 `Fail()` 记一行日志吞掉 ⇒ 钉点没发生 ⇒ 原始坏点/跳变点直通
`DynamicRenderer`，长线照画。探针实证：旧写法跑完 `pin.Count == 0`（`Add` 抛后集合空）。

修法：借模板首点 —— `StylusPoint pinned = template[0]; pinned.X = x; pinned.Y = y;
pin.Add(pinned);`（模板就是同一包，描述必然一致）；`template.Count == 0` 直接 return。

### 35.3 ★ 分支顺序：必须「先作废、后写回」

Move/Up 的跳变分支原来的顺序是「先截断写回、后置旗标/清锚/清湿墨」。写回一旦抛异常
（§35.2 就是这么炸的），`Fail()` 只记日志、不外抛，异常路径把**「本笔作废」一起跳过** ⇒
长线既画出来又提交下去，这次检测完全白做。修法：`OnBreakDetected(...)`（Move）/
四个作废动作（Up：`_jumpDetected` + 清锚 + `_buffer.Reset()` + `TryResetRenderer()`）
提到截断写回之前。

护栏口径：harness **按方法切片后比 `IndexOf`**，不用全文 `Contains` —— 全文 `Contains`
分不清「同一分支里的先后」与「两个不相干位置各出现一次」。

### 35.4 ★★ 丢笔幽灵：只从撤销栈删还不够，统一时间线也要摘

`OnStrokeCollected` 的丢笔分支原来只做 `Silently(() => Strokes.Remove(e.Stroke))`。
探针实证：「加入本笔」那一步**照样留在撤销栈里**，老师一按 `Ctrl+Z` 就把长线整笔复活成
一条谁也没见过的鬼影。修法两步：

1. `InkHistory.DiscardAdded(stroke)` 同时覆盖两种时机 —— 变更还挂在**待提交事务**里
   （从 `_pending` 摘掉，提交时净空 ⇒ 不占撤销格）与**已经入栈**（栈顶若是「只加入这一笔、
   别的什么都没干」⇒ 整步弹掉）。配套把 `Edit.IsEmpty` 改成按引用去重的**净变化**判断
   （同一笔既加又删 ⇒ 净零；擦除是「移除原笔 + 加入碎笔」，两边**不同对象** ⇒ 非零，不受影响）。
2. ★ **本轮新发现**：只清 `InkHistory` 会让**统一时间线 `BoardHistory`** 留下一格幽灵 ——
   `StepRecorded` 早已把那一格记进时间线，`DiscardAdded` 弹撤销栈时时间线没跟着回退。
   后果：撤销按钮一直亮着，且老师按下的那一次 `Ctrl+Z` **被这一步白白吞掉一次**。
   故加 `InkHistory.StepDiscarded` 事件，`BoardHistory` 订阅后走 `NoteDiscardedInkStep()`
   （只在「末尾那格确实是墨迹步、且正好是当前指针位置」时摘；对不上宁可不动 ——
   指针错位的代价远大于多留一格退不动的幽灵步）。

这一层缺口是 **harness 断言抓出来的**：断言同时钉了 `History.UndoCount == 0` 与
`host.CanUndo == false`，前者过、后者不过 ⇒ 顺着这个差异才追到 `BoardHistory`。
教训：**「清一层」的修复要问一句「上面还有几层记着这件事」**。

### 35.5 阈值死区（留观，本轮不改）

`JumpDetector` 的判据是「速度超阈 **AND** 距离超阈」（`JumpSpeedThreshold = 2.0` /
`JumpMinDistance = 80`）。包内 dt=0 ⇒ 速度退化为「距离/1」⇒ 实际门限就是 80 world。
手掌并入的物理位移 > 85 world 才被抓，**79~85 world 之间是真实盲区**。本轮**不改**
（下调门限会误伤暴力快划），改为把盲区钉成断言：
`IsJump(...,79,0,0) == false`、`IsJump(...,81,0,0) == true`，将来有人动判据会先亮。

同属留观：落笔包登记的原始锚取的是包内**首个完好点**（与 `_buffer.Begin(first)` 一致），
而不是该包完好前缀的**末点** —— 于是下一包首点对照的锚偏早，多算了「落笔包内部那一小段」
的位移。真机落笔包内相邻点位移 < 5 world（281 Hz），整包量级 < 20 world，离 80 门限还有
4 倍余量，不会误判；真要收紧，把锚改推到最后那个完好点即可（一行）。

## 36. 代码体检热修 —— WebPanel 就绪队列线程安全（2026-09-29）

延续 §23 / §35 的代码体检查法，在 `WebPanelController` 抓到一处并发缺陷：
就绪闸门队列 `_queued`（`List<string>`）有 **7 个访问点**，且分属不同线程 ——

- `SendAsync` 入队：任意线程（插件 / 工具在后台线程发命令）；
- `OnReadyTimeout`（M23 就绪超时）Clear：**线程池线程**（`Timer` 回调）；
- `OnRawMessage` LoadFailed 分支 Clear、`OpenAsync` / `BeginClose` Clear、
  `FlushQueue` 的 `ToArray`+Clear：UI 线程；
- `QueuedCommandCount` 的 `Count` 读：任意线程（诊断 / harness）。

`List<T>` 不是线程安全的：并发 Add 撞上 Clear 会偶发抛
`IndexOutOfRangeException` / 损坏内部计数。现场症状是「点了没反应」且日志查不到
（命令在队列里丢了、异常发生在后台线程）—— 正是 §23 说的「最难查的那一类」。

### 36.1 ★ 一把 `_queuedLock` 守全部 7 个访问点，纪律是「先置标志、后清队」

- 新增 `private readonly object _queuedLock = new();`，7 个访问点**全部**过锁
  （`Count` 读也要：跨线程读长度同样是访问，漏一处就是 bug 还活着）。
- `FlushQueue` **锁内取快照**（`ToArray` + `Clear`）、**锁外逐条 `Post`**：
  持锁期间不调后端发送，免得队列锁被拖长、卡住超时回调的 Clear。
- `OnReadyTimeout` / LoadFailed 分支同一套纪律：先置 `_loadFailed = true`，
  再在锁内 `Clear` —— `SendAsync` 入队前本来就先查 `_loadFailed`，
  超时之后的新命令直接丢弃，不会滞留队列等一个永远不来的放行。
- `OnReadyTimeout` 原有的 `_open / _ready / _loadFailed` 三段复查
  （「宁可漏报也不误报」）原样保留，本刀只把队列访问加锁，不动判定。

### 36.2 ★★ 可测性先行：借既有假时钟注入推 `_testClock`，超时到期 0ms

就绪超时这条路径原先**不可测**：生产是真实 20 秒 `Timer`，回调在线程池 ——
harness 里真等 20 秒太慢，不等又撞不稳并发窗口。构造器本来就有 `nowMilliseconds`
注入点（原先只用来确定性断言 `changed` 节流），这次从它推出
`private readonly bool _testClock = nowMilliseconds != null`：注入了假时钟时
`ArmReadyTimer` 把到期设为 **0ms**（线程池立即触发），超时路径不用等 20 秒就
确定性地跑到，且天然在线程池上，并发撞车窗口真实存在。生产恒为 `false`，
走的还是 20 秒常量 `ReadyTimeoutMilliseconds`，行为零变化。

教训：兜底路径不可测，写得再对也证明不了 —— 先**借既有注入点**把路径变成
「确定性可跑到」，再谈写并发断言（别为一条路径新造一套时钟体系）。

### 36.3 ★★ 新断言 5b：8 线程 × 1000 条撞超时 Clear（Program.cs 就绪闸门 5b 块）

`OpenAsync` 后故意不 ready（模拟「页面一直没起来」，正是 M23 超时要接住的情形）⇒
主线程先塞 1000 条（保证超时 Clear 撞上时队列里确实在被写）⇒ 8 线程 × 1000 条
`SendAsync` 用 `ManualResetEventSlim` 一起起跑撞 0ms 到期的 `OnReadyTimeout`。
断言三件套：**不抛异常**（8001 条全收集）且 `IsLoadFailed`（按载入失败收口）
且 `Posted == 0`（一条命令都没发出去）。基线 1007/0 → **1008/0**。

护栏口径：只断言「不抛 + 收口正确 + 零发出」，**不断言**收尾时
`QueuedCommandCount` 的具体值 —— 超时 Clear 与线程收尾的先后是合法竞态，
断死值会自造假 FAIL（§5 老规矩：断言要比被测行为宽松到刚好抓住缺陷）。

## 37. M25 —— 参数面板文本参数：函数表达式 / 公式 LaTeX（2026-09-30）

### 37.1 契约：GfxTextField + IGfxTextParameterSink（纯新增，只加不改）
- 文本没有范围/步长概念 ⇒ 独立 <c>GfxTextField</c> 类（Key/Label/Value/IsReadOnly/IsMultiline），不给 <c>GfxParameterField</c> 加字符串重载（会留三个死字段）。
- <c>GfxParameterPanel.TextFields</c> 带默认空列表的新属性 ⇒ 旧插件构造面板不写它，行为与从前一模一样。
- <c>IGfxTextParameterSink</c> 是**新接口**而不是给 <c>IGfxParameterSink</c> 加方法：给已有接口加成员会让旧插件 dll 加载时满足不了接口（TypeLoadException）。宿主 is 判断，没实现 ⇒ 面板上「能看不能改」。
- 面板是纯数据（GfxTextField），不是控件 —— harness 无窗口也能断言「表达式项在不在、值与存档一不一致」。

### 37.2 接线
- <c>FunctionRenderer</c>：BuildPanel（表达式文本项 + 每个参数字母一个数值项【从当前表达式重新收集】+ 三个标注开关 0/1）+ <c>Apply</c>（param_*/开关）+ <c>ApplyText</c>（expr）。坏表达式放行：渲染器退化成红框占位，输入框本身是修表达式的入口。
- <c>FormulaRenderer</c>：BuildPanel（LaTeX 单个多行文本项；副标题 = 渲染正常 / 当前无效）+ <c>ApplyText</c>（latex）。
- <c>GfxParameterCoordinator.ApplyText</c> 与 Apply 完全同构：先取面板拿字段定义 → trim 后相等就不动（不留空白历史步）→ 问插件要落盘键值对 → 只在真的会变时才 BeginStep + <c>UpdateTexts</c>。
- <c>GfxParameterPanelView</c>：文本项行（单行回车提交 / 多行走「应用」按钮，LaTeX 60px 高换行）；可见性判定从「数值项非空」改成「数值项或文本项非空」—— 公式对象只有文本项没有数值项，「只有文本项的面板」不是空面板。

### 37.3 ★ Add 自动选中 ⇒ 像素计数探针必须先取消选中

## 38. M26 —— 数学键盘复用：MathKeyboard 抽进契约工程（2026-09-30）

### 38.1 为什么抽（兑现 M7.4 的「设计成可复用控件」）

  必须走 Abstractions（出现两份同名就是两个不同类型，is 判断直接失效）。
